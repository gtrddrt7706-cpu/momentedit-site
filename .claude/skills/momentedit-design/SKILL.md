# momentedit.kr 디자인 작업 규칙

## 이 사이트가 무엇인가

경기 고양시의 **프라이빗 스몰웨딩 스튜디오**. 하객 25명 이하, 가족 중심 예식.
평일 210만원 / 주말 280만원, 부가세 포함 전액 공개. 140분 시그니처 시퀀스가 핵심 상품.

타깃은 **대형 예식장의 소모적인 하루가 부담스러운 30대 예비부부**다.
이들이 사이트에서 확인하고 싶은 건 화려함이 아니라 **"여기는 믿을 만한가"** 하나다.

그래서 이 사이트의 디자인 목표는 자극이 아니라 **신뢰와 절제**다.
여백이 곧 고급감이고, 사진이 주인공이고, 타이포는 사진을 받쳐주는 역할이다.

## 절대 하지 말 것

이건 취향 문제가 아니라 **브랜드 정체성 훼손**이다. 사용자가 명시적으로 요청하지 않는 한 금지한다.

- **다크 모드 / 다크 테마 배경** — 이 브랜드는 밝고 따뜻한 톤이 전부다
  - ★**예외 1곳** — `index.html:4680`의 `@media (prefers-color-scheme: dark)` 블록은
    **지우지 말 것.** 다크 테마를 넣는 코드가 아니라 그 반대로, 다크 환경에서도
    라이트 값을 강제해 다크 렌더링을 막는 **방어 코드**다.
    `color-scheme:light`만으로는 이 미디어쿼리가 여전히 적용되어, 예전에 `html`/`body`가
    `#1a1714`(거의 검정)로 칠해지면서 **iOS 상태바 세이프에어리어가 검은 띠**로 보였다.
    지금은 라이트값(`#6f2b24` → 크림)과 동일하게 맞춰 그 현상을 없앤 상태다.
    이 규칙("다크모드 금지")을 근거로 블록을 삭제하면 **검은 띠가 그대로 회귀한다.**
    코드 자리에도 같은 취지의 주석이 남아 있다.
- **글래스모피즘, 뉴모피즘, 네온, 글로우, 그라디언트 메시**
- **보라·청록·형광 계열 액센트** (팔레트 밖의 색)
- **튀는 모션** — bounce, spring, elastic, 회전, 3D 틸트, 패럴랙스 과다
- **자동 재생 캐러셀, 팝업, 카운트다운 타이머, 긴급성 배너**
- **둥근 모서리 남발** — 라운드가 커질수록 캐주얼해진다
- **이모지를 UI에 사용**
- **본문에 순수 검정(#000)** — 크림 배경에서 너무 강하다
- **히어로 진사→크림 전환 구간을 실기기 확인 없이 만지는 것** — 2026-07-31 비네트를
  진사 심계로 바꿔봤으나(헤드리스 A/B에선 개선) 사용자가 실기기에서 '더 안 좋다'로
  판정해 회갈(58,45,34) 원복. 이 미묘한 톤은 헤드리스 렌더와 실기기(OLED·색관리)가
  다르게 보인다. 이 구간의 색 변경은 반드시 사용자 실기기 확인을 통과한 뒤에만 확정할 것

트렌디한 효과를 넣고 싶어지면 참으라. 웨딩 업종에서 트렌디함은 **곧 촌스러워질 위험**이고,
예비부부는 "요즘 스타일"이 아니라 "오래 봐도 괜찮을 것 같은 곳"을 찾는다.

## ★ 색·폰트를 고치기 전에 반드시 읽을 것 (함정)

**`shared/tokens.css`를 고치면 화면에 아무 반영이 안 된다.**

이 파일은 헤더에 "디자인 토큰 정본(single source of truth)"이라 적혀 있지만,
**어느 HTML에도 `<link>`되어 있지 않다.** (`*.html` 전체 grep 결과 참조 0건 · 2026-07-30 실측)
파일 자체 주석에도 "지금은 어디에도 연결 안 됨 = 라이브 영향 0"이라 쓰여 있다.

라이브에 실제 적용되는 색·폰트는 **각 페이지 `<style>` 안의 인라인 `:root`**다.

| 페이지 | `:root` 위치 | 변수 네이밍 |
|---|---|---|
| `index.html` | **306행** (2948행에 보조 블록) | `--bg` / `--text` |
| `mypage.html` | **43행** | `--bg` / `--text` |
| `admin.html` | **24행** | ★ `--paper` / `--ink` / `--card` (**이름이 다름**) |
| `schedule.html` | **34행** (431행에 보조 블록) | `--bg` / `--text` |

`guide.html:32` · `seat.html:28` · `parents.html:38` · `live.html:97` · `privacy.html:37` ·
`cancel.html:29` · `preview.html:17` · `order-preview.html:12`에도 `:root`가 있다.
(`inquiry.html` · `form.html` · `invitation-gallery.html`은 `:root` 없음)

tokens.css를 연결하는 것은 그 자체로 **되돌리기 비싼 변경**이다(전 페이지 렌더링에 영향).
사용자가 명시적으로 요청하지 않는 한 연결하지 말고, 인라인 `:root`를 고친다.

## 색·변수 수정 시 3개 페이지 동기화 규칙 (고객 화면만)

브랜드 색·폰트 변수를 바꾸면 **`index` · `mypage` · `schedule` 3개를 함께 고친다.**
한 곳만 고치면 고객이 페이지를 넘나들 때 톤이 어긋난다.

### ★ `admin.html`은 동기화 대상이 아니다 (2026-07-30 사용자 지시)

`admin.html`은 **내부 관리자 전용 화면**이라 고객 브랜드 톤을 따라갈 이유가 없다.
`--paper` / `--ink` / `--card` 변수명을 **그대로 유지한다.**

- 고객 화면 3개를 고쳤다고 해서 admin을 따라 고치지 말 것
- admin을 `--bg`/`--text` 네이밍으로 "통일"하지 말 것 — 이름이 다른 게 정상이다
- admin에만 있는 업무용 색(`--blue` `--red` `--redbg` `--yellow` `--yellowbg` `--gold-line`)도 그대로 둔다

동기화할 때 주의할 점:

- **페이지마다 변수 집합이 다르다.** 없는 변수를 지우거나 임의로 채우지 말 것.
  - `index`에만: `--gold-text` `--footer-bg` `--footer-text` `--max` `--gap` `--tracking-ko` `--serif-jp`
  - `mypage`에만: `--gold-deep` `--gold-deeper` `--label-soft` `--mono` `--card-white` `--dot-future`
  - `schedule`에만: `--radius`
- **이미 값이 어긋나 있는 변수가 있다.** 통일한다면 의도적으로 결정할 것이지,
  "같아야 하니까" 한쪽에 맞추면 접근성이 무너진다.

  | 변수 | index | mypage | schedule | tokens.css |
  |---|---|---|---|---|
  | `--hairline` | `rgba(28,27,25,.18)` | `#E6E1D8` | `rgba(28,27,25,.14)` | `#E6E1D8` |
  | `--label-soft` | (없음) | `#6F695D` | (없음) | `#7C766A` |
  | `--gold-soft` | (없음) | `rgba(...,.28)` | `rgba(...,.16)` | `rgba(...,.28)` |

- `mypage.html:45` 주석에 "index.html :root 와 동일"이라 적혀 있지만 **사실이 아니다.**
  주석을 근거로 삼지 말고 실제 블록을 대조하라.

## 팔레트 (저장소 실측값)

아래는 추측이 아니라 인라인 `:root`에서 읽은 실제 값이다.

| 역할 | 변수 | 값 | 쓰는 곳 |
|---|---|---|---|
| 캔버스 | `--bg` (admin `--paper`) | `#FAFAF8` | 페이지 배경. 기본값 |
| 캔버스 2·3 | `--bg2` / `--bg3` | `#F5F3EF` / `#EDEBE6` | 섹션 교차 배경 |
| 본문 | `--text` (admin `--ink`) | `#1C1B19` | 순수 검정 대신 따뜻한 먹색 |
| 강조 | `--accent` | `#3A2D22` | 제목·버튼 배경 |
| 브랜드 씰 | `--seal` | `#6B2A24` (딥 버건디) | CTA, 강조 포인트. **넓은 면적 금지** |
| 보조 텍스트 | `--sub` | `#5A554C` | 설명문 |
| 옅은 텍스트 | `--light` | `#75705F` | 캡션·라벨 하한선 |
| 테두리 | `--border` | `#DDD8D1` | |
| 골드(장식) | `--gold` | `#B89A75` | **선·아이콘 전용. 글자 금지** |
| 골드(텍스트) | `--gold-text` / `--gold-deep` | `#7A5F37` | 골드빛 글자는 반드시 이 값 |

`html`의 초기 배경만 `#6f2b24`로 따로 지정돼 있다(`index.html:345`).
첫 페인트 때 흰 캔버스가 비치는 것을 막는 용도이고 **팔레트 토큰이 아니다.**
`--seal`(`#6B2A24`)과 값이 비슷하지만 다른 색이니 혼동하지 말 것.

### ★ 골드는 2값 분리를 반드시 유지한다

이건 실수로 갈라진 게 아니라 **접근성 때문에 의도적으로 나눈 것**이다.
"중복이니 통일하자"는 판단으로 하나로 합치지 말 것.

```
--gold      #B89A75   장식 전용 (선·아이콘·테두리)
--gold-text #7A5F37   텍스트 전용 (index) = --gold-deep (mypage)
```

`#B89A75`는 크림 배경에서 **2.54:1**이라 WCAG AA(4.5) 미달이다. **글자에 쓰면 안 된다.**
`index.html:322`와 `mypage.html:60` 코드 주석에도 같은 처방이 남아 있다.

#### 둘 중 뭘 쓸지 판단하는 기준 (2026-07-30 사용자 지시)

"장식이냐 텍스트냐"는 **글자와 붙어 있느냐**로 가른다.

- **`--gold` (장식)** — 글자와 **떨어진** 요소에만. 구분선 · 테두리 · 독립 아이콘.
- **`--gold-text` (텍스트)** — 글자와 **같은 줄에 붙어 있으면 전부.**
  기호 · 단위 · 화살표 · 플러스/마이너스 같은 글리프도 여기 포함된다.
  "아이콘이니까 장식"이라는 이유로 `--gold`를 쓰지 말 것.
- **한 요소 안에 두 골드를 섞지 않는다.**

실제 사례: `.faq-more-toggle` 버튼의 `"더 자세한 질문 6 보기 +"`에서
`"6"`은 텍스트, `"+"`는 아이콘이라 톤을 갈랐더니 **위계로 안 읽히고 색 오류처럼 보였다.**
`"+6"`은 한 덩어리 라벨이므로 둘 다 `--gold-text`로 통일했다.

검증된 대비비(배경 `#FAFAF8` 기준 · 직접 계산):

```
#1C1B19  --text          16.47:1   AAA
#3A2D22  --accent        12.73:1   AAA
#6B2A24  --seal          10.14:1   AAA   (역상: 크림 글자 + 씰 버튼도 동일)
#5A554C  --sub            7.08:1   AA
#7A5F37  --gold-text      5.71:1   AA    (골드빛 글자는 여기까지)
#6F695D  --label-soft     5.21:1   AA    (mypage 값)
#75705F  --light          4.74:1   AA    ← 텍스트 하한선
────────────────────────── 이 아래는 본문 텍스트 사용 금지 ──────────────────────────
#7C766A  --label-soft     4.32:1   미달  (admin·tokens.css에 남아 있는 값)
#9A7B4F  --gold-deep      3.78:1   미달  (admin에 남아 있는 값)
#B89A75  --gold           2.54:1   미달  ← 장식 전용
#C2A988  --gold-btn-border 2.16:1  미달  ← 테두리 전용
```

보조 텍스트를 옅게 하고 싶은 유혹이 있을 텐데, `--light`(`#75705F`, 4.74:1) 아래로 내려가면
본문 크기에서 접근성 기준에 미달한다. 옅어 보이게 하고 싶으면 **색이 아니라 크기와 자간**으로 조절하라.

`admin.html`의 `--label-soft`(`#7C766A`)와 `--gold-deep`(`#9A7B4F`)은 현재 AA 미달 값이다.
관리자 전용 화면이라 우선순위가 낮지만, **이 값을 고객 화면으로 옮겨 쓰지는 말 것.**

## 접근성 결정 기록 — 전제가 깨지면 재검토할 것

과거에 내린 접근성 판단 중 **특정 실측을 전제로 한 것**을 남긴다.
전제가 바뀌었는데 결정만 남아 있으면 그때부터 그 결정이 위반이 된다.

### `.live-mockup-wrap`의 `aria-hidden="true"` (2026-07-30)

`index.html:5605`. 디지털 참석 페이지를 축소해 보여주는 **장식용 목업**이라
스크린리더가 건너뛰게 했다. 안에 4.5~9px 텍스트가 49건 들어 있는데
읽으라고 넣은 문구가 아니다(크기는 의도된 것이므로 키우지 말 것).

이 결정은 **"내부에 포커스 가능 요소가 0개"라는 실측에 근거한다.**
(측정 당시: `a[href]`·`button`·`input`·`[tabindex]` 0개 · `img` 0개 · 하위 156개 전부 비대화형)

**★ 이 목업에 버튼·링크·입력이 추가되면 `aria-hidden`을 반드시 함께 재검토할 것.**
`aria-hidden="true"` 안의 요소는 **포커스는 되는데 스크린리더가 읽지 않아**
키보드 사용자가 "지금 어디에 있는지 모르는" 상태가 된다. 명백한 접근성 위반이다.

목업에 대화형 요소를 넣어야 한다면 `aria-hidden`을 떼고 대신 개별 텍스트를
처리하거나, 대화형 요소를 목업 바깥으로 빼는 쪽을 검토한다.

## 타이포그래피

이 사이트는 이미 좋은 패턴을 쓰고 있다. **바꾸지 말고 일관되게 지켜라.**

```
THE REALITY          ← 영문 라벨: 작게, 대문자, 자간 넓게, 버건디 또는 옅은 먹색
결혼식 하루가                ← 국문 헤드라인: 크게, 굵기는 중간(600 이하), 자간 좁게
15시간의 소모전이 되는 이유       ← 국문 서브: 헤드라인의 55~65%
```

규칙:

- **영문 라벨의 자간을 넉넉히** (0.12em~0.2em). 이게 에디토리얼 인상을 만든다
- **국문 헤드라인의 자간은 좁게** (-0.02em 내외). 한글은 자간이 넓으면 흐트러진다
- **굵기는 700을 넘기지 말 것.** 웨딩 사이트에서 굵은 글씨는 소리 지르는 느낌이다
- 본문 행간 1.7~1.9. 한글 장문은 넉넉해야 읽힌다
- 한 화면에 **폰트 크기 3단계 이하**

### 크기 스케일 — 7단계 고정 (2026-07-31 적용, [TYPO_SCALE7])

본문·라벨은 **11 / 12 / 13 / 14 / 16 / 18 / 20** 일곱 값만 쓴다. 반px 금지.
- 새 크기가 필요하면 이 7개 중에서 고른다. 8번째 값을 만들지 않는다.
- **디스플레이(22px 이상)**·**마이크로 라벨(8·9px 눈썹표기)**은 별도 계층 — 기존 값 유지.
- **폰 목업 장식 구역**(`live-mockup-wrap`·`jr-showcase`·`delivered-mail`·`.dm-*`·`.mock*`)의

### ★ index.html 섹션 리듬 — 2단 (2026-07-31 v2)

**섹션 사이 간격은 `.divider`가 단독으로 정한다. 값은 두 단계뿐이다.**

```
기본 경계  : --gap × 2 + 스탬프 40px            = 모바일 200px · 데스크톱 248px
장 전환 4곳: (--gap + 32px) × 2 + 스탬프 40px   = 모바일 264px · 데스크톱 312px
```

장 전환 4곳 = `#about + .divider` · `#live + .divider` · `#invest + .divider` ·
`#journey + .divider` (갤러리 진입 · 가격 진입 · 여정 진입 · 사람 소개 진입).
규칙은 `index.html`의 `[SECTION_RHYTHM_TIER2]` 마커에 있다.

조절 손잡이는 둘뿐이다. **기본 리듬은 `--gap`**(`:339` 데스크톱 104px ·
모바일 미디어쿼리 80px), **장 전환의 여분은 `+32px` 상수** 하나. 구간별로
개별 값을 주기 시작하면 다시 드리프트로 돌아간다.

**이력 — 한 번 틀렸던 판단.** 원래 4구간이 248·256·264px로 제각각이었고,
조사 결과 여분값이 경계의 위계가 아니라 그 섹션을 끝내는 컴포넌트를 따라가는
드리프트였다(예: `invest`·`journey`가 둘 다 +56인 건 우연히 같은 `.cta-block`으로
끝나서). 그래서 200/248 단일값으로 통일했는데, **배포 직후 사용자가 답답함을
느꼈다.** 전후 실렌더 비교로 확인하니 좁아진 4곳은 전부 콘텐츠 성격이 바뀌는
자리였다 — 출신은 드리프트가 맞았지만 눈에는 장 사이 쉼표로 기능하고 있었다.

**교훈: 여백의 출신이 우연이어도 체감은 위계일 수 있다. 리듬처럼 몸으로
느끼는 값을 통일할 때는 근거가 완벽해도 배포 전에 사용자 눈으로 확인받을 것.**

### 마진이 섹션 밖으로 새는 구조 (재발 지점)

`section`에는 **상하 padding이 없다**(`padding: 0 28px`). 그래서 첫·마지막 자식의
세로 마진이 섹션 경계를 통과해 빠져나가고, 그만큼 구간이 넓어진다.
중첩된 자식의 마진도 부모에 padding/border가 없으면 계속 통과한다
(실제로 `.price-block`의 `margin-top:36px`이 `.reveal`을 뚫고 나왔다).

차단 규칙이 `index.html:1424`에 있다.

```css
section:not(#rsvp) > *:last-child { margin-bottom: 0 }
#invest > .reveal:first-child > .price-block:first-child { margin-top: 0 }
```

- **`#rsvp`는 일부러 제외했다.** 마지막 섹션이라 이 마진이 footer와의 간격(88px)을
  만든다. 여기까지 0으로 만들면 footer 간격이 같이 바뀐다.
- **인라인 스타일은 이 규칙을 이긴다.** 새 여백 문제가 보이면 CSS부터 찾지 말고
  해당 요소의 `style="margin:…"`을 먼저 확인할 것.
- **`display:flow-root`로 가두지 말 것.** 마진을 섹션 안에 가두면 측정값은 200px가
  되지만 공백이 섹션 안쪽으로 옮겨갈 뿐이라 **눈에 보이는 리듬은 그대로다.**
  실측으로 확인했다 — 간격은 224px 줄었는데 페이지 총높이는 오히려 40px 늘었다.
  마진은 가두는 게 아니라 **없애야** 한다.

## 모션

넣어도 되는 것은 딱 두 종류다.

1. **스크롤 진입 페이드업** — `opacity 0→1`, `translateY 16px→0`, 600~800ms, ease-out
2. **호버 시 아주 미세한 변화** — 밝기 4% 또는 밑줄 등장. 크기 변화는 1.02배 이하

지켜야 할 선:

- `prefers-reduced-motion: reduce`를 **반드시** 존중할 것
- 한 섹션에 애니메이션 요소 3개 이하. 순차 지연(stagger)은 80ms 이하
- 스크롤 하이재킹, 고정 스크롤, 스크럽 애니메이션 금지

## 모션 램프 ([MOTION_RAMP5], 2026-07-31)

**전환 시간은 5단계만** — `0.12s`(즉각 피드백) · `0.3s`(호버·색) · `0.45s`(이동·변형)
· `0.7s`(등장) · `1.2s`(대형 연출). 통합 전 26종이 흩어져 있었고 0.3·0.4·0.45가
공존해 구분되지 않는 이웃값이었다(0.05s 차이는 사람이 못 느낀다).

**이징은 `var(--ease)` 하나로 통일.** CSS 기본 `ease`나 `cubic-bezier(0.16,1,0.3,1)`
리터럴을 직접 쓰지 말 것 — 전자는 브랜드 감각이 아니고(19곳에서 발견), 후자는
`--ease`와 같은 값의 중복이다(7곳). 특수 이징 `--ease-ink`(잉크 번짐)·
`--ease-seal`(인장)만 예외.

**★`transition-delay`와 shorthand 4번째 값(지연)은 램프 대상이 아니다.**
모바일 메뉴·아카이브 그리드의 `0.08 / 0.16 / 0.24 …`는 등차 스태거 수열이라
램프에 맞추면 리듬이 깨진다. 값만 보고 '정리'하지 말고 지속시간인지 지연인지 먼저 볼 것.

## 목록을 '설정 앱'으로 만들지 말 것 ([ADV_INDEX], 2026-08-01)

상담 도우미 패널(`.me-adv-*`)의 질문 메뉴가 "너무 올드하다"는 지적을 받고 개편했다.
**구형이 낡아 보인 원인 세 가지는 다른 목록에도 그대로 적용된다.**

1. **전폭 헤어라인을 줄마다 긋는 것.** 12줄이면 선이 12개다. 이 브랜드의 주 표현수단인
   여백을 12등분해 잘라버린다. 선은 가장 싸고 가장 시끄러운 구분자다 — **여백으로 나눠라.**
2. **`justify-content: space-between`으로 글자와 화살표를 양 끝에 붙이는 것.**
   가운데 200px짜리 빈 골짜기가 생기고, 그 순간 '표(table cell)'로 읽힌다.
   목차처럼 **`flex-start` + 글자 바로 뒤에 ›**를 붙이면 같은 데이터가 에디토리얼로 읽힌다.
3. **위계 역전.** 메뉴 칩이 16px인데 그 메뉴가 여는 답변 버블은 14px이었다.
   메뉴가 내용보다 크게 외치고 있었다. **메뉴는 내용과 같은 격이거나 한 단 아래다.**

개편 규격(칩): 14px · 400 · 자간 0.01em · 행간 1.5 · 패딩 `12px 10px`(= 45px 탭 타깃) ·
`gap: 2px` · 라운드 6px · 선 없음. `:hover`는 `--seal`(10.14:1)로 — 구형의 `--gold`는
**호버하는 순간 2.54:1로 떨어져 AA 미달**이었다. 폰엔 호버가 없으므로 `:active`에
`background: var(--bg2)` 워시를 반드시 함께 둔다.

`.me-adv-chips`에 `margin: 2px -10px 0`을 준 이유: 눌림 워시가 글줄 좌우로 10px 번져야
손가락이 누른 면적과 보이는 면적이 맞는다. 글자는 칩의 `padding-left: 10px`이 되받아
본문 22px 라인을 유지한다.

### 라벨 위 여백은 아래의 2배 ([TYPO_RHYTHM] 실적용 사례)

`무엇이 궁금하세요?` 라벨의 위·아래 여백이 같으면 **헤더 것인지 목록 것인지 안 읽힌다.**
위 34px(본문패딩 24 + 라벨 margin-top 10) · 아래 14px(칩 margin-top 2 + 칩 패딩 12)로 잡았다.

### 한글에 라틴 서체 규칙을 걸지 말 것

구형 `.me-adv-chips-label`은 한글을 `var(--serif)`(Cormorant) + `font-style: italic` +
`text-transform: uppercase`로 조판하고 있었다. Cormorant엔 한글 글리프가 없어 폴백으로
떨어지고, 거기 italic이 걸려 **가짜 기울임**이 되고, uppercase는 한글에 **아무 효과가 없다.**
한글 소라벨은 `var(--serif-ko)` · 12px · 400 · 자간 0.08em([LABEL_KO_TRACK]) · `--sub`.

### `›`의 광학 보정

`›`(U+203A)는 명조 em박스에서 수학축 근처에 앉아 한글보다 **2px 낮게** 보인다.
`position: relative; top: -2px`로 맞춘다. **정렬은 `top`, 움직임은 `transform`** —
둘을 `transform`에 섞으면 호버 때 보정이 날아간다.
색은 `--gold-text`다. 글자와 같은 줄의 글리프이므로 장식 `--gold` 금지(기존 규칙 그대로).
`opacity`로 흐리게 하지도 말 것 — 0.75만 걸어도 5.71:1이 3.4:1로 떨어진다.

## 오버레이가 켜지면 상태바 색을 직접 고정하라 ([ADV_TC], 2026-08-01)

**증상**: 크림색 상담 패널을 열면 아이폰 상태바만 진사 띠로 남았다.

**원인**: 패널의 `lockScroll()`이 모바일에서 `body{position:fixed}`를 걸면 **`scrollY`가
0으로 붕괴한다.** 그러면 히어로 스크롤 핸들러가 "지금 히어로 맨 위"로 오해하고
`theme-color`를 `#6f2b24`로 되돌린다. 패널 코드는 `theme-color`를 한 번도 만지지 않았는데
패널을 여는 행위가 간접적으로 색을 바꾸고 있었다.

**처방**(이 사이트의 계약이다 — 새 오버레이도 따를 것):

```
열 때  window.__meTCLock = 1;  meta#meThemeColor.content = 오버레이 배경색
닫을 때 window.__meTCLock = 0;  window.__meTCSync()      // unlockScroll() 뒤에 호출
```

히어로 핸들러는 `if(tc && !window.__meTCLock)`로 잠금을 존중한다.
`__meTCSync()`가 **캐시(`tcCream`)를 비우고 다시 계산**하는 게 핵심이다. 그냥 스크롤
이벤트만 쏘면 캐시가 "이미 크림"이라 판단해 **닫은 뒤 복귀가 한 번 씹힌다.**
4가지 경우(히어로 위/아래 × 열기/닫기)를 전부 실측해 통과시켰다.

**일반 규칙: `position:fixed` 스크롤 잠금은 `scrollY`를 읽는 모든 코드를 거짓말하게 만든다.**
새 오버레이를 만들 때 스크롤 위치에 반응하는 다른 스크립트가 있는지 먼저 확인할 것.

## 핸들러를 그대로 넘기지 말 것 ([ADV_OPEN_TOP], 2026-08-01)

```js
fab.addEventListener('click', open);        // ✗ open(MouseEvent) — 첫 인자가 truthy가 된다
fab.addEventListener('click', function(){ open(false); });   // ○
```

`function open(keepScroll)`에 MouseEvent가 들어가 `if(!keepScroll){ body.scrollTop=0 }`이
**통째로 건너뛰어졌다.** 직전 `addMsg(인사말)`의 `scrollDown()`이 남긴 211px이 그대로 남아,
FAB로 열면 **항상 라벨과 상위 3개 항목(비용·결제 / 예식 진행·시간 / 공간·위치·하객)이
화면 위로 잘려 있었다.** 가장 많이 묻는 항목이 첫 화면에서 안 보이고 있었다는 뜻이다.

**옵션 인자를 받는 함수를 리스너에 직접 넘기지 말 것.** 이 사이트에서 실제로 난 사고다.

- 방향이 확정된 뒤에만 `preventDefault` — 세로 스크롤을 먼저 뺏지 않는다
- 시작점 조상에 가로 스크롤·`canvas`·입력 요소가 있으면 포기

**임계값**: 확정 30%(화면폭) 또는 속도 0.55px/ms. 따라오는 최대 이동 42%.
**연출**: 페이지가 손가락의 55%만큼 따라 밀리고 왼쪽에 진사 빛이 번진다.
되돌아갈 땐 0.3s, 나갈 땐 0.45s — 둘 다 `--ease`. 스프링·바운스·그림자 없음.

## 작업 절차

**1) 고칠 페이지의 `:root`부터 연다**

이 저장소에는 **빌드 도구가 없다.** `package.json` · 번들러 · 프레임워크가 없는
순수 정적 HTML 멀티페이지이고, CSS·JS가 각 HTML에 인라인으로 들어 있다.
`tailwind.config` · `globals.css` · `theme` 파일을 찾지 말 것 — **존재하지 않는다.**

```
1. 고칠 페이지의 인라인 :root 를 연다 (위 '함정' 절의 위치표 참조)
2. shared/tokens.css 는 미연결이므로 고쳐도 반영되지 않는다
3. 위 팔레트 표와 다른 값이 있으면 사용자에게 알리고 저장소 값을 기준으로 삼는다
4. 브랜드 색·폰트 변수를 바꾼다면 4개 페이지 동기화 규칙을 함께 지킨다
```

파일이 크다(`index.html` 296KB · `mypage.html` 700KB). 통째로 읽지 말고
`:root` 위치와 고칠 셀렉터를 grep으로 좁혀서 접근하라.

**2) 고치기 전에 반드시 설명한다**

무엇을 왜 바꿀지 먼저 말하고 동의를 받는다. 웨딩 사이트는 사장님의 감각이
정답인 영역이 많다. 코드부터 고치지 말 것.

**3) 한 번에 한 섹션만**

전체를 한꺼번에 바꾸면 되돌리기 어렵고, 어디서 나빠졌는지 알 수 없다.
"히어로만", "FAQ만" 식으로 범위를 좁혀 진행한다.

**4) 바꾼 뒤에는 확인 목록을 제시한다**

- 모바일 390px에서 깨지지 않는가
- 대비비가 기준을 넘는가 (본문 텍스트는 `#75705F` 4.74:1 이 하한선)
- 골드를 글자에 썼다면 `#7A5F37`인가 (`#B89A75`는 2.54:1로 금지)
- `prefers-reduced-motion`에서 애니메이션이 꺼지는가
- 기존 섹션과 여백 리듬이 어긋나지 않는가
- 브랜드 변수를 건드렸다면 고객 화면 3개(`index`·`mypage`·`schedule`)가 동기화됐는가
  (`admin`은 동기화 대상이 아니다 · `--paper`/`--ink` 유지)
- `shared/tokens.css`만 고치고 반영됐다고 착각하지 않았는가

**5) 판단이 서지 않으면 덜 하는 쪽을 고른다**

이 브랜드에서 과한 것보다 밋밋한 것이 낫다.
