# 왕복 작업 규칙 — 코워크 ↔ 코드

작성 2026-09-06. 기준 커밋 `4b49b977`.

---

## 1. 왜 이 규칙이 필요한가

`/점검` 라운드에서 **붉었던 4건 중 3건이 «재는 쪽» 문제**였다(#665).
같은 기간 코워크가 낸 3건 중에도 **2건이 오탐**이었다.

- 히어로 로고 대비 `1.09:1` — **페이드인 중간**을 잰 값이었다
- 「빈 화면이 연속된다」 — **리빌 대기가 1.2초로 짧았다**

양쪽 타율이 **똑같이 3분의 1**이다. 한쪽이 더 정확해서 왕복하는 게 아니다.

> **그래서 왕복의 목적은 발견을 늘리는 것이 아니라 헛발을 걸러내는 것이다.**

발견 하나를 더 찾는 것보다, 이미 올라온 발견이 진짜인지 가려내는 편이 값이 크다.
헛발은 조용히 사라지지 않는다 — 고치는 손이 실제 화면을 망가뜨린다.

## 2. 역할

| | 할 수 있는 것 |
|---|---|
| **코드만** | 저장소 읽기·수정 · `push` · `merge-guard` · 배포 · git 이력 조회 · GAS |
| **코워크만** | 사용자가 올린 이미지 읽기 · 인스타 릴스 영상 · 웹 문서와 GitHub 조회 · 독립 클론으로 반증<br>★외부 웹사이트 렌더는 **불가**(차단됨) |
| **겹침** | **렌더 측정 — 일부러 둘 다 잰다.** 이게 이 규칙의 핵심이다 |

겹치는 일을 일부러 중복시키는 이유는 §1 이다. 두 값이 갈리는 순간이 헛발을 잡는 자리다.

### ★2026-09-06 개정 — 배분 근거는 「누가 쥐고 있나」가 아니라 「누가 push 할 수 있나」다

코워크 컨테이너는 `momentedit-site` 에 **push 를 못 한다**(git proxy 403 ·
「not in this session's authorized repository set」). `fetch` 는 되고 `push` 만 막힌다.
사용자가 세션 소스에 저장소를 넣기 전까지는 그 상태가 유지된다.

그래서 §7 「같은 파일 동시 편집 최소화」의 취지는 그대로 두되 배분 규칙을 바꾼다:

| | 코워크 | 코드 |
|---|---|---|
| 읽기·측정·A/B 검증 | ○ | ○ |
| 파일 수정 | 로컬에서만(검증용) | ○ |
| **커밋·push·병합** | **×** | **○** |
| 실제 백엔드가 도는 검사(GAS 제출 등) | × (외부망 못 염 · 실제 문의가 나가면 안 된다) | ○ |

**코워크의 산출물은 «패치 + 재본 값»까지다.** 그것을 코드 쪽이 받아
①토큰 단위로 감사하고 ②자기 환경에서 다시 재고 ③게이트를 돌려 올린다.
값이 갈리면 **폰트가 온전한 쪽(코드)이 정본**이다(§5-13).

## 3. 발견을 올리는 형식

```
발견 ·      (한 줄)
잰 값 ·     (숫자. 조건 명시 — 폭 · 스크롤 위치 · 대기시간)
잰 방법 ·   (어떤 API 로 어떻게 · 무엇을 기준선으로 삼았는지)
기준 커밋 · (어느 커밋에서 쟀는가)
반대편 확인 · 일치 / 불일치 / 미확인
```

★「잰 방법」에 **무엇을 기준선으로 삼았는지**를 반드시 적는다.
같은 화면을 봐도 기준선이 다르면 값이 갈린다 — §6 이 실제 사례다.

## 4. 판정

| 상태 | 하는 일 |
|---|---|
| **양쪽 일치** | 진짜다. 고칠 안을 만든다 |
| **양쪽 불일치** | **먼저 «재는 쪽»을 의심한다.** 제품을 고치기 전에 측정 조건 차이(대기시간·뷰포트·커밋·기준선)부터 대조한다 |
| **한쪽만 쟀다** | **«미확인»으로 두고 반대편에 넘긴다. 고치지 않는다** |

불일치일 때 제품부터 고치면, 실제로는 멀쩡한 화면을 «고쳐서» 망가뜨린다.
지금까지 그렇게 될 뻔한 것이 5건이다(§1 의 3건 + 코워크 2건).

## 5. 측정할 때 지켜야 할 것 — 지금까지 걸린 함정들

1. **리빌 애니메이션은 최소 2초 기다린 뒤에 잰다.**
   1.2초로 쟀다가 「빈 화면 연속」 오탐이 났다.
2. **글자 겹침은 `Range.getClientRects()` 로 잰다.**
   `element.getBoundingClientRect()` 는 줄바꿈된 블록의 **전체 상자**라 실제 글자와 다르다.
3. **대비는 화면에 그려진 색을 재고, 애니메이션이 끝난 뒤에 잰다.**
   페이드인 중간을 재서 `1.09:1` 오탐이 났다.
4. **헤드리스와 실기기는 다르게 보인다.** 미묘한 톤은 실기기 확인 전에 확정하지 않는다
   (히어로 진사→크림 구간이 실제로 그랬다).
5. **잰 커밋을 항상 적는다.** 상대가 다른 커밋을 보고 있을 수 있다.
6. **★한 스크롤 지점만 재지 않는다.** 문서 전체를 훑어야 최악값이 나온다.
   한 지점만 재면 «그 자리에 긴 줄이 없어서» **0 이 나온다** — 실제로 880·900px 에서 그렇게 속았다.
7. **★무엇을 기준선으로 삼았는지 적는다.** 아이콘의 **버튼 상자**와 **실제 획**은 12.5px 떨어져 있다.
   기준이 다르면 같은 화면에서 27px 과 15px 이 동시에 나온다(§6).
8. **★자동 생성 파일을 손으로 고치지 않는다.** `audio-review-tone.html` 을 손편집했다가
   게이트에 걸렸다. 생성기와 **짝으로** 고쳐야 한다.
9. **★배경 알파는 «합성한 뒤» 잰다.** `rgba(...)` 배경을 그대로 대비 공식에 넣으면 값이 무너진다.
   부모 배경 위에 알파를 합성한 실제 색으로 재야 한다.
10. **★가상요소는 자기 `background` 를 첫 레이어로 깔고 잰다.**
   `::before`/`::after` 가 스스로 배경을 칠하면 그 위에 글자가 얹힌다. 부모 배경으로 재면
   전혀 다른 값이 나온다 — `.price-block.highlight::before` 「OPENING」이 그래서 `1:1` 로 잡혔다.
   실제로는 `--seal` #6B2A24 위 흰 글자로 **10.6:1**, 넉넉히 통과다.
11. **★고정 레일은 «전환 중» 좌표를 준다.** `.me-fab-stack` 은 페이지 위쪽에서
   **투명 + 오른쪽 12px** 로 숨어 있다가 스크롤에 맞춰 돌아온다. 한 번의 `page.evaluate` 로
   여러 요소를 훑으면 전환이 끝나기 전 좌표를 읽어 레일이 실제보다 12px 오른쪽에 잡히고,
   **7px 겹침이 통째로 사라진다.** 요소마다 스크롤하고 **기다렸다** 재라
   (`home-a11y.mjs` 의 `[A11Y_SETTLE]`). 초안이 정확히 이래서 진짜 결함을 못 잡았다.
12. **★`scrollIntoView` 앞에 `html{scroll-behavior:auto}` 를 주입한다.**
   부드러운 스크롤이 켜져 있으면 `scrollIntoView` 는 «예약»만 하고 돌아와,
   바로 뒤의 `getBoundingClientRect()` 가 **옛 좌표**를 읽는다.
13. **★코워크 쪽 절대 좌표·문서 높이는 그대로 믿지 않는다 — 웹폰트가 일부 안 뜬다.**
   코워크 컨테이너는 `fonts.googleapis.com` 을 못 받아 Cormorant Garamond 가 대체 세리프로
   그려진다(한글 Noto 는 정상). 영문 라벨 폭이 달라지면 줄바꿈이 달라지고 문서 높이가 달라진다.
   실측 차이: `inquiry.html` 문서 높이 390px 에서 **99px**, 320px 에서 **66px**.
   → 비교는 반드시 **같은 환경 안의 델타**로 한다. 절대값이 필요하면 코드 쪽 값이 정본이다
   (`document.fonts.check('12px "Cormorant Garamond"')` 로 어느 쪽인지 먼저 확인할 것).
14. **★대비는 «값»이 아니라 «역할»로 가른다.**
   장식선·순수 구분자(정보를 나르지 않는 `·` 같은 것)는 대비 하한선 밖이다.
   기능 마커(FAQ 의 `+`, 링크의 `↗` 처럼 상태·동작을 알리는 글리프)는 비텍스트 3:1 을 지켜야 한다.
   `--gold` 를 쓰는 가상요소 12개 중 **글자를 그리는 것이 4개**, 그중 **기능 마커는 2개**였다.
   역할로 안 가르면 12개나 4개를 다 올려 «고칠 것»을 부풀리게 된다.
15. **★보정이 필요하면 크기가 틀린 것일 수 있다.**
   저널 재생 버튼은 26px 이라 메타줄(20.3px)을 밀었고, 그걸 위아래 음수 마진 3px 으로 눌렀다.
   20px 으로 줄이자 **보정 자체가 필요 없어졌다**(#673). 증상을 누르기 전에 원인 치수를 의심할 것.
16. **★CSS 속성의 «방향»을 기억으로 말하지 말고 주입해서 재라.** (코워크 제안)
   `min-height` 는 하한이지 상한이 아니라 크기를 «막을» 수 없다. 그런데 내용 높이를 16px 로
   어림잡은 탓에 「padding 을 키워도 min-height:40px 에 막혀 40 에서 멈춘다」는 판정이 나왔다.
   실제 내용은 24px 이라 padding 10 이면 44 로, 하한을 이미 넘어선다.
   한 페이지 안에서 순서대로 주입해 재면 30초에 갈린다 — 원본 [40] · padding만 [44] · 둘 다 [44].
17. **★값이 갈리면 «세는 규칙»부터 맞춘다. 대개 대상이 다른 것이다.**
   `inquiry.html` 타이포를 코워크는 「18종」, 코드는 「42종」으로 셌다. 둘 다 맞았다 —
   코워크는 **크기 종류**를, 코드는 **(크기 × 클래스) 줄 수**를 셌다(코드의 출력 오독).
   규칙을 맞춰 다시 세니 **18종 · 4단(211/15/2/1)** 으로 완전히 일치했다.
   비교 전에 ①모집단(무엇을 요소로 세나) ②가시성 기준 ③제외 구역을 먼저 합의할 것.
18. **★★잰 범위를 넘어서 말하지 마라.** — 이 라운드에서 가장 자주 밟은 함정이고,
   아래 네 사고가 전부 같은 뿌리다: **잰 것이 무엇인지 확인하기 전에 결론을 냈다.**
   - **일부를 재고 전체를 말했다.** 상위 단 개수(15/2/1)만 보고 「하단도 평평하다」고 단정 —
     하단을 재 보니 조합 23종으로 기준 페이지(39종)와 거의 같았다.
   - **한 축만 재고 처방했다.** 「index 27px vs inquiry 17px」이라는 크기 한 축으로 20px 을 제안 —
     같은 일을 하는 다른 장치(`.sec-head` 의 선)가 이미 걸려 있었다(`[SEC_TITLE_DEVICE]`).
   - **그림을 재지 않고 읽었다.** A/B 스크린샷 두 장의 **스크롤 위치가 달라** 고정 헤더가
     크롭에 걸린 것을 「글자가 겹친다」로 읽었다. → **A/B 는 같은 스크롤 위치에서 찍는다.**
   - **겹침 검사가 자기 자신을 셌다.** Range 상자를 전수 대조했더니 6건이 나왔는데 전부
     부모×자식 쌍이었다(「Required · 필수」 안의 「필수」). 전후가 똑같이 6건이라 들켰다.
     → **겹침을 잴 때 조상-자손 쌍을 뺀다.** 전후 값이 같으면 검사를 먼저 의심할 것.
   - **순회를 «라벨 문자열»로 셌다.** Tab 순회에서 같은 요소인지를 이름으로 판정하니
     `priority` 체크박스 8개가 같은 `name` 이라 두 번째에서 «한 바퀴 돌았다»가 됐다
     (23스텝에서 멈춤 · 실제는 60스텝). **요소 자체(uid)로 센다.** 양쪽이 같은 함정에 걸렸다.
   - **비교 대상의 «종류»가 달랐다.** 간격을 잴 때 다음 형제가 «내용 블록»인지
     «힌트 문단」인지에 따라 값이 다른데(28px vs 8·14px), 한 줄로 세면 «제각각»으로 보인다.
     → 간격은 **같은 종류끼리** 비교한다. 다르면 그건 드리프트가 아니라 두 규칙이다.
   - **부모가 다른 요소를 형제처럼 쟀다.** field-group 사이 572px 은 «두 질문 사이»가 아니라
     **섹션 경계를 넘은 거리**였다. 형제 순회는 부모 안에서만 돈다는 것을 잊으면 이렇게 된다.

### 6-3. 코드가 같은 조건으로 다시 잼 — **판정: 일치(기준을 맞추면)**
`index.html` 이 `4b49b977` 과 **바이트 동일**함을 확인한 뒤, 320px · scrollY 8000 ·

**차이의 원인은 «기준선»이었다.**

```
레일 268 ~ 314 (46px 버튼)
  버튼 상자 좌 = 268        ← 누르는 영역
  아이콘 획 좌 = 280.5      ← 눈에 보이는 획 (버튼 안쪽으로 12.5px)
```

코워크 목록은 두 기준을 **한 목록에 섞어** 적었다(268 과 281 이 함께 있다).
기준을 맞추면 값이 붙는다:

| 문장 | 코워크 | 코드(획 기준) | 코드(상자 기준) |
|---|---|---|---|

## 6-10. 왜 단조가 아닌가 — 코워크 요청으로 확인함

## 10. 라운드 밖에서 나온 진짜 결함 2건 (2026-09-06 · 실기기 제보)

**두 건 다 라운드 1 의 7개 항목에 없었고, 화면을 보는 검사는 전부 초록이었다.**

### 10-1. CSS 주석 중첩 → `.journal-listen` 규칙 통째로 소실 (PR #670 · main `83cb3c93`)

주석 안에서 주석을 한 번 더 열었다. CSS 주석은 중첩되지 않아, **첫** 닫는 표시가 바깥까지
닫고 그 뒤 설명문 4줄이 CSS 로 읽혔다. 파서는 회복하려고 다음 `{ }` 블록 하나를 삼켰다.

CSSOM 실측이 그대로 보여준다 — `.journal-card-meta .journal-dot`(307) 다음이 곧바로
`.journal-listen::before`(308). **베이스 규칙 하나만** 없었다.
`:hover`·`svg`·`[data-state]` 파생 11개는 멀쩡히 남아 더 안 보였다.

결과: 저널 재생 버튼이 26px 골드 원이 아니라 **브라우저 기본 네모 버튼**

**왜 아무 검사도 못 잡았나** — 링크·접근성·탭타깃·문구·렌더 검사 전부 통과했다.
규칙 «하나»만 조용히 없어져 페이지가 대체로 멀쩡했고, 전체 스크린샷으로 26px 차이는 안 보인다.
→ 새 검사 `scripts/audit/css-comment-nest.mjs`. 화면이 아니라 **파서가 무엇을 버렸나**를 본다.
   반증 확인(일부러 중첩시킨 파일에 종료 코드 1) · 저장소 86파일 중 이 1건뿐이었다.

### 10-2. 고정 레일이 26px 버튼의 27% 를 덮어 탭이 레일로 감 (PR #671 · main `24810777`)

390px 에서 재생 버튼(오른쪽 끝 정렬)의 오른쪽 **7px** 이 `.me-fab-stack` 아래였다.

홈 전체 컨트롤을 훑어 레일에 덮이는 33개를 «덮인 비율»로 줄 세운 결과:

### 10-2b. ★이 왕복이 값을 한 지점 — 헛발을 걸렀지, 발견을 늘린 게 아니다

라운드 1~2 사전점검에서 양쪽이 올린 발견은 15건 안팎, **살아남아 코드에 들어간 것은 5건**이다.

| | 폐기된 발견 |
|---|---|
| 코워크 | 히어로 대비 `1.09:1` · 빈 화면 연속 · 「링크 이름 없음」 · `min-height` 가 막는다 · 「하단이 평평하다」 · 모서리 8종 · 로고 둘 |

왕복의 값은 «발견을 늘리는 것»이 아니라 «헛발을 전부 거르는 것»에 있다.
이 비용(패치 왕복·재측정)을 치르는 이유가 이것이다.

### ★비율이 안 내려간다 — 그게 왕복을 계속 도는 근거다 (2026-09-06 코워크 제안)
| | 올린 것 | 산 것 |
|---|---|---|
| 라운드 1 | 7 | 3 |
| 라운드 2 | 6 | 3 |
라운드를 거듭해도 오탐 비율이 절반 근처에서 안 내려간다. **숙련으로 줄어드는 종류가 아니다** —
매번 새 화면·새 축을 보기 때문이다. 그러니 «오탐을 줄이자»가 아니라
**«오탐이 코드에 닿기 전에 걸리는 구조를 유지하자»**가 목표다.

### ★틀린 값이라도 «옳은 질문»이면 값이 있다 (2026-09-06 코워크 제안)
라운드 2 3번에서 코워크의 「Tab 이 23개에서 끝난다」는 **틀린 숫자**였다(실제 60).
그런데 그 질문이 진짜 결함 둘을 끌어냈다 — 닫힌 상담 패널 3스텝 · index 만 포커스가 패널 밖.
→ **값을 못 믿겠으면 «값»이 아니라 «질문»으로 넘긴다.**
   「23개다」가 아니라 「23개로 나오는데 끊긴 건지 표준인지 봐 달라」로 넘긴 것이 맞았다.

### 10-3. 라운드 설계에 넣을 것 — 이 두 건이 말해 주는 것

1. **«보이는가»와 «작동하는가»는 다른 축이다.** 라운드 1 은 색·크기·간격만 봤다.
   덮여서 안 눌리는 컨트롤은 그 축에 없다. → 라운드마다 **탭 라우팅**을 따로 본다.
2. **«화면이 멀쩡함»은 «CSS 가 온전함»을 뜻하지 않는다.** 규칙 하나가 사라져도 페이지는 돈다.
   → 파서 단계를 따로 본다.
3. **작은 컨트롤은 큰 것과 같은 기준으로 재면 안 된다.** 350px 가 32px 덮이는 것과
   26px 가 7px 덮이는 것은 같은 «32px vs 7px» 이 아니라 **9% vs 27%** 다.
4. **실기기 제보는 헤드리스가 못 여는 창이다.** §5-4 를 넓힌다 — 톤뿐 아니라
   «실제로 눌리는가»도 실기기가 먼저 안다.

## 12. `inquiry.html` 간격 — 판정 (2026-09-06 · 390px · main `cb1ae818`)

코워크가 「다르다」까지 올린 세 건. 전부 재서 **셋 다 «측정 대상이 달랐던 것»**으로 판정한다.

### 12-1. 규칙이 있는가부터
`[SECTION_RHYTHM_TIER2]` 는 **`index.html` 의 `.divider` 전용**이다 — 폼 내부는 정하지 않는다.
다만 같은 문서 맨 위에 일반 규칙이 하나 있다:
> 인접한 요소 간 간격보다 **섹션 사이 간격이 최소 3배**여야 구분이 읽힌다

이건 적용된다. 아래 12-4 가 그 판정이다.

### 12-2. 「field-group 사이 572px」 → 측정 범위 문제
572px 은 두 질문 사이가 아니라 **섹션 경계를 넘은 거리**다.
형제 순회가 부모 안에서만 돌아 「사이에 아무것도 없다」로 보였을 뿐이다.
같은 부모 안의 실제 값은 **28px ×7 로 일정**하다. 드리프트 없음.

### 12-3. 「섹션 머리 → 첫 요소 8px ×2」·「라벨 → 내용 8px ×1」 → 다음 요소의 «종류»가 다르다
| 다음에 오는 것 | 간격 |
|---|---|
| 내용 블록(`div.field-group`·`compact-group`·`story-wrap` …) | **28px** ×4 / **16px** ×6 |
| 힌트 문단(`p.field-group-hint`) | **8px** ×2 / **14px** ×3 |

`.field-group-hint` 에 `margin: -8px 0 20px` 가 걸려 있다 — 힌트를 제목 밑에 **붙이려고**
일부러 당긴 값이다. 8px 은 그 결과이지 드리프트가 아니다.
「연락처」·「예약 조회용 비밀번호」·「희망 예식 시간대」 셋이 8px 인 것도 전부 다음이 힌트라서다.
→ **간격은 같은 종류끼리 비교해야 한다**(§5-18에 추가).

★남는 것 하나 — 라벨→힌트가 **8px 과 14px 로 갈린다**(6px 차이).
  코워크가 스스로 세운 「2px 은 안 보인다」 기준보다는 크지만, 둘 다 «붙이려는» 의도의 값이고
  화면에서 구분이 안 된다. **고칠 값 없음**으로 둔다.

### 12-4. 3배 규칙 — 실제로는 «2배»다. 이건 사용자 판단으로 올린다.
| | 값 |
|---|---|
| 인접 질문 사이 | **28px** |
| 섹션 경계 | **56px** ×3 · **84px** ×1 |

56 / 28 = **2.0배**로, 문서가 말하는 3배에 못 미친다.
다만 이 경계에는 여백 말고 **`.sec-head` 의 `border-bottom` 1px 과 `Nº` 번호 제목**이 함께 있다.
3배 규칙의 전제는 «여백만으로 가를 때»라, 선과 제목이 있는 자리에 그대로 대면 과대 판정이 된다
(`[SEC_TITLE_DEVICE]` 와 같은 논리).
→ **위반으로 세지 않는다.** 다만 경계 하나만 84px 인 것은 일관성 문제라 함께 올린다.
   56 → 84 로 맞추면 3배가 되고 문서가 약 112px 길어진다. 사용자 판단 자리다.

### 12-5. 대비 — 미달 1건. 코워크 값 그대로 확인.
`summary::before` `"+"` 14px · `#b89a75` on `#f5f3ef` → **2.395:1** (기준 3:1 · 비텍스트 마커)
`index` 의 `.faq-q::after` · `a.access-link::after` 와 **같은 뿌리**다 — `--gold` 를 기능 마커에 쓴 것.
→ `--gold-text` 교체 대상이 **2곳에서 3곳**으로 늘었다. 한 곳을 놓친 게 아니라 한 종류를 놓쳤다.

## 14. 라운드 3 — 하객 사진 올리기 · 부모님 안내 (2026-09-08)

### 14-1. 하네스가 두 번 틀렸다 — 둘 다 «측정»이지 제품이 아니다

**① 표본 화면(`?g=demo`)으로는 못 잰다.** `guide.html` 에 그대로 있다:
```js
if(!DEMO) bindGuestUpload();
```
표본은 업로더를 **일부러 배선하지 않는다**(버튼은 있고 눌러도 아무 일이 없다).
모르고 재서 「요청 0건 · 위반 11건」이 나왔다. 하마터면 없는 결함 11개를 넘길 뻔했다.
→ 진짜 토큰 경로(`?g=t_sim`)로 열고 `guideView` 응답을 심어야 `DEMO=false` 가 된다.

**② 시트를 `.sheet` 로 찾았다.** 실제 이름은 `#dtipOv` 이고 `.k`/`.h`/`.d` 로 나뉜다.
그 탓에 「성공 시트가 안 떴다」와 「잘린 5장을 말하지 않는다」 **두** 결론이 뒤집혔다.
후자는 초과 안내가 **시트 부제**로 가기 때문이다 — 선택자 하나가 두 판정을 바꿨다.

> §5-18 **검사 대상이 그 상태에서 «작동하도록 배선돼 있는가»부터 확인한다.**
> demo·미리보기 화면은 배선을 일부러 끊어 두는 경우가 있다.
> 그리고 **선택자는 코드에서 확인한다** — 짐작한 이름으로 «없다»가 나오면 그건 발견이 아니다.

### 14-2. 초과분이 실패분보다 불리했다 — 코워크가 옳았다

여섯 시나리오는 전부 통과했다. 그런데 코워크가 「6/6 통과에는 동의하지만 고칠 것 없다에는 반대」라며
**같은 사고의 다른 얼굴**을 짚었다. 값으로 확인하니 그대로였다:

| | 실패한 사진 | 넘친 사진(30장 초과) |
|---|---|---|
| 다시 보내는 길 | 「다시 시도」 버튼 — 그 파일들을 그대로 재전송 | **없음** · `inp.value=''` 로 선택이 비워짐 |
| 다시 골라야 하나 | 아니오 | **예** — 35장 중 어느 5장인지 기억해서 |
| 안내가 붙는 자리 | 인라인 11.5px (누를 것과 함께) | 시트 **부제 12px** · 성공 본문 **15px** 뒤 |

잘못한 것도 없는데 초과가 더 불리했다. `[GP_OVER_PICK]`(2026-08-22)이 「조용한 절삭」을
말로는 막았지만 **말까지만** 막은 것이다. 셋을 함께 고쳤다 — `GP_OVER_KEEP`(파일을 쥐고
「남은 N장 보내기」) · `GP_OVER_AHEAD`(올리는 동안부터 말한다) · `GP_OVER_WEIGHT`(넘쳤으면
성공 시트를 안 띄운다).

> **말로 알리는 것과 되돌릴 길을 주는 것은 다른 일이다.**
> 「몇 장이 안 갔다」를 화면이 말하면 검사는 통과한다. 그런데 사람이 할 수 있는 게
> «처음부터 다시»뿐이면, 알린 것이 위로밖에 안 된다. 실패 경로에 이미 있던 대접을
> 초과 경로에 안 준 것이 원인이었다 — **같은 성격의 사건은 같은 대접을 받아야 한다.**

### 14-3. 「조합」이 새 결함을 꺼냈다 — 코워크의 요청이 맞았다

코워크: *"각각은 멀쩡한데 겹칠 때 깨지는 경우가 있다. 「아주 크게 + 재생 중」이 최악 조합이다."*
실제로 그 자리에서만 나왔다.

`[LEAD_IN_NO_JUMP]` — 리드인 2초 동안 볼륨 안내를 `display:none` 으로 감춰서,
막대가 그 2초만 작았다가 소리가 시작되며 커졌다. **320px 에서 69 → 97px.**
그런데 `[HINT_NO_POP]`(2026-08-18)이 **바로 그 움직임**을 「배려로 만든 것이 고장으로 읽힌다」며
없앤 기록이 같은 파일에 있다. 2026-08-30 `[LEAD_IN_SAY]` 가 **같은 자리·다른 원인**으로 되살렸다.
→ `visibility:hidden` 으로 바꿔 둘 다 지킨다(감추되 자리는 남긴다).

> §5-19 **되살아난 결함은 «같은 코드»로 돌아오지 않는다.** 지운 줄이 그대로 복구되는 역전은
> merge-guard 가 잡는다. 잡히지 않는 것은 **다른 이유로 같은 증상**을 만드는 새 코드다.
> 마커는 그 자리에 남아 있었고 초록이었다 — 마커가 지킨 것은 «문장»이지 «움직임»이 아니었다.
> 그래서 이번엔 마커를 «높이가 같은가»에 걸었다(리드인 vs 재생 중 실측 비교).

### 14-4. 내 대리 지표가 8건의 가짜 위반을 만들었다

`body.listening{padding-bottom:70px}` vs 실제 막대 높이(320px 97px · 390px 73px)를 비교해
「막대가 아래여백보다 크다」를 위반으로 셌다 — **8건**. 그런데 **같은 판에서** 실좌표 겹침 검사가
「가림 0곳」을 냈다. 지표 둘이 어긋났다.

실좌표가 옳았다. 마지막 글(사업자정보) 아래에 다른 여백이 이미 있어, 70px 이 27px 모자라도
글은 안 가렸다. 다만 남는 틈이 **8px** 뿐이었다 — 우연히 덮이고 있었을 뿐이다.
→ 위반에서 빼고(`[BAR_SLACK]`), 대신 `--bar-h` 로 막대를 재서 넣었다(틈 8 → 36px).

> §8 에 추가 — **대리 지표(proxy)로 결함을 선언하지 않는다.** 「A 가 B 보다 크다」는
> 「사용자가 손해를 본다」와 다른 말이다. 손해를 직접 재는 검사가 같은 판에 있으면 그쪽이 이긴다.
> 그리고 이번처럼 **어긋남 자체가 값이다** — 대리 지표가 틀렸다는 것은 그 숫자가 어림수라는 뜻이고,
> 어림수는 지금 안 아파도 다음 화면 폭에서 아프다.

### 14-5. 코워크 쪽 오탐 하나 (스스로 잡음)

320px 에서 요소가 630px 까지 뻗어 의심했으나 전부 `.me-adv-*`(닫힌 상담 패널 · `visibility:hidden`)
였다. 라운드 2 에서 탭 순서를 고치며 넣은 그 `visibility` 다.
같은 판의 `scrollWidth`(가로넘침 없음)와 어긋나 스스로 걸렸다 — §5 가 실제로 작동한 사례다.

> §5-20 **제외 목록은 검사마다 다시 건다.** 한 스크립트에서 「화면 밖 오버레이 제외」를
> 걸었다고 다음 스크립트가 물려받지 않는다.

### 14-7. 코워크가 §14 에 덧댄 둘 (2026-09-08 · 받는다)

**① 마커는 «문장»이 아니라 «현상»에 건다.**
`[HINT_NO_POP]` 이 없앤 것은 「막대가 튀는 현상」인데, 마커는 그때 지운 **문장**에 걸려 있었다.
그래서 8월 30일에 다른 원인으로 같은 현상이 돌아왔을 때 게이트는 초록이었다.

> §5-22 **제거 지시를 마커로 지킬 때, 지킬 대상이 «문장»인지 «현상»인지 먼저 정한다.**
> 현상을 없앤 결정은 현상으로 지켜야 한다. 문장에 걸면 다른 경로로 돌아온다.
> 이번 교정: 마커를 「리드인 높이 == 재생 중 높이」라는 **비교**에 걸었다.

**② 대리 지표를 «지우지» 마라.** §14-4 는 「손해를 직접 재는 검사가 이긴다」로 끝났는데,
그러면 대리 지표를 없애는 쪽으로 읽힌다. 그게 아니다 —
남는 틈이 **8px** 뿐이라는 것을 알려준 게 그 대리 지표다.
실좌표 검사는 「지금 안 아프다」만 말하고 「얼마나 아슬아슬한지」는 말하지 않는다.

> §8 보강 **둘을 같이 둔다. 어긋나면 실좌표를 따르되, 어긋남 자체를 기록한다.**
> 판정은 실좌표가 하고, 대리 지표는 «여유»를 숫자로 남긴다(16px 미만이면 경고 · 위반 아님).

### 14-8. 「글자가 커지면 여백 계산이 달라지지 않나」 — 안 달라진다 (실측)

코워크가 21.5px 단계에서 여유가 줄어들 것으로 봤다. 재 보니 **거의 그대로**다:

| 폭 | 단계 | `--letter-size` | 막대 = `--bar-h` = 아래여백 | 마지막 글 높이 | **여유** | 문서 높이 |
|---|---|---|---|---|---|---|
| 320 | 보통 | 17.5px | 97px | 41px | 35px | 4503px |
| 320 | **아주 크게** | 21.5px | 97px | 41px | **36px** | 5944px |
| 390 | 보통 | 17.5px | 73px | 20px | 35px | 3893px |
| 390 | **아주 크게** | 21.5px | 73px | 20px | **36px** | 5123px |

**이유가 요점이다 — 마지막 블록이 `--letter-size` 축 «밖»에 있다.**
문서 맨 끝은 편지가 아니라 푸터(상호·대표·사업자등록번호)이고, 그건 단계와 무관한 고정 크기다.
그래서 단계는 **문서 길이만** 바꾸고(4503 → 5944 · +32%) 꼬리 기하는 안 바꾼다.
고치기 전 8px 이었을 때도 네 단계 전부 8/7/8/8 로 같았다 — 같은 이유였다.

> §5-23 **「A 를 키우면 B 도 커지겠지」는 확인 전까지 추측이다.**
> 어떤 축이 그 요소에 실제로 닿는지부터 본다 — 여기서는 편지만 `var(--letter-size)` 를 받는다.

### 14-9. 라운드 3 닫힘 (2026-09-09) — 코워크가 덧댄 셋

**① 못 쟀으면 «0» 이 아니라 «못 쟀다»로 넘긴다.**
코워크는 조합(아주 크게 + 재생 중)을 클래스만 손으로 붙여 재려다 막대 높이가 0px 로 나오는 것을 보고,
「가리는 글자 0건」이라는 **결과를 넘기지 않고** 「이쪽이 못 쟀다」로 넘겼다.
높이 0 짜리가 아무것도 안 가리는 건 당연한 일이라, 그 0 을 결과로 받았으면 그걸 근거로 삼았을 것이다.

> §10-4 **못 쟀으면 «0» 이 아니라 «못 쟀다»로 넘긴다.**
> 0 은 결과고, 못 쟀다는 상태다. 둘을 같은 칸에 적으면 상태가 결과로 읽힌다.
> (merge-guard 의 종료코드 2 「안 쟀다」가 같은 생각이다 — 사람이 넘기는 말에도 그 칸이 있어야 한다.)

**② 검사가 붉을 때 갈래는 둘이 아니라 셋이다.**
`[KST_WEEKDAY]` 가 실제로 드러낸 것은 버그가 아니라 **사업 제약**이었다 —
주말 상담 슬롯이 `18:20` 하나뿐이라는 사실. 코드 문제가 아니고 고칠 것도 아니다.

> §5-24 **검사가 붉을 때 「제품이 틀렸나 · 검사가 틀렸나」 둘만 보지 마라. 세 번째가 있다 —
> 사업 규칙이 검사의 가정과 다른 경우다.** 이때 고칠 것은 검사고, 남길 것은 그 규칙이다.

**③ 시간에 기대는 검사는 «언제 돌려도»를 반증한다.**

> §5-25 「지금 통과」가 아니라 **「언제 돌려도 통과」**를 반증한다.
> 한 축(과거가 됨)만 막고 다른 축(요일·월말·공휴일)을 안 막으면 같은 사고가 다른 얼굴로 돌아온다.
> 실제로 `[KST_AHEAD]`(2026-09-05)가 첫 축을 막은 지 나흘 만에 둘째 축으로 돌아왔다.

### 14-10. 라운드 3 결산 — 진짜 발견 둘이 나온 «자리»

코드에 들어간 것: 지도 3개 44px · 성함 44px · 초과분 셋(`GP_OVER_KEEP`/`AHEAD`/`WEIGHT`) ·
리드인 튐(`LEAD_IN_NO_JUMP`) · 막대 높이 실측(`BAR_HEIGHT_REAL`) · 달력 게이트(`KST_WEEKDAY`).

**진짜 발견 둘은 「각각은 멀쩡한데」 자리에서 나왔다.** 그게 이 라운드가 알려준 것이다.

| 발견 | 어떤 축으로 봤을 때 나왔나 |
|---|---|
| 초과분이 실패분보다 불리하다 | **비슷한 것 둘을 나란히** — 실패 경로와 초과 경로를 한 표에 놓으니 대접이 다른 게 보였다 |
| 리드인에 막대가 튄다 | **시간축** — 「겹칠 때」가 아니라 「2초 동안만 다른 화면」이었다 |

> §5-26 **라운드를 열 때 이 두 축을 처음부터 넣는다** (2026-09-09 코워크 제안).
> ① **비슷한 것 둘을 나란히 놓기** — 같은 성격의 사건 둘(실패/초과 · 성공/부분성공)을
>    한 표에 놓고 «대접이 같은가»를 본다. 하나만 보면 각각 멀쩡해 보인다.
> ② **시간축** — 화면을 한 장이 아니라 «구간»으로 본다. 누른 직후 · 기다리는 동안 · 끝난 뒤.
>    한 장만 찍으면 리드인 2초처럼 «잠깐만 다른» 상태를 영영 못 본다.

**누계** — 양쪽이 올린 것 중 절반가량이 여전히 측정 오류다(§10-2b). **그리고 하나도 코드에 안 닿았다.**

### 14-11. §5-24 각주 — 규칙을 만든 다음 날 그 규칙에 걸렸다 (2026-09-09)

§5-24(검사가 붉을 때 갈래는 셋)를 쓴 다음 날, `typo-ramp.mjs` 첫 판이 정확히 그 세 번째 갈래로 걸렸다.

「모든 px 를 세니 램프 밖 **14종**」 → 전부 제목(26~52px)·아이브로우(8~9px)였다.
램프의 범위가 **11~20px** 이라는 것은 merge-guard 에 **이미 적혀 있었다**
(「본문·라벨 7단계(11~20) · 반px 금지 · 목업 구역 예외」).
제품도 검사도 안 틀렸고, **검사의 가정이 규칙과 달랐다.**

> 규칙을 만든 다음 날 그 규칙에 걸린다는 건, 그 규칙이 **흔한 실수**를 짚었다는 뜻이다.
> 새 검사를 짤 때 첫 질문은 「무엇을 셀까」가 아니라 **「그 규칙의 범위가 어디까지인가」**다.

### 14-12. 검사는 «선언»과 «렌더» 두 칸으로 나눈다 (코워크 제안 · 반영)

`clamp(13px, 1.6vw, 15px)` 의 상한 15px 은 **선언**으로는 램프 밖이지만,
폰(~923px)에서는 하한 13px 이 걸려 **렌더**로는 램프 안이다. 1000px 이상에서만 15px 이 나온다.
같은 표에 섞으면 「고객이 실제로 보는 위반」과 「선언상의 위반」이 뒤섞여 우선순위가 흐려진다.

| 칸 | 강점 | 한계 |
|---|---|---|
| 선언 (텍스트) | 지금 그 폭에서 안 걸리는 값도 잡는다 | em·rem·%·var 를 못 푼다 · 죽은 CSS 를 센다 |
| **렌더** (브라우저 3폭) | 전부 풀린다(못 쟀다 0) · 죽은 CSS 자동 제외 · 목업을 **DOM 조상으로** 거른다 | 그 폭에서 안 걸리는 값은 못 본다 |

> §5-27 **«선언»과 «렌더»는 다른 사건이다. 한 검사 안에서도 칸을 나눠 센다.**
> 둘을 섞으면 「위반 N건」이 무엇을 뜻하는지가 흐려진다.

**렌더 칸을 만들며 또 틀렸다** — `[RAMP_NO_OPACITY]`.
`opacity < 0.05` 를 「안 보이는 것」으로 걸렀는데, 1280px 첫 화면에서 `.hero-tease-main` 이
스크롤 등장 연출 때문에 `opacity:0` 이었다. 그 탓에 15px 위반이 **「0건」**으로 나왔다.

> §5-28 **크기를 세는 검사에서 「지금 투명한가」는 상관이 없다.** 글자는 투명해도 그 크기다.
> 필터는 «그 검사가 묻는 것»에만 걸어야 한다 — 관성으로 가져온 필터가 답을 뒤집는다.
> (같은 사고를 라운드 2 `home-a11y` 에서도 냈다 — 전환 중인 레일을 읽어 겹침이 사라졌다.)

### 14-13. 죽은 CSS — index.html 클래스 401종 중 80종이 아무 데서도 안 쓰인다

`.mfs` 하나를 확인하려다 저장소 전체(html·js·gs·mjs, 프리뷰 폴더 제외)를 훑었다.

| 계열 | 종수 | 왜 죽었나 |
|---|---|---|
| `mock-*` (`mock-env-*`·`mock-form-*`·`mock-credit-*`·`mock-sec-*` 포함) | 약 50 | **목업이 인라인에서 `<iframe id="gaFrame">` 으로 바뀌었다.** index 의 CSS 는 iframe 문서 안에 못 닿는다 |
| `channel-block-*` · `f-contact-*` · `reveal--*` 등 | 나머지 | 개별 |

동적 조립(`'mock-env-'+key` 같은 것)이 있는지도 따로 찾았다 — **0곳**이다.

★**안 지웠다.** 물어본 것은 `.mfs` 한 줄이었는데 실제로는 계열 전체이고, 지우는 변경이라 사용자 결정이 필요하다.
★그리고 이 조사는 **한 파일이 아니라 저장소 전체**를 봐야 성립한다 —
  `[RAMP_NO_DEAD]` 에서 한 파일만 보고 `.me-adv-*` 를 「죽었다」고 셌던 오탐이 그 증거다.

### 14-14. 가드는 지킬 대상을 «좁게» 잡는다 (2026-09-09 · §5-22 와 짝)

`nochk '양가 가족만 모시는'` 으로 옛 문장을 막았더니 **내 근거 주석**이 걸렸다.
바꾼 이유를 코드 옆에 적으려면 옛 문장을 인용해야 하는데, 그 인용이 곧 위반이 된다.

> §5-30 **문장에 걸면 그 문장을 «설명»할 수 없다 — 인용이 위반이 된다.**
> 그리고 버려지는 건 항상 주석이다. 가드는 빨강으로 강제하고 주석은 안 그러니까.

**§5-22 와 한 뿌리다.** 둘을 묶는 문장:

> **가드는 지킬 대상을 좁게 잡는다. 넓게 잡으면 «현상»을 놓치거나 «근거»를 지운다.**
>
> | | 넓게 잡으면 | 좁게 잡으면 |
> |---|---|---|
> | §5-22 | 문장에 걸어 «현상»을 놓친다(`HINT_NO_POP` 이 다른 원인으로 되살아났다) | 현상에 건다 — 「리드인 높이 == 재생 중 높이」 |
> | §5-30 | 파일 전체에 걸어 «근거»를 지운다(주석의 인용이 위반) | 살아 있는 자리를 **마크업째** 지정한다 |

**해법은 규칙이 아니라 문법이다** — 다음 사람이 헤매지 않게 형태로 적어 둔다:

```sh
nochk '양가 가족만 모시는' index.html              # ✗ 주석의 인용까지 잡는다
nochk 'hero-tease-sub">양가 가족만' index.html     # ○ 살아 있는 마크업만 잡는다
```

즉 **속성값·태그·선택자를 앞에 붙여 «그 자리»를 지정한다.** 문자열만 쓰면 파일 전체가 대상이 된다.

### 14-15. 한계를 정하는 규칙이 둘이면 «뒤바뀌는 폭»을 재라 (2026-09-09 · §5-29 보강)

히어로 부제의 «쓸 수 있는 폭»은 두 규칙이 정한다 —
부모 `.hero-tease` 의 `100vw − padding 56px`, 그리고 자신의 `max-width: 600px`.
코워크가 1280px 한계를 **1224px** 로 냈다(부모만 본 값). 실제는 **600px** 이다.

**실측한 전환점 (viewport 폭 기준)**

| 폭 | 부모 여유 | max-width | 실한계 | 이긴 쪽 |
|---|---|---|---|---|
| 430 | 374 | 600 | **374** | 부모 padding |
| 640 | 584 | 600 | **584** | 부모 padding |
| 655 | 599 | 600 | **599** | 부모 padding |
| **656** | **600** | **600** | **600** | 동률 |
| **657** | 601 | 600 | **600** | **max-width** |
| 1280 | 1224 | 600 | **600** | max-width |

**이 오류가 안 드러난 구조가 요점이다.** 좁은 화면에서는 부모가 이기니 두 계산이 «같은 답»을 낸다.
문구 검증을 320·360·390·430 넷으로만 했다면 오류가 영영 안 나온다.
1280 을 넣었기에 954 대 355 로 갈렸다.

> §5-29 보강 **한계를 정하는 규칙이 둘 이상이면(부모 padding · 자신의 max-width),
> «둘이 뒤바뀌는 폭»을 반드시 측정 폭에 넣는다.**
> 한쪽만 이기는 구간에서만 재면 다른 규칙이 있다는 사실 자체가 안 보인다.
> ★이건 §5-25(언제 돌려도 통과)의 **폭축 버전**이다 — `KST_AHEAD` 가 한 축(과거)만 막고
> 다른 축(요일)으로 돌아온 것과 같은 모양이다. 시간축이냐 폭축이냐만 다르다.

**공식 — 두 번째 갈래를 빠뜨리지 말 것(코워크 지적)**

```js
const c = getComputedStyle(container);
const avail = container.clientWidth - parseFloat(c.paddingLeft) - parseFloat(c.paddingRight);
const mw = getComputedStyle(line).maxWidth;              // 'none' · '600px' · '60ch' · '80%'
const cap = /px$/.test(mw) ? parseFloat(mw) : null;      // ★px 이 아니면 숫자로 못 읽는다
//   parseFloat('60ch') === 60 이다 — 60px 로 읽혀 «있지도 않은 좁은 한계»를 만든다.
//   px 이 아니면 그 요소를 아주 긴 글로 채워 실제 폭을 재거나, 이 갈래를 «못 쟀다»로 넘긴다(§10-4).
const limit = Math.min(avail, cap === null ? Infinity : cap);
```

### 14-16. 라운드 3 성적 — 같은 것을 «따로» 재서 갈린 것이 네 번

| 무엇 | 누가 틀렸나 | 누가 잡았나 |
|---|---|---|
| 레일 획좌표(전환 중 읽음) | 클로드코드 | 실기기 제보 |
| Tab 순회 「23에서 끝난다」 | 코워크 | 클로드코드 |
| 1280px `opacity:0` → 「램프 밖 0건」 | 클로드코드 | 코워크의 사전 측정 |
| 1280px `max-width` 누락 → 여유 954 | 코워크 | 클로드코드 |

**두 번은 이쪽이, 두 번은 그쪽이 틀렸고, 네 번 다 다른 쪽이 잡았다.**

> §10-5 **한쪽만 재면 그 값이 정본이 된다.** 틀린 값에 이의를 제기할 자리가 없기 때문이다.
> 두 번 재는 비용은 «같은 일을 두 번 하는 것»이 아니라 «정본을 만들지 않는 것»에 대한 값이다.
