## 0. 한 줄 요약

정보통신업(SW·앱) 트랙에서 제시할 실체는 **웨딩 스튜디오 운영 전 과정(상담 예약 → 계약 → 결제 → 제작 → 결과물 전달 → 하객 안내)을 하나의 웹 플랫폼으로 자체 개발한 것**이다. 프론트엔드·백엔드·AI·결제 설계·자동화·테스트·문서까지 1인이 기획·개발·운영한다. 총 코드량은 **약 8만 6천 줄(정확히는 86,800줄 · 이미지·외부 벤더 라이브러리 제외, 실측)**이다. 라벨을 통일하면: **핵심 서버 로직(백엔드+서버리스) 약 1만 6천 줄**, 여기에 관리자 UI·공용 JS·테스트를 더한 **애플리케이션 로직 총 약 2만 4천 줄**, 나머지 약 6만 3천 줄은 고객 화면·청첩장 템플릿 HTML(반복 마크업 포함)이다.

### 1-2. 언어·프레임워크 비중

- **프론트엔드: 프레임워크 0 · 빌드 스텝 0.** 저장소 전체에 `package.json`·`node_modules` 없음(실측). React·Vue·Next·jQuery 등 서명 0건. 순수 바닐라 JS + 정적 HTML + CSS.
- **백엔드: 2계층.** ① Google Apps Script(`.gs`, clasp 배포) ② Vercel 서버리스 함수(`api/*.js`, CommonJS, Node 런타임 · 외부 의존성 0 · 내장 `fetch`만 사용).
- **외부 라이브러리 비중: 극소.** 프론트 벤더는 `shared/qrcode.min.js`(QR 생성) 1종과 Google Fonts CDN뿐. 서버리스는 npm 의존성 0. 즉 **직접 작성 코드 비중이 사실상 전부**이며, 이는 "라이브러리 조립"이 아니라 "직접 구현"임을 뒷받침한다.

### 2-2. 예약 시스템 (고객 여정)

**상품별 진행 단계(현재단계):** 정의 위치 `automation/platform/00_platform-config.gs`.

- **시그니처(예식) 9단계**: 신청접수 → 상담확정 → 시착 → 상담완료 → 계약완료 → 입금완료 → 제작중 → 예식완료 → 결과물전달
- **웨딩스냅 6단계**: 신청접수 → 촬영확정 → 계약완료 → 입금완료 → 촬영완료 → 결과물전달
- **공통 예외**: 미계약 · 취소 · 노쇼

**상태 필드(값 열거, 실측):**

| 필드 | 값 |
|---|---|
| 계약상태 | 미발송 → 발송 → 서명완료 |
| 입금상태(계약금) | 대기 → 완료신호(고객) → 확인(관리자) |
| 제작상태 | 잠금 → 작성중 → 완료 |
| 결과물상태 | 대기 → 원본전달 → 선택완료 → 보정중 → 컨펌대기 → 컨펌완료 → 전달완료 |
| 시착동의상태 | 대기 → 동의요청 → 동의완료 |
| 중도금상태 / 잔금상태 | 대기 → 완료신호 → 확인 |

**데이터 모델:** `Customers` 시트 **58컬럼**(순서 고정·신규 컬럼 append). 저장소는 **Google Sheets 단일**(별도 DB 없음 · redis/postgres/mongo/firebase 등 0건 실측).

**자동화된 단계:**
- 가입 시: 허니팟·필수검증 → 비번 해시(원문 폐기) → **개인코드 자동 발급** → Customers 행 생성 → **로그인 토큰 자동 발급** → 상담예약 행 동시 생성 → **접수 메일 자동 발송**(자동로그인 링크 포함) → 관리자 알림. 2분 중복제출 dedup.
- 메일 링크 클릭 → 토큰 자동 로그인.
- 계약 서명 시 캘린더 `[가예약]`→`[예식확정]` 자동 전환, 미서명 계약서 72h 자동 파기, D-day 리마인드 자동 발송.

**수동 개입이 필요한 지점(관리자):** 상담 일정 승인, 시착 동의 게이트 열기, 계약서 발송, 계약총액 입력, 입금 "확인"(통장 대조), 예식·촬영 완료 처리, 결과물 링크 등록. 즉 **상태를 앞으로 미는 승인·확인·발송은 관리자 수동**, 고객은 서명·입금신호·정보입력을 셀프로 수행.

**상담 예약 화면 A/B/C:** ScreenA(신청 폼) · ScreenB(일정 슬롯 선택) · ScreenC(시간 변경 제안).

**캘린더 연동:** Google Calendar 종일 이벤트로 가예약·예식확정 시각화. 더블부킹 방지(시그니처 1일 3슬롯 09:00·12:20·15:40, 각 140분). **점유의 진실은 시트**(캘린더는 시각화 전용, 실패해도 흐름 안 막힘).

### 2-4. 결제 (Toss Payments) — **라이브/미완료 명확 구분**

| 항목 | 상태 |
|---|---|
| 계좌이체 + 관리자 수동 확인 | **라이브(운영 중)** |
| 결제 마일스톤 상태머신(계약금·중도금·잔금) | **라이브** |
| 중도금·잔금 알림톡 리마인드(일일 트리거) | **라이브** |
| 전자계약(요청→발송→서명→기록→Drive 보관) | **라이브** |
| 환불·취소 견적 엔진 + `cancel.html` + 관리자 환불 큐 | **라이브** |
| **Toss 카드결제(프론트+백엔드+금액검증+멱등성)** | **구현 완료·비활성(`PAY_CARD_ENABLED` OFF, 샌드박스 키)** |
| Toss 활성화 전제(통신판매업 신고 → 라이브 계약 → 키 교체 → 플래그 ON) | 미완료(예정) |

- **결제 마일스톤(실측):** 시그니처 = 예약금 100,000원 → 계약금 10%(예약금 공제) → 중도금 40%(예식 D-149) → 잔금 50%(예식 D-9). 웨딩스냅 = 계약금 20% → 잔금 80%.
- **정직성 핵심:** 현재 **실운영 결제는 계좌이체 + 관리자 통장 대조**다. Toss 카드결제는 **코드는 완성됐으나 플래그로 꺼져 있고 키가 샌드박스**다. 카드결제를 "가동 중"이라 쓰면 안 됨. 다만 "**결제 연동을 서버측 금액 재계산·멱등성·LockService까지 갖춰 구현해 두었다**"는 사실은 유효.

### 2-5. 전자계약서

- **생성:** 고객이 예식 정보 입력(`handleRequestContract`) → 관리자 발송(`adminSendContract`, 계약상태 발송·발송일시·링크). 문서 본체는 `/contract/`의 정적 HTML 템플릿(`v1-1.html`·`snap-v1-0.html`·`fitting.html` + `archive/`)을 브라우저에서 고객 데이터로 채워 렌더.
- **서명(하이브리드):** 캔버스 **손서명(base64 PNG)** → 별도 `Signatures` 시트 저장 + 클릭 동의. 계약상태 서명완료 전환.
- **보관·효력:** 서명본 HTML을 Google Drive("모먼트에디트 계약서 서명본" 폴더) 자동 아카이브. **동의기록(JSON 스냅샷)** = 약관버전·표시금액·약관지문(termsHash)·서명시각 등 효력 재현 근거(내부 전용·마이페이지 비노출). 72h 미서명 자동 파기.

### 2-6. 청첩장·하객편지

- **템플릿 수(실측):** 라이브 파라미터 청첩장 **16종**(모바일 커버 `i/cover-01~08` 8종 + 가족형 `i-family/family-01~08` 8종) + 갤러리 데모 8종 = HTML 24개.
- **URL 파라미터 구조:** `?e=<eventId>`. eventId = `신랑이니셜-신부이니셜-MMDD` + **랜덤 6자 접미**(혼동문자 제외) → 패턴 추측으로 타 커플 청첩장 열람 불가. 라이브도 동일 `?e=`. 좌석은 별도 `?t=<토큰>`.
- **작동:** 정적 HTML을 Vercel이 서빙 + 런타임 하이드레이션(`shared/hydrate.js`가 `{{PLACEHOLDER}}`를 시트 데이터로 채움 · 커플별 파일 생성 안 함). 소셜 봇 전용 OG 메타 주입(`api/og-inv.js`, 봇 UA만 라우팅 · 사람 트래픽은 정적 파일 직행).

## 4. B2B SaaS 전환 관점

### 4-1. 재사용 가능한 모듈(멀티테넌트 전환 시)

- **인증/세션**(개인코드·SHA-256 스트레칭·토큰 슬라이딩 연장) → 벤더별 고객 계정에 그대로 이식 가능.
- **고객 여정 상태머신**(단계 정의·전이 가드·"지금 할 일" 매핑) → 어떤 웨딩 벤더든 상담→계약→결제→납품 흐름은 동형.
- **결제 마일스톤 엔진**(계약금·중도금·잔금 비율·기한 파생·리마인드·계좌이체 신호-확인) → 파라미터화하면 재사용.
- **전자계약**(요청→발송→손서명→동의기록 JSON→Drive 보관) → 문서 템플릿만 테넌트별 교체.
- **환불/변경 견적 엔진**(§7/§8/§9 규칙) → 위약금 정책을 테넌트 설정으로.
- **AI 상담 스택**(KB 단일 진실원·핵심정보 버전·회귀셋·비용/안전 대시보드) → 벤더별 KB만 갈아끼우면 됨.
- **알림 게이트웨이**(Solapi 알림톡→SMS 폴백·야간 보류·잔액경고) · **관리자 콘솔**(큐·파이프라인·감사).

### 4-2. 하드코딩된 모먼트에디트 전용 로직(분리 필요)

- 상품 상수(`시그니처`·`웨딩스냅`)와 단계 배열이 코드에 고정 → **테넌트별 상품/단계 정의**로 외부화 필요.
- 결제 비율·슬롯 시각(09:00·12:20·15:40)·140분 등 상수 하드코딩 → 설정화 필요.
- 계약서·청첩장 템플릿, 브랜드 문구, 스프레드시트 ID, 발신 프로필·KB 사실이 단일 테넌트 전제.
- 단일 Google Sheet 저장소 → 멀티테넌트는 **테넌트 격리(시트/DB 분리 또는 스코프 컬럼)** 필요.

### 4-3. 전환에 필요한 추가 개발(개괄 · 공수는 미확인/추정)

- 테넌트 등록·격리·구성(상품/단계/결제/템플릿 설정 UI).
- Sheets 단일 저장소 → 멀티테넌트 데이터 계층(스코프화 또는 DB 이관).
- 온보딩·구독 과금(벤더가 고객), 권한/롤 모델.
- (정직성) 구체 공수 산정은 본 조사 범위 밖 → `미확인`. 다만 **핵심 도메인 로직은 이미 존재**하므로 신규 구축이 아니라 **일반화·격리 작업**이 전환의 본질.

## 6. 정직성 주석 (심사·실사 대비 · 반드시 인지)

1. **git 최초 커밋일 ≠ 실제 착수일.** site 저장소는 7/19 재초기화됨. 실제 착수 근거는 사업자등록(4/1)·docs 저장소(5/18)·회계 기준일(5/19).
2. **AI 코딩 도구 사용.** 대표자는 AI 코딩 어시스턴트를 도구로 사용해 개발한다(커밋 작성자 기록에 반영). 팀·외주·에이전시는 없는 **1인 개발·운영**. 대외 자료는 "1인이 기획·설계·개발·결제연동·운영까지 완주"로 쓰는 것이 정확하며, "한 줄씩 수기 작성"은 주장하지 않는다.
3. **Toss 카드결제는 비활성(구현 완료·플래그 OFF·샌드박스 키).** "가동 중" 표현 금지. 실운영 결제는 계좌이체+수동 확인.
4. **개업 전 상태(개업일 2026-10-26).** 사업자등록은 2026-04-01 완료. 현재는 개업 전 준비·개발 단계.
5. **B2B SaaS 전환은 계획.** 현재 시스템은 단일 테넌트(모먼트에디트 전용). 전환 공수는 미산정(`미확인`).
