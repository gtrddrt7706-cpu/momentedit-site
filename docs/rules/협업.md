## ★📮 코워크 전달 메시지 = 폐지 (2026-08-01 사용자 지시 · 3회 반복)

**응답에 `## 📮 코워크 전달 메시지` 칸을 만들지 않는다. 다른 세션(CC)에게 일을 넘기지도 않는다.**
내가 할 수 있는 일은 전부 내가 직접 끝낸다. "이건 CC 몫", "CC가 리뷰해 줬으면" 같은 문장을 쓰지 않는다.

### 왜 폐지했나
2026-07-30에 만든 규칙이지만, 사용자가 **세 번** 같은 지적을 했다:
- *"코워크전달메세지박스는뭐야 너가코워크잖아"*
- *"추천대로하는데 근데 왜 cc로 넘겨 너가못해?"*
- *"Cc에게 전하지 말고 너가직접하는게 좋지않아?"*

사용자 입장에서 이 칸은 **전달 심부름**이다. 내가 할 수 있는 일을 상자에 담아 사용자에게 건네면,
사용자가 그걸 다시 옮겨야 한다 — 일이 줄어드는 게 아니라 사용자에게 늘어난다.
"리뷰해 달라"도 마찬가지다. 되돌리기 비싼 변경이면 **내가 검증 스크립트를 짜서 확인하고**,
그래도 판단이 필요하면 사용자에게 직접 묻는다. 제3자를 경유하지 않는다.

### 그럼 파일 충돌은 어떻게 막나 (칸 없이도 이미 다 돌아간다)
- `git fetch` → `rebase origin/main` — 낡은 버퍼로 덮어쓰는 사고를 구조적으로 막는다.
- `automation/tests/merge-guard.sh` — 마커가 역전되면 푸시 전에 걸린다.
- **커밋 메시지** — "무엇을 왜 고쳤나"·"지우지 말 것"은 여기에 적는다. 코드 옆에 남아야 오래 산다.
- **코드 주석 마커** — 되살아나면 안 되는 결정은 파일 안에 근거를 적는다(제거 지시 보존 규칙과 동일).
상자는 사용자를 거쳐야 전달되지만, 위 넷은 저장소 안에 있어 사용자가 아무것도 안 해도 작동한다.

### ★2026-08-09 예외 신설 — 「클로드코드 전달문」은 만든다 (사용자 지시)

> 사용자 원문: *"앞으로 클로드 코드랑 협력하면서 진행할거니깐 의사소통을 원할하게 하기위헤
> 필요하다면 텍스트박스를 만들어 전달해줄"*

위 폐지 규칙은 **내가 할 수 있는 일을 남에게 넘기는 것**을 막으려는 것이다. 그 취지는 그대로다.
바뀐 것은 상황이다 — git 프록시 403 때문에 **푸시를 내가 물리적으로 못 한다**(DEPLOY_ONE 참고).
그 자리를 클로드코드가 메우기로 사용자가 정했다. 그러니 그 한 가지에 한해 전달문을 만든다.

**만드는 경우 (이것만)**
- 푸시·병합처럼 **내가 못 하는 실행**을 클로드코드가 대신할 때
- 실행 결과를 되받아 내가 검증해야 할 때(무엇을 보고해 달라고 적는다)

**여전히 안 만드는 경우**
- 내가 할 수 있는 코드 작업 → 내가 끝낸다. "이건 CC 몫" 금지
- "리뷰해 줬으면" → 검증 스크립트를 내가 짜서 확인한다. 판단이 필요하면 사용자에게 직접 묻는다

**형식 — 반드시 코드펜스 한 덩어리**
사용자가 **복사해서 붙일** 것이라 통째로 긁히는 모양이어야 한다(*"텍스트 박스로 만들어죠 전달해줄게 복사해서"*).
설명을 상자 밖에 흩어 두지 않는다 — 상자 하나만 긁으면 클로드코드가 할 일을 다 알 수 있어야 한다.
담을 것: ①지금 상태 ②할 일(명령 그대로) ③하지 말 것(프록시 우회·자동생성 파일 손편집)
④되보고할 것(**종료 코드**로 · 화면 글자 아님) ⑤사람 몫(GAS 재배포·실청)

**길이** — 상황이 반복되면 짧게. 매번 같은 금지 문구를 통째로 되풀이하지 말고
`지시문_배포_20260809.md` 같은 기존 문서를 가리키고 달라진 것만 적는다.

### ★2026-08-09 확장 — 「분업」이 원칙이다 (사용자 지시)

> 사용자 원문: *"너가 전부 하려고하지말고 클로드코드가 잘할수잇는부분이잇으니

위 예외는 '내가 못 하는 실행(푸시)' 한 가지만 넘기라는 것이었다. 그 범위를 **넓힌다.**
이제 기준은 "내가 할 수 있느냐"가 아니라 **"누가 더 잘하느냐"**다.
다만 폐지 규칙의 원래 취지는 남는다 — **심부름을 만들지 않는다.** 넘기는 것은
사용자를 거쳐도 값이 있는 것(코드펜스 한 덩어리)이어야 하고, 애매하면 내가 한다.

**내가 맡는 것 (코워크)**

**클로드코드에 넘기는 것**

**둘 다 하지 말아야 할 것** — 같은 파일 같은 줄을 동시에 고치는 것. 넘길 때 파일을 나눈다.

### ★2026-09-07 확장 — 「네가 할 일」 앞에 코워크를 한 번 거친다 (사용자 지시)

> 사용자 원문: *"우선 코워크한테 요청하고 않된다고하면 그때 나한테 말해"*

종전에 '## 🙋 네가 할 일'은 «내가 물리적으로 못 하는 것»을 적는 칸이었다.
이제 한 단계가 더 붙는다 — **«내가 못 하고, 코워크도 못 하는 것»**만 적는다.

**순서**
1. 내가 할 수 있으면 내가 한다 (종전과 같다)
2. 내가 못 하면 **코워크에 먼저 요청한다.** 특히 «환경 차이»로 갈리는 것 —
   프록시가 막는 사이트 열기, 로그인이 필요한 화면 보기, 브라우저 실측
3. 코워크가 «안 된다»고 답한 뒤에야 사용자에게 올린다

**왜** — 사용자에게 올리면 사용자가 직접 해야 한다. 코워크가 할 수 있는 일을
사용자에게 넘기면 심부름이 하나 늘어난다(폐지 규칙의 원래 취지와 같다).
프록시 차단은 세션마다 다르므로 «내가 막혔다 = 아무도 못 한다»가 아니다.

**예외** — 사람만 할 수 있는 것은 코워크를 거치지 않고 바로 올린다.
전화·방문·서류 발급·결제·승인·실기기 확인·귀로 듣는 판정.

**★같은 날 어겼다 (2026-09-07)** — 규칙을 만든 그 대화에서 KOSIS 73301 사업체 수를
«코워크도 저도 막힌 것»이라며 사용자에게 올렸다. 사용자가 *"코워드도못해?"* 하고 물어
드러난 사실은 둘이었다: ①코워크에 **물어본 적이 없다** ②`kosis.kr` 을 **내가 직접 시도한 적도 없다**
(막혔다고 보고한 것은 앞서 돌린 리서치 에이전트였고, 나는 그 말을 그대로 옮겼다).
그 사이 코워크는 pixpics·wedsoft·homm·planonwedding·spacecloud 를 전부 열고 있었다 — 환경이 다르다.

**그래서 붙이는 절차 (올리기 전에 이 순서를 실제로 밟는다)**
1. **내가 직접 시도한다.** 남의 세션·에이전트가 «막혔다»고 한 것을 근거로 쓰지 않는다.
   내 손으로 받은 에러 메시지가 없으면 «막혔다»고 쓰지 않는다.
2. 막히면 **코워크에 요청문을 만든다.** 무엇을·어디서·어떤 형태로 받을지 적는다.
3. 코워크가 «안 된다»고 **답한 뒤에야** 사용자에게 올린다.
- 「내가 못 한다」와 「아무도 못 한다」는 다른 문장이다. 뒤엣것을 쓰려면 근거가 둘 있어야 한다.

### ★★2026-09-25 개정 — 설계는 코워크 · 구현은 코드 · 서로 검토하고 제안한다 [COWORK_SPLIT_0925] (사장님 말씀)

> 사장님 원문(코워크 전달): *«설계는 코워크가, 구현은 코드가 한다. 코워크도 구현을 직접 보면서
> 수정 · 개선까지 한다. 코드도 잘하는 부분이 있으니, 완벽한 결과물을 위해 코드의 제안도 받을 수 있게 한다.»*

위 「분업」의 기준(«누가 더 잘하나»)은 그대로다. 달라진 것은 **나누는 선**과 **되돌아오는 길**이다.

| | 맡는 일 |
|---|---|
| **코워크** | 설계(고객 눈 · 순서 · 문안 · 시간 · 화면 명세) · 사장님께 여쭐 결정 정리 · **구현 검토**(공개 저장소의 가지와 main 을 직접 받아 390 · 1280 으로 띄워 설계와 대조) · 고칠 점과 개선안(필요하면 패치) |
| **코드(나)** | 구현 전부(원천 전파 · 생성기 · 게이트 · 가지 · PR · 병합 · GAS 파일 첨부) · 기술 판단 · **제안**(더 나은 방법 · 위험 · 설계의 빈틈) |
| **사장님** | 결정 · GAS 재배포 · 귀로 듣는 판정 · 둘 사이 전달 |

**주고받는 형식 — 한 번에 한 파일(또는 코드펜스 한 덩어리)**
- 코워크 → 코드 «설계 명세»: 목적 · 무엇을(동작과 문구 그대로) · 받아들일 기준 · 건드릴 것 같은 곳(힌트) · 하지 말 것
- 코드 → 코워크 «구현 보고»: PR · 커밋 · 가지 / 바꾼 파일 / **보는 법**(어느 화면을 어떤 상태로 열면 보이나) / 게이트 결과(숫자 · 종료 코드) / 명세와 다르게 한 것과 까닭 / 코드 제안
- 코드 제안의 틀: 번호 · 무엇을 · 왜(근거: 파일 · 줄 · 사고 기록) · 대안 · 위험 · **사장님 결정이 필요한가(예/아니오)**
  - 설계를 바꾸는 제안 → 코워크가 받아 사장님 결정으로 올린다. **코드가 먼저 바꾸지 않는다.**
  - 기술 방법만 바꾸는 제안 → 코드가 정한다.
- 코워크 → 코드 «검토 회신»: 꼭 고칠 점 / 권하는 개선 / 확인됨 — 셋으로 나눈다.

**병합 순서 — [SHIP_NOW] 의 예외가 하나 늘었다**
- 되돌리기 싼 변경(문구 · CSS · 작은 동작) → 종전대로 병합까지 간다. 코워크는 병합 **뒤** 검토하고, 고칠 것은 후속 PR 로 받는다.
- **고객 화면을 크게 바꾸는 것**(예: 식순 고르기 개편)과 되돌리기 비싼 것(시트 · 스키마 · 저장된 초안 호환 · 개인정보)
  → **가지 + PR 까지만 올린다.** 병합 전에 코워크가 검토한다. 가지 이름에 `preview` 를 넣으면 베르셀 미리보기 주소가
  생긴다([PREVIEW_BRANCH_ONLY] · 미리보기에서는 GAS 연결이 막힌다 [PREVIEW_GUARD]). 사장님 확인이 필요한 것은 코워크가 여쭌다.
- 이 대기는 «내가 못 끝낸 것»이 아니라 «검토를 기다리는 것»이다 — 구현 보고에 «병합 대기 · 코워크 검토 중»으로 적는다.

#### ★코워크 검토는 «코워크와 함께 하는 작업»에만 건다 [COWORK_WHEN_INVOLVED] (2026-09-25 사장님 지적)

> 사장님 원문: *«너가 왜 코워크한테 보고를 해?» «전에 코워크랑 협력해서 작업했던 적이 없었잖아»*

예약금 카드결제(PR #843)를 위 «병합 전 코워크 검토»에 걸고, 구현 보고를 코드펜스로 만들어 사장님께
«코워크에 전달해 달라»고 했다. 그런데 그 작업은 처음부터 **사장님과 나만** 주고받았다 — 코워크의 설계 명세도,
코워크가 기다리는 검토도 없었다. 규칙 문장만 보고 걸어서 **사장님께 전달 심부름을 하나 만든 것**이다(📮 폐지 규칙이 막으려던 바로 그것).

- 병합 전 코워크 검토는 **코워크가 설계 명세를 보낸 작업**, 또는 **사장님이 «코워크 검토»를 말한 작업**에만 건다.
- 사장님과 직접 주고받은 작업은 종전대로 **내가 검증하고 병합까지** 간다. 되돌리기 비싼 것은 **사장님께 직접** 묻는다(병렬 세션 규칙 6).
- 코워크에 보일 일이 생겨도 사장님께 코드펜스 전달을 부탁하지 않는다 — 저장소가 공개라 코워크는 **PR 본문을 직접 읽는다.**
