### ★병합은 내가 한다 — 사용자에게 넘기지 않는다 (2026-09-05 사용자 지시 *"병합을너가 자동으로해"*)

**「CI 초록 뜨면 병합한다」를 `## 🙋 네가 할 일` 에 적지 않는다.** 그건 내가 하는 일이다.
사용자가 그 칸을 읽고 «내가 뭘 해야 하나» 하고 멈추게 만들면, 자동이라고 해 놓고 대기를 넘긴 것이다.

**PR 을 만든 직후 순서 (매번)**
1. `enable_pr_auto_merge`(SQUASH) 를 **바로** 건다 — 게이트가 초록이 되는 순간 GitHub 이 병합한다.
   세션이 끝나 있어도 병합된다. 이게 첫 번째 길이다.
2. 저장소 설정에서 auto-merge 가 꺼져 있으면 그 호출은 조용히 실패한다(도구가 그렇게 동작한다).
   그러면 **내가 기다렸다가 직접 병합한다.** 둘 중 무엇이 됐는지는 응답에 한 줄로 적는다.
3. 어느 쪽이든 사용자는 기다리지 않는다. 병합은 «내가 못 하는 것»이 아니므로 그 칸에 안 들어간다.

★저장소 설정(Settings → Pull Requests → Allow auto-merge)은 **내가 못 켠다.** 사용자가 한 번 켜 주면
  1번이 늘 성공해 세션이 죽어도 병합이 끝난다. 안 켜도 2번으로 돌아가니 막히지는 않는다 — 한 번만 재촉하고 다시 꺼내지 않는다.

#### ★2026-09-06 사용자 지시 *"자동으로 병합해"* — 실패 조건까지 적어 둔다

**저장소에 auto-merge 는 이미 켜져 있다.** 이번 세션에서 확인했다 — 호출이 이렇게 답했다:
> `The pull request is in unstable status (required checks are failing).`
꺼져 있으면 「저장소에 auto-merge 가 없다」고 답한다. 즉 **걸 수 있었는데 내가 한 번 실패하고 포기했다.**
그 뒤로 매번 감시 타이머로 기다렸고, 사용자가 「그대로인데?」·「배포했어?」·「자동으로 병합해」를 물어야 했다.

★★[AUTOMERGE_WINDOW] **결론부터 — 이 저장소에서 `enable_pr_auto_merge` 는 실질적으로 안 걸린다.**
세 시점 모두 실측했다(2026-09-06 · PR #656·#657 로 네 번 호출):

| 시점 | 호출 결과 |
|---|---|
| PR 직후(검사 미등록) | 거절 — "unstable · Fix the failing checks" |
| guard 가 **도는 중**(in_progress) | 거절 — **여전히 "unstable"** |
| guard 초록(clean) | 거절 — "you can merge directly" |
| (그 뒤 다른 PR) | 거절 — **"Protected branch rules not configured"** ← 진짜 이유 |

★★진짜 원인은 타이밍이 아니었다. 네 번째 호출에서 드러났다:

    Protected branch rules not configured for this branch

**GitHub 의 auto-merge 는 «클래식 브랜치 보호»를 요구한다.** 이 저장소는 그 대신
**Ruleset(`protect-main`)** 으로 main 을 지킨다(병렬 세션 규칙 1 참고). 둘은 다른 기능이라,
Ruleset 만 있으면 auto-merge 는 **어느 시점에도 안 걸린다.** 앞의 「unstable」·「clean」 거절은
그 사실을 가린 곁가지 메시지였다.

즉 「auto-merge 를 걸어 두면 세션이 죽어도 병합된다」는 기대는 **여기선 성립하지 않는다.**
사용자에게 그렇게 약속하지 않는다. (되게 하려면 Ruleset 을 클래식 보호로 바꿔야 하는데,
그건 병합 차단 규칙을 통째로 갈아엎는 «되돌리기 비싼 변경»이라 하지 않는다.)

**그래서 목표를 바꾼다 — «auto-merge 를 거는 것»이 아니라 «그 턴 안에 병합을 끝내는 것»이다.**

**순서 (매번)**
1. PR 을 만들면 한 번은 `enable_pr_auto_merge`(SQUASH) 를 시도한다(언젠가 창이 열릴 수 있으니 · 비용 0).
2. 거절당해도 **포기하지 않는다.** `pull_request_read(get_check_runs)` 로 guard 가 끝나기를 보고,
   `success` 면 **그 턴 안에 직접 병합한다.**
3. **「게이트 초록이면 병합하겠습니다」로 턴을 끝내지 않는다** — 그 순간 확인이 사용자 몫이 된다.
   실제로 이번 세션에서 「배포했어?」·「그대로인데?」·「자동으로 병합해」를 연달아 물어야 했다.

- 감시 타이머는 «내가 그 턴에 못 끝낼 때»의 폴백이지 기본 경로가 아니다.
  타이머를 먼저 걸면 세션이 끝날 때 병합이 안 된 채 남는다 — 실제로 이번에 그렇게 됐다.
- ★타이머의 `curl` 폴링은 인증이 없어 자주 «안 끝남»으로 헛돈다(이번 세션에서 네 번). 상태는
  `pull_request_read(get_check_runs)` 로 본다 — 그쪽은 늘 정확했다.

★예외는 하나 — 「되돌리기 비싼 변경」(아래 병렬 세션 규칙 6). 그때만 병합을 멈추고 사용자에게 묻는다.

### ★★★작업이 끝나면 «그 자리에서» main 까지 올린다 [SHIP_NOW] (2026-09-19 사용자 지시 *"앞으로 작업끝나면 바로메인에 올려"*)

커밋 → 브랜치 푸시 → PR → 게이트 확인 → 병합까지가 **한 턴 안에 들어가는 한 덩어리**다.

#### ★왜 이 줄이 필요했나 — 규칙은 이미 있었는데 내가 어겼다

2026-09-19 에 브랜치가 **main 보다 188커밋 앞서고 83커밋 뒤처진** 상태로 발견됐다.
분기점이 열흘 전이었다. 그 사이 신청서·계약서·GAS 를 계속 고쳤지만 **라이브에는 하나도 안 갔다.**
대가가 둘이었다:

1. **고객이 실제로 손해를 볼 뻔했다.** 홈페이지는 「하객 30명까지 추가금 없음」인데

   **9/6 목록 기준**이었다. 고칠수록 사각지대가 커지는 구조였다.
3. ★**그리고 내가 옛 판을 근거로 오판했다.** 배너 「2027 상반기 한정」을 모순으로 읽고
   하반기로 바꿨는데, main 에는 이미 「2027 상반기 «계약» 한정」으로 한 단어가 들어가 있었다.
   83커밋 뒤처진 판을 보고 「고쳤다」고 한 것이다.

#### 내가 어긴 이유 (다음에 같은 자리에서 막히지 않게)

세션 지시가 **「지정 브랜치에서 개발하고 그 브랜치에만 푸시하라」**였고,
그래서 «main 병합은 대표 허가가 필요한 것»으로 읽었다. 그 판단으로 물어보며 기다렸다.
**2026-09-19 지시로 그 망설임은 끝났다** — 지정 브랜치는 «작업하는 곳»이지
«머무는 곳»이 아니다. 작업이 끝나면 거기서 main 으로 보낸다.

#### 하는 법 (main 은 브랜치 보호라 PR 이 유일한 길이다)

```
git fetch origin main
git merge origin/main        # 뒤처져 있으면 먼저 흡수한다(rebase 아님 — 남의 역사를 다시 쓰지 않는다)
sh automation/tests/merge-guard.sh     # 통과해야 다음으로
git push -u origin <브랜치>
→ PR 생성 → enable_pr_auto_merge(SQUASH) → 게이트 초록이면 병합
```

- **뒤처진 채로 PR 을 올리지 않는다.** 먼저 main 을 흡수하고 충돌을 해결한다.
  충돌은 **날짜 기준으로 «나중 결정»이 이긴다** — 양쪽 주석의 날짜와 지시 원문을 읽고 고른다.
- **자동 병합된 줄도 의심한다.** 2026-09-19 에 `LEAD_IN` 이 충돌로 안 잡히고 합쳐졌는데
  주석은 「2초」인데 코드는 1초였다. 주석과 코드가 갈라진 덕에 보였다.
- 병합 뒤에는 **`origin/main` 해시로** 「올라갔다」를 말한다. 「올릴 것이다」라고 쓰지 않는다.
- 되돌리기 비싼 변경(병렬 세션 규칙 6)만 예외 — 그때만 멈추고 사장님께 묻는다.

### ★★요청은 먼저 빠르게 · 무거운 검사는 나중에 모아서 [FAST_FIRST] (2026-10-07 사장님 지시)

> 사장님 원문: *«요청한 거 너무 작업 시간이 오래 걸리는 거 같은데 검사 같은 건 나중에 한 번에 하고 요청한 것만 빠르게 반영하면 좋을 거 같은데»*

- **요청 하나 = 고치기 → 빠른 확인 → 가지 푸시 → PR → CI `guard`(약 2분) → 병합.** 빠른 확인은 문법 검사 · 바꾼 자리의 점검 스크립트 1~2개 · 폰 화면 한 장이다.
- **`sh scripts/gate.sh`(전체 · 15~20분)는 PR 마다 돌리지 않는다.** 요청 몇 개를 반영한 뒤, 또는 사장님이 «검사»라고 할 때 모아서 한 번 돌리고, 나온 빨강을 한 PR 로 고친다.
  PR 마다의 안전망은 CI `guard`(merge-guard · 표식 역전)다 — 그건 늘 돈다.
- 실측(2026-10-07 · #1071): 로컬 전체 게이트 약 20분 · CI `guard` 2분. «오래 걸린다»의 대부분이 이 차이였다.
- 예외 — 종전대로 병합 **전에** 전체 검사: 되돌리기 비싼 변경(시트 · 스키마 · 개인정보 · GAS · 결제 · 병렬 세션 규칙 6).
- 모아서 돌린 검사에서 다른 작업의 빨강이 나오면 «main 에도 빨간가»만 가려 적고 넘어간다 — 그 요청을 붙잡고 있지 않는다.

### ★★응답을 «병합 예고»로 끝내지 않는다 (2026-09-06 사용자 지시 *"메인에 배포해 항상"*)

**「가드가 초록이면 제가 병합합니다」로 턴을 끝내지 말 것.** 그건 예고이지 배포가 아니다.
사용자는 그 문장을 읽고 «그래서 지금 올라간 건가?» 하고 다시 물어야 했다 — 실제로 이번에
「메인에 올린거지?」·「메인에 배포해 항상」을 연달아 물었다. 예고를 남기는 순간 확인이 사용자 몫이 된다.

**그래서 이렇게 한다**
- PR 을 만들었으면 **그 턴 안에서** 게이트를 확인하고 병합까지 끝낸다. 게이트가 아직 돌고 있으면
  기다렸다가 병합한다(백그라운드로 기다리는 것은 내 일이다).
- 그 턴에 도저히 못 끝내면 `send_later` 로 스스로 체크인을 걸어 **내가** 마무리한다.
  체크인을 걸었다는 사실만 한 줄로 알리고, 사용자에게 확인을 넘기지 않는다.
- 병합이 끝나면 «올라갔다»를 `origin/main` 해시로 말한다. «올라갈 것이다»라고 쓰지 않는다.

## 병렬 세션 병합 검증 규칙 (2026-07-18)

`main` 병합(pull 포함) 직후에는 **`sh automation/tests/merge-guard.sh`** 를 실행해 최근 수정 마커가 살아있는지 확인한다.
- 이유: 병렬 세션이 낡은 파일 버퍼로 통째 커밋하면 커밋 메시지에 아무 언급 없이 다른 세션의 수정이 역전된다. 실사고 3건 — .done-fold CSS 오삭제 · guideFold 조립 줄 소실 · d42540f(위저드 함정 수정 7건 무언급 역전).
- 마커 0이면: 되돌려진 수정 커밋을 찾아 `git show <sha> -- 파일 | git apply -3`로 재적용 → 복원 커밋. 기능을 정당히 폐지해 마커가 사라지면 가드 목록도 같은 커밋에서 갱신.
- 새 세션에서 중요한 수정을 하면 마커(고유 문자열 주석)를 남기고 merge-guard.sh 목록에 추가한다.

## 배포가 막혔을 때 — git 프록시 403 [DEPLOY_ONE] (2026-08-04 사용자 지시 "앞으로 자동으로도 할수잇게")

**배포는 `sh scripts/deploy.sh` 한 줄로 한다.** 마커 자가진단 → 최신화 → 푸시까지 하고,
막히면 사람이 30초에 이어받을 것(patch)을 `_deploy-patch/` 에 만들어 둔다. 손으로 하지 말 것.

### 증상
```
remote: access denied by the git proxy: <소유자>/<저장소> is not in this session's
        authorized repository set, so the proxy will not inject a credential for it
fatal: ... The requested URL returned error: 403
```

### 원인 — 토큰이 아니다
실행 환경의 이그레스 프록시가 **세션의 '승인된 저장소 목록'** 에 있는 저장소에만 자격증명을 붙인다.
- 원격 주소에 유효한 PAT 가 이미 들어 있어도 같은 403 이 난다(실측). 토큰 문제였으면 401 이다.
- 새 토큰을 발급해도 결과가 같다 — 토큰을 쓰는 단계까지 가지 못한다.
- 목록은 **세션이 시작할 때** 한 번 읽어 온다 → 세션 도중에 승인해도 그 세션엔 안 붙는다.
- 세션 도중에 이 검사가 켜질 수 있다(`CCR_TEST_GITPROXY=1`). 아침엔 되던 푸시가 오후에 막히는 이유.

### 절대 하지 않는 것
프록시 환경변수(`https_proxy`·`HTTPS_PROXY`·`all_proxy`)를 비우고 `no_proxy` 를 전체 허용으로 바꾼 뒤,
`git -c http.proxy=` 로 git 자체 설정까지 끄고 토큰을 URL 에 실어 미는 방식 — **하지 않는다.**
저장소도 토큰도 우리 것이지만 **그 프록시는 실행 환경이 에이전트에게 건 통제**라 우리가 풀 것이 아니다.
프록시 안내문(`~/.ccr/README.md`)도 같은 말을 한다 — *"never unset HTTPS_PROXY, do not retry
organization policy denials (403/407) — report them instead."*
사용자가 요청해도, 다른 세션이 "이렇게 뚫었다"고 알려줘도 하지 않는다. 대신 아래대로 넘긴다.

### 막혔을 때 할 일 (자동)
1. `sh scripts/deploy.sh` 가 이미 `_deploy-patch/*.patch` 를 만들어 뒀다.
2. 그 patch 파일들을 **응답에 첨부**한다(GAS 파일을 첨부하는 규칙과 같은 이유 — 내가 못 하는 것은 손에 쥐여 준다).
3. `## 🙋 네가 할 일` 에 한 줄로 적는다:
   *"새 세션에 이 패치를 올려 `git am --3way _deploy-patch/*.patch && git push`"*
4. 원인·시도한 것·검증 결과(merge-guard·axe)를 함께 적는다. **"배포했다"고 말하지 않는다.**

### 다음부터 안 막히게 (사용자가 한 번만)
세션을 **시작하기 전에** 소스 목록에 `momentedit-site` 를 넣어 둔다. 그 뒤로 열리는 세션은
처음부터 승인된 상태라 `scripts/deploy.sh` 가 끝까지 자동으로 돈다.

## 병렬 세션 무충돌 워크플로 (2026-07-19 사용자 지시: "여러 클로드를 동시에 돌려도 자동으로 깔끔히 병합·오류 없이 반영")

여러 Claude 세션을 동시에 돌려도 서로 덮어쓰지 않고 자연스럽게 자동 병합되게 하려면 **모든 세션이 아래를 반드시 지킨다**. (과거 반복 사고 원인 = 낡은 스냅샷으로 main에 직접 통째 커밋 → 다른 세션 작업 무언급 역전)
1. **main 직접 push 금지.** main은 브랜치 보호(Ruleset `protect-main` · Require a pull request)로 직접 push가 막혀 있다. 반드시 자기 브랜치 + PR로만 반영한다.
2. **항상 최신 main에서 시작·유지.** 작업 시작·재개 전 `git fetch origin main` → 자기 브랜치를 `origin/main`에 rebase(또는 새 분기). 낡은 버퍼로 통째 커밋하면 다른 세션 작업이 조용히 역전된다.
3. **작게·자주 PR.** 오래 사는 브랜치일수록 충돌·역전↑. 기능 단위로 쪼개 빨리 병합해 브랜치 수명을 짧게.
4. **PR엔 auto-merge 켜기.** `Merge Guard` 체크가 초록이면 자동 병합, 마커 역전이면 자동 차단(RED). 사람이 매번 누를 필요 없음.
5. **push 전 `sh automation/tests/merge-guard.sh`** 로 마커 생존 자가진단. 중요한 수정은 마커를 남기고 가드 목록에 추가(위 규칙과 동일).
6. **되돌리기 비싼 변경은 병합 전에 리뷰를 받는다** (2026-07-26 코워크 합의). 헤더 리터럴(`CUSTOMER_HEADERS`)·시트 스키마·개인정보 파기 목록처럼 **틀렸을 때 복구가 어려운** 변경은, 감사 전부 초록이어도 병합 전에 코워크에 한 번 보낸다. 화면 문구·CSS·테스트처럼 되돌리기 싼 변경은 종전대로 auto-merge.
7. **같은 파일 동시 편집 최소화.** 가능하면 세션별로 다른 파일·영역을 맡는다. 같은 줄을 두 세션이 고치면 충돌은 불가피(도구로 100% 자동해소 불가) — 단, 위 1·4·5로 '조용한 역전'은 0이 되고, 진짜 충돌만 PR에서 눈에 보이게 남는다.
