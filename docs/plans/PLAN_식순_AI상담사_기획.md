## 0. 한 줄 컨셉과 약속의 경계

**"식순을 만드는 그 화면 안에, 이 예식의 모든 순간을 아는 전담 상담사가 함께 앉아 있다."**

- 고객이 빌더를 진행하다 막히는 질문에 즉답: 이벤트의 뜻·유래, 우리 예식에서의 진행 방식, 실제 나레이션 문안, 소요 시간, 누가 무엇을 하는지, 준비물, 예절·관례, "우리 상황엔 뭐가 어울려요?" 추천까지.
- 단순 FAQ봇이 아니라 **지금 이 고객이 만들고 있는 식순(코스·고른 순간·현재 스텝)을 알고** 답하는 그라운딩 상담사.
- **약속의 경계(명시)**: "어떤 질문이든"은 **식순 설계 범위 안**에서다. 다음은 처음부터 경계 밖으로 선언하고 해당 창구로 넘긴다 — 이 경계를 숨기면 §5 인사말이 과장이 된다.
  - 당일 운영·리허설·지연 대응 → 미정 정책(결정 필요 워크시트 A절), 확정 전까지 디렉터 상담
  - 가격·결제·계약·개인 일정 변경 → 마이페이지 상담사(기존 '마이' 접점)
  - 목록 밖 특별 연출 → 디렉터와 상담 설계(가능·불가 단정 금지)
- 부모님·지인 등 제3자 접근은 이번 범위 밖(부부 계정 경유). 필요성이 보이면 별도 기획.

### 왜 필요한가 (근거)

1. 식순 빌더는 5~10회 재방문하며 몇 주에 걸쳐 쓰는 도구. 그 사이 생기는 질문("링워밍이 뭐예요?", "편지 안 쓰면 이상한가요?")이 지금은 갈 곳이 없다 → 이탈·미완성·불안.
2. 주 고객층은 "주례 없는 소규모 예식"이 처음이라 관례 지식 자체가 없다. 연구1~2의 근거(감동 이벤트 2개 이내, peak-end, 밸리 배치)를 풀어주면 선택 불안이 줄어든다.
3. 이벤트별 디테일 질문은 디렉터 상담 시간을 가장 많이 먹는 유형 → AI가 흡수하면 상담은 확정·검수에 집중.

## 2. 지식 설계 (핵심) — `api/_ritual-kb.js`

"이벤트 하나하나 모든 걸 파악"의 실체는 프롬프트가 아니라 **KB의 완성도와 정합**이다.
**단일 진실원 = order-preview.html의 실제 문안·옵션.** 연구 문서(연구1~3·코스설계)는 '왜'를 채우는 보조 원천으로만.

### 2-1. 이벤트 백과 (1층 · 전 이벤트 × 고정 스키마)

대상(빌더 실데이터 기준 전수 — v1 누락분 보강):
하객 맞이(**나레이션/두 분 목소리 녹음** 선택·D-7 업로드) · 입장(멘트 6종·**목소리 선택**) · 베일다운 · 첫인사 ·
혼인 서약(**울컥하면 배우자가 대신 읽기** 옵션) · 링워밍 · 반지 교환 · 성혼 선언(낭독 주체: 나레이션/하객 합송/가족) ·
밸리(와인 유니티/케이크/비움) · 축배 · 축가 · 편지 낭독(부모님께/서로에게/양쪽 — **대독 옵션 없음**, 아래 주의) ·
**플래시 세리머니**(감동 코스 · 낮춤 조명+폰 불빛) · 부모님 헌정 · 부모님 덕담(**나레이션 대독(blessProxy)** 옵션) ·
성장영상(링크 제출) · 글 적어두기 · 폐식·단체촬영.

> ★ 사실관계 주의(검증에서 잡은 v1 오류): "오열 걱정" 답변은 실제 존재하는 옵션으로만 안내한다 —
> 서약은 **배우자 대독**, 덕담은 **나레이션 대독**이 있고, **편지에는 대독 옵션이 없다**(없는 '성우 대리 낭독'을 지어내면 안 됨.
> 편지 대독을 만들지는 별도 결정 사항).

각 이벤트당 스키마 10항목:

```
① 정의·유래        이게 뭔지, 어디서 온 관례인지 (예: 베일다운=일본 표준·한국 희귀)
② 우리 진행 방식    실제 흐름(앞뒤 연결 포함)
③ 나레이션 문안     빌더의 실제 멘트 전문(버전별) — 화면과 동일 인용
④ 소요 시간        분 단위 + 총 시간 안 비중
⑤ 선택지·스왑      고를 수 있는 옵션 전부와 느낌 차이
⑥ 사람·역할        누가 하는지, 섭외·부탁 팁
⑦ 준비물·마감      D-7(글·음성·영상)·D-14(식순 확정) 기한
⑧ 자주 묻는 질문    "안 하면 이상한가요?" "울 것 같아요"(→실옵션 매핑) 등
⑨ 추천 근거        연구 기반 한 줄(감정 아크·어른 하객·소규모 특성)
⑩ 미정·상담 항목    확정 안 된 것(답 안 만들고 상담 안내)
```

### 2-2. 구조·코스 지식 (2층) — ★5개 코스 전부 (v1의 최대 오류 정정)

- **빌더에는 이미 5개 코스가 전부 `ready:true`로 살아 있다**(담백·감동·가족·미니멀·축하 — 라벨·배열은 `COURSES` 실데이터 기준).
  v1은 코스설계_v1(3코스·감동/가족 미완 전제)을 원천으로 삼아 **라이브 상품의 40%를 모르는 KB**가 될 뻔했다.
  → KB 2층의 원천은 `COURSES` 객체(코스별 seq·opt·detail·flow)다. 코스설계_v1은 배경 근거로만.
- 공통 설계 규칙: 자물쇠 3(입장·첫인사·폐식) · 감동 이벤트 2개 이내 · 밸리 배치 · 정점 65~85% · 끝은 정돈된 벅참 → 단체촬영.
- 시간 구조: 본식 약 25~30분, 140분 시퀀스 안에서의 위치.
- "0개 더해도 완성"(담백함이 기본) · 특별 요청=상담 경로.

### 2-3. 운영 정책 (3층)

- **기한은 이미 일치한다(검증 확인): 빌더 화면도, 기존 `_kb.js`도 전부 D-14(예식 2주 전).** v1이 인용한 "화면 D-9ㆍAI 2주 불일치"는 낡은 메모였음 → 결정 대기함 항목도 'D-14 유지 확인'으로 정정. 글·음성·영상 파일은 D-7.
- 외부 음원·축가 범위, 시간 연장, 리허설, 종교 의식·반려동물 등: 기존 `_kb.js` 값 + 미정 목록(`PLAN_AI상담사_결정필요.md` A절)은 답을 만들지 않고 상담 연결.
- 기한·가격류는 KB 하드코딩 대신 **aiFacts(핵심정보) 최우선** 블록으로 덮어쓰기(기존 advisor와 동일).

### 2-4. KB 정합 — 수동 미러 금지, 구조적 공유로

빌더 문안은 주 단위로 바뀐다(실측). "주석+수동 점검"만으로는 §10의 1순위 리스크(화면↔답변 불일치)를 못 막는다.

1. **1차(리팩터)**: 빌더의 문안 리터럴(ENTRY·DECLARE·LETTER·VEIL·RINGWARM·TRIBUTE·TOAST·GUEST·COURSES 등)은 이미 구조화돼 있다 → **공유 데이터 모듈**(예: `assets/ritual-data.js`)로 빼서 order-preview.html과 `_ritual-kb.js`가 같은 원천을 사용. 예외인 인라인 `narBox('…')` 문자열 4곳은 이때 구조로 편입.
2. **2차(가드)**: CI 문안 대조 테스트(automation/tests) — 빌더 대표 문안 N줄이 KB에 그대로 존재하는지 검사, 어긋나면 실패. `점검` 스킬 항목은 보조로 유지.
3. 소유권: 빌더 문안을 고치는 작업이 곧 KB를 고치는 작업이 되도록(같은 파일) 설계하는 것이 1번의 목적.

## 3. 그라운딩 — "지금 두 분의 식순"을 알고 답한다

상태 요약 예(임베드 모드):

```
[지금 만드는 식순]
코스: 담백 · 현재 화면: 편지 낭독
고른 순서: 입장(멘트 A·서사형) → 첫인사(직접) → 서약(직접) → 반지 O → 성혼(나레이션) → 밸리 없음 → 편지(부모님께) → 폐식
추가한 순간: 축가(가족) · 시간 합: 약 26분
서약문: 작성됨(310자) · 편지: 아직 비어 있음
예식일: 2026-10-24 (D-97) · 신랑 OOO · 신부 OOO
```

- 가능한 답: "지금 구성이면 몇 분?", "우리 식순에서 편지 다음은?", "제가 뭘 아직 안 채웠죠?", 현재 배열 기준 추천.
- **데이터 경로(신규 작업 · v1 누락)**: 이름·예식일·고객코드는 mypage → iframe으로 현재 안 넘어간다. `orderFill` postMessage 확장으로 동봉(§1-2). 독립 열람 모드는 신원 없이 KB로만 동작(이름 미치환·일반 답변).
- **비밀 보호(절대 규칙)**: 서약·편지·인사말 **본문은 상태 요약에 넣지 않는다**(글자수·작성 여부만).
- **붙여넣기 현실 대응(신규)**: 고객이 채팅창에 편지 전문을 직접 붙여넣는 경우는 위 보호 밖이다(모델 전송+질문 로그 90일 보관 · 마스킹은 전화·이메일 패턴만).
  - 엔드포인트에서 **긴 산문형 입력은 질문 로그 적재 시 축약·비저장** 처리(예: 200자 초과 산문은 "[긴 글 첨부됨 · 로그 생략]"로 대체).
  - 화면 문구도 정직하게: "빌더에 쓰신 글은 AI에게 전달되지 않아요. 채팅창에 직접 붙여넣으신 내용은 답변을 위해 사용돼요." (과잉 약속 금지 원칙과 일치)

## 4. UI — 빌더 안에서, 스텝을 아는 상담사

### 4-1. 진입·발견성

- 공용 위젯 재사용(§1-2 개조 4종 반영). FAB 스타일·드로어 UX는 기존과 동일.
- **이중 상담사 금지**: mypage 오버레이가 열려 있는 동안 마이 FAB는 숨긴다(한 화면 한 상담사). 향후 빌더가 mypage로 이식(실행플랜 C-2)되면 한 위젯이 화면 맥락(마이↔식순)을 전환하는 구조로 합류 — 지금의 분리 배선은 그때 설정 이관만으로 재사용되게 `ME_ADV_PAGE` 설정만 페이지가 소유한다.
- **발견성 넛지 1회**: 처음 선택형 스텝에 진입했을 때 FAB 옆 1회성 말풍선 `이 순서가 궁금하면 여기서 물어보세요` (탭·닫기 후 재노출 없음). 조용한 아이콘만으로는 "관례 지식이 없는" 타깃이 존재를 모른다.
- 인사말(과장 제거): `식순을 만들다 순서가 궁금하면 물어보세요. 코스와 순간 하나하나의 진행 방식과 문안을 알고 있어요.`

### 4-2. 맥락 칩

- 드로어를 열 때마다 **현재 스텝 기준 추천 질문 3개** 갱신(위젯 함수형 chips+재렌더 훅 — §1-2).
  - 편지 스텝: `편지는 보통 얼마나 길게 쓰나요?` `읽다가 울 것 같으면 어떻게 하나요?` `부모님께와 서로에게, 뭐가 다른가요?`
    (두 번째 칩의 답은 §2-1 주의대로 실옵션만: 서약=배우자 대독 · 덕담=나레이션 대독 · 편지는 짧게 쓰는 요령과 마무리 문장 팁)
  - 링워밍 스텝: `링워밍이 뭔가요?` `가족만 돌리면 몇 분 걸리나요?` `반지 교환과 같이 해도 되나요?`
  - 코스 스텝: `코스마다 뭐가 다른가요?` `저희는 어른 하객이 많은데 어떤 코스가 맞을까요?`
- 칩 답변도 동일 엔드포인트(상태 그라운딩 포함 · 하드코딩 즉답 아님).

### 4-3. 대화 연속성·체감

- **대화 저장(신규)**: 위젯 transcript는 현재 메모리 전용이라 재방문 시 소실 → 빌더 localStorage(`me_order` 옆)에 최근 대화 저장·복원. 부부가 기기 2대로 써도 답을 다시 볼 수 있게 서버 동기화까지 갈지는 결정 대기함(추천: localStorage 우선, 동기화는 수요 확인 후).
- **오디오 공존**: 드로어 열림 → 재생 중 나레이션 정지(§1-2 ④).
- **지연 기대**: 스트리밍 없음(전체 응답 대기) → 답변은 2~5문장 유지 + 대기 중 문구 `답변을 준비하고 있어요` 1줄. 스트리밍 전환은 Phase 2 검토.
- **프라이버시 신뢰 문구 위치(신규)**: 글 적어두기 스텝의 입력칸 아래 1줄 고정 + 해당 스텝에서 드로어 첫 열림 시 1줄 — 두려움이 생기는 바로 그 지점에서 §3 문구 노출.

### 4-4. 페르소나 분기 (v1 모순 수정)

- **임베드(계약 고객)**: 마이페이지 전담 비서 페르소나(영업 0 · 케어).
- **독립 열람(계약 전 방문자)**: 전담 비서가 아니라 **기존 SALES_CORE(영업 한 줄) + 자연스러울 때 상담 예약 안내** — advisor.js의 page 분기 방식 그대로. v1처럼 계약 전 방문자에게 '영업 금지 비서'를 붙이면 "전환을 돕는 상담"이라는 노출 근거 자체가 무너진다.
- 공통: 답변 2~5문장 · 존댓말 · 마크다운/전각 줄표 금지 · 안심 문구엔 근거.

## 6. 에스컬레이션·운영 루프

- **임베드(식별 가능)**: `[[ESCALATE]]` → 인계 박스 → `handoff.js`(접점 '식순') → 기존 아침보고·미처리 집계 자동 포함.
- **독립(익명) 모드는 맨 인계 금지(신규 · dead-end 방지)**: 신원이 없어 디렉터가 회신할 수 없는 인계가 쌓인다(검증 확인: '비로그인 방문자'로 적혀 연락 수단 없음). 익명 에스컬레이션은 ①상담 예약 페이지 안내(기존 [[BOOKING]] 패턴) 또는 ②인계 박스에서 연락처 1칸을 받은 뒤에만 handoff 발사.
- **야간 정직 문구**: 에스컬레이션 문구의 "바로 전달했어요"는 야간엔 `내일 영업시간에 디렉터가 이어서 답해드려요`로 시간대 분기(아침보고 체계와 일치).
- `_qlog` 적재(§3의 긴 글 비저장 처리 포함) → 💡개선 탭에 축적 → ①KB 보강 ②aiFactSet ③결정 워크시트 A절 답 채우기로 승격.
- 회귀셋(aiReg)에 식순 대표 질문 5~8개 등록 — **단 §1-3 GAS 라우팅 분기가 선행돼야 실제 식순 엔드포인트를 검사한다.**
- `scripts/ai-live-sim-ci.js`에 `runRitual` 러너(상태 블록 + 나레이션 포지셔닝 금지어 채점 포함)를 **Phase 1에 포함**(v1은 Phase 2 검토로 미뤘음 — 출시 시점 자동 커버리지 0이 되는 구멍).
