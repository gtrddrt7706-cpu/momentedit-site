## 1. ① 적대적 검증 — 게이트가 초록인 채 제품이 깨진 사례 넷

방법: `main` 깨끗한 상태에서 제품 파일만 훼손 → 두 게이트 실행 → 원복.
(★훼손은 커밋된 상태에서만 했다 — 미커밋 고침이 `git checkout` 에 지워지는 사고를 두 세션 다 밟았다.)

### A. 다른 트랙의 문자열이 전부 8자로 잘려도 초록

`automation/platform/80_production.gs` · `handleSaveProductionTrack` 진입부

```js
// [MUTANT_A] guideinfo 가 아닌 트랙의 문자열을 8자로 자른다
if (track !== 'guideinfo' && body && body.draft) {
  for (var _mk in body.draft) if (typeof body.draft[_mk] === 'string') body.draft[_mk] = body.draft[_mk].slice(0, 8);
}
```

**결과: roundtrip 0 · guard 0.** 게이트 ①은 `track: 'guideinfo'` **한 트랙만** 저장해 본다.
나머지 여섯(`dining`·`ritual`·`final`·`seat`·`snap`·`confirm`)은 한 번도 안 지난다.
실제로 이 꼴이 나면 청첩장 문구·다이닝 요청사항·최종 확정 메모가 조용히 잘린다.

### B. 후기(review)가 5자로 잘려도 초록

`handleSubmitSurvey` 진입부에 `body.review = String(body.review).slice(0, 5);`

**결과: roundtrip 0 · guard 0.** 게이트 ③은 `answers.overall === 'very'` 만 본다.
`review`(고객이 쓴 후기 본문)는 셀에서도 관리자 상세에서도 **한 번도 대조되지 않는다.**
③의 관리자 확인은 `'very' || '매우' || '후기'` OR 조건이라 셋 중 하나만 살아도 통과한다.

### C. 되읽기에서 청첩장·최종확정을 통째로 지워도 초록

`_prodLoad` 가 `invitation`·`final` 키를 `delete` 하도록 변경

**결과: roundtrip 0 · guard 0.** 고객이 저장한 청첩장·최종 확정이 화면에서 사라지는데
게이트는 `guideinfo` 만 되읽어 확인한다.

### D. 설문 제출이 동의기록을 통째로 비워도 초록

`handleSubmitSurvey` 가 `row.set('동의기록', '{}')` 를 실행

**결과: roundtrip 0 · guard 0.** ★넷 중 가장 나쁘다 —
동의기록에는 `계약금확인`·`결과물전달일` 같은 **되돌릴 수 없는 정산 기록**이 들어 있다.
게이트 ②는 **제작 저장 경로 하나**로만 키 보존을 시험한다. 다른 핸들러가 같은 셀을 건드리는 경우는 안 본다.

### 공통 원인 — 게이트가 「대표 하나」로 짜여 있다

넷 다 같은 모양이다: **검사가 지나간 길만 안전하고, 안 지나간 길은 무방비**다.
그물 자체는 잘 짜였다(진짜 핸들러를 부르고 특수문자·유니코드까지 본다).
문제는 **표본이 하나**라는 것뿐이다.

**메우는 방향(합의 후에)**: 트랙 이름을 하드코딩하지 말고 `_prodCols()` 에서 **동적으로 뽑아 전수**로 돈다.
지금 `guideinfo` 에 쓰는 그 왕복을 트랙 수만큼 반복하면 A·C가 함께 막힌다.
B는 `review` 원문 대조 한 줄, D는 「동의기록을 건드리는 핸들러 전수」로 넓히면 된다.

| 오탐 | 진짜 이유 |
|---|---|
| 「취소 버튼 없음」 | 판을 찾는 선택자가 **안쪽 div** 를 집었다. 실제 버튼 목록을 통째로 찍어 보니 `그냥 나가기 · 저장하고 나가기 · 취소하고 계속 만들기` 셋이 다 있었다 |
| 「목차 칩 0x0」 | **완성 화면에서 쟀다.** 거기선 목차 줄이 안 그려져 0x0 이 나온다. 걷는 중(ring 단계)에서 재니 40px 이다 |

★**새 규칙 하나**: 칩·레일처럼 **화면마다 있고 없고가 갈리는 것은 「있는 화면」에서 잰다.**
0x0 은 「작다」가 아니라 「없다」이고, 그 둘을 같은 칸에 넣으면 멀쩡한 고침이 결함으로 보고된다.
(앞선 둘 — `::after` 히트영역 · 스크린샷 잘린 가장자리 — 과 같은 종류다. 세 번 다 자가 문제였다.)

## 3. ③ 모의 세계 현실성 — 어긋난 곳 둘

`scripts/audit/_gasworld.mjs` 와 진짜 `writeCell`(`automation/form-to-couple.gs:375`)을 대조했다.

### 3-1. ★모의 세계에는 「헤더가 없는 컬럼」이 존재할 수 없다

```js
// 진짜 writeCell
var c = colOf[header];
if (!c) { Logger.log('  (헤더 없음, 건너뜀: ' + header + ')'); return; }   // ← 조용히 사라진다
```

모의 세계의 `HEADERS` 는 `CUSTOMER_HEADERS + _prodCols() + 확장목록` 으로 조립된다 —
**항상 모든 컬럼이 있는 세계**다. 그래서 이 저장소가 문서로 못 박아 둔 그 사고
(`addProdTrackColumns` 주석: *"컬럼이 없는 상태로 배포되면 writeCell 이 조용히 건너뛰어
저장이 통째로 사라진다 · 화면엔 저장됐어요"*)를 **구조적으로 재현할 수 없다.**

가장 무서운 실패 모드가 모의 세계에서는 일어날 수 없는 일이다.

### 3-2. 빈 값 스킵(`force`) 규칙이 없다

진짜 `writeCell` 은 `value === '' && !force` 면 **안 쓴다**(점진 입력 보존).
모의 세계의 `setValue` 는 무엇이든 그대로 쓴다.
→ 「지우려고 빈 값을 보냈는데 안 지워지는」 부류를 모의 세계에서는 못 잡는다.

★3-1이 곧 §1-C 가 통과한 이유이기도 하다 — 컬럼이 사라지는 세계가 없으니
컬럼이 사라져서 나는 사고도 시험되지 않는다.

**메우는 방향(합의 후)**: 모의 `sheetC.getRange` 를 진짜 `writeCell` 규칙에 맞춘다 —
`COL_OF` 에 없는 헤더면 쓰지 않고 이벤트만 남기고, 빈 값은 `force` 없이는 무시.
그러면 「컬럼 없이 배포」와 「빈 값 삭제」 두 부류가 그 순간부터 시험 대상이 된다.
