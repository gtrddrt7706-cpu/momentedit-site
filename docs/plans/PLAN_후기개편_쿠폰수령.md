# A. 현행 진단

## A-1. 지금의 후기 (mypage.html `_surveySchema` · `_surveyCardHtml`)

시그니처 10문항 · 스냅 10문항, **전부 3~5지 선다**(탭 한 번). 뒤에 자유서술 1칸(선택) + 공개 동의 체크 1개.
관리자(admin.html)는 분포 막대 · 브랜드 3축 이행률 · 추천의향/종합만족 %로 집계.

**실리가 없는 이유 5가지 (코드 근거)**

| # | 문제 | 근거 | 결과 |
|---|---|---|---|
| A1 | **'놓친 것'을 물어놓고 적을 칸이 없다** | `gap` 문항이 `있었어요 · 알려드릴게요`를 골라도 이어지는 입력이 없음 (`_surveySchema` 마지막 항목) | 신호만 남고 **내용이 영원히 안 들어온다.** 사용자가 원하는 바로 그 정보가 여기서 증발 |
| A2 | 자유서술 1칸이 두 역할을 겸함 | `가장 기억에 남는 순간, 또는 더 좋았으면 하는 점 · 한마디` | 좋은 얘기가 앞에 오는 프레임 → 대부분 칭찬만. 개선점은 뒤로 밀림 |
| A3 | 개선용과 공개용이 한 칸 | 같은 텍스트에 `이 후기를 소개에 써도 좋아요` 체크 | 공개될 수 있는 글에 불만을 못 씀. **솔직함의 구조적 차단** |
| A4 | 왜(why)가 없다 | 10문항 전부 폐쇄형. `아쉬웠어요`를 골라도 이유를 못 적음 | 관리자는 "%가 낮다"까지만 알고 무엇을 고칠지는 모름 |
| A5 | 보상 조건이 모호하게 읽힘 | `후기를 남겨주시면 감사의 마음으로 스타벅스 커피 2잔을 보내드려요` | 내용과 무관하게 제출만 하면 지급인데 그렇게 안 읽힘 → **좋게 써야 할 것 같은 압력**(리서치 §C-2) |

## A-2. 지금의 쿠폰 (admin.gs `adminIssueCoupon` · mypage `renderCoupon`)

- 관리자가 바코드 **이미지(base64 data URI, 최대 2장)** + 사용기한을 수동 업로드 → `쿠폰상태='발급'` → 마이페이지 카드에 표시.
- **마이페이지 수령 자체는 이미 구현돼 있다.** 사용자가 새로 원한 건 이 경로가 아니라 **자동화·신뢰도**로 읽힌다.

**문제 3가지**

| # | 문제 | 근거 |
|---|---|---|
| B1 | 후기 완료 → 발급까지 **리마인드가 없다** | 관리자 큐(`adminHome`)에 쿠폰 관련 `pushQ` **0건**. 알림은 설문 제출 메일 한 통뿐이라 묻히면 그대로 누락 |
| B2 | 고객에게 **언제 오는지** 안 알려줌 | 완료 화면 문구가 `준비되면 위쪽에…` 수준. 기한 약속이 없어 문의 유발 |
| B3 | 바코드 이미지를 시트 셀에 base64로 저장 | `쿠폰데이터` 컬럼. 2장이면 셀 용량 압박(다른 트랙에서 이미 50k 한도 이슈 경험) |

# B. 리서치 요약 (설계 근거)

## B-1. 실행 가능한 피드백을 뽑는 문항 설계

- **폐쇄형을 프라이머로, 개방형을 바로 뒤에.** 방금 평가한 맥락이 남아 있을 때 물어야 답이 구체적이다.
- **범위를 좁힌다.** "한 가지만", "가장" 같은 제한을 넣지 않으면 응답자는 백지를 내거나 장문을 쏟는다.
- **개방형은 2~4개**, 전체의 20~30%. 그 이상은 피로로 응답률이 꺾인다.
- **중립 표현.** "무엇이 좋으셨나요"(유도) 대신 "무엇이 기억에 남으셨나요"(중립).
- 끝에 포괄 1칸("더 알려주실 게 있을까요")을 선택으로 둔다.

## B-2. 보상과 응답 편향

- 인센티브는 **참여 편향**(보상 목적 응답자)과 **응답 편향**(주는 쪽을 기쁘게 하려는 답)을 만든다. 무보상이 데이터 품질은 더 낫다는 주장도 있다.
- 다만 우리는 이미 지급 중이고 관계 기반(예식을 함께한 부부)이라 참여 편향은 낮다. **응답 편향만 설계로 눌러야 한다.**
- 완화법: **보상이 내용과 무관함을 문항 앞에서 명시**한다. "무엇을 쓰셔도, 아쉬운 점을 쓰셔도 똑같이 드려요"가 핵심 문장.

## B-3. 쿠폰 자동 발급 수단 (한국)

- **기프티쇼 비즈**(KT 운영, B2B 모바일 쿠폰 점유율 약 40%): **개인사업자 가입 가능**, **Open API 제공**, 구매 수량 제한 없는 상품 존재, 등급별 할인.
- **핀(PIN) 발행** 방식이 우리 구조에 맞는다: 수신자 개인정보를 넘기지 않고 PIN만 받아 우리 화면에 표시. 마이페이지가 이미 세션 인증이라 그대로 얹으면 된다(MMS 발송은 번호를 넘겨야 함).

# C. 제안 — 후기 개편

## C-1. 설계 원칙 4줄

1. **길이는 만족한 고객에게 그대로, 아쉬웠던 고객에게만 늘어난다.** (조건부 개방형)
2. **개선용과 공개용을 분리한다.** 솔직함은 "이건 우리만 봅니다"에서 나온다.
3. **보상은 내용과 무관하다고 먼저 말한다.**
4. **관리자 화면에서 '집계'가 아니라 '처리할 일'로 도착한다.**

## C-2. 문항 구조안

기존 10개 폐쇄형은 **유지**(집계 연속성·과거 데이터 비교 가능). 여기에 얹는다.

**① 조건부 개방형 — 부정·중립 답에만 열림**
`아쉬웠어요 / 기대보다 아쉬워요 / 예상 밖 비용이 있었어요 / 전환이 아쉬웠어요` 등을 고르면 그 문항 **바로 아래**에 한 줄 입력이 열린다.
> 어떤 점이 아쉬우셨는지 **한 가지만** 적어주시겠어요?

- 만족한 고객은 화면이 그대로다(응답률 방어).
- 리서치의 "프라이머 직후 배치 + 범위 제한"을 그대로 적용.

**② `gap` 문항 필수 후속** ← A1 구멍 차단
`사소하게 있었어요` 또는 `있었어요 · 알려드릴게요` 선택 시 **입력 필수**.
> 무엇이었는지 알려주세요. 저희가 놓친 부분을 고치는 데 그대로 씁니다.

**③ 추천 이유 한 줄** (`recommend` 직후 · 선택)
> 그렇게 답하신 이유를 한 줄로 적어주시겠어요?

NPS류 지표는 이 한 줄이 있어야 쓸모가 생긴다. 추천/비추천 양쪽 다 물음.

**④ 마지막 두 칸을 분리** ← A2·A3 해소

| 칸 | 문구(안) | 성격 |
|---|---|---|
| 공개용 | 다음 부부에게 이 순간을 소개한다면, 어떤 하루였다고 말해주시겠어요? | 선택 · 공개 동의 체크는 **이 칸에만** |
| 내부용 | 저희만 볼게요. 다시 하신다면 무엇을 바꾸고 싶으세요? **한 가지만** | 선택 · **공개 안 함 명시** |

**⑤ 보상 안내 문구 교체** ← A5·B-2

현재: `후기를 남겨주시면 감사의 마음으로 스타벅스 커피 2잔을 보내드려요`
제안: `보내주시면 스타벅스 커피 2잔을 드려요. 아쉬웠던 점을 적으셔도 똑같이 드리니, 편하게 사실대로 남겨주세요.`

> 문구 규칙 준수: 전각 줄표 없음 · 이모지 없음 · 소요시간 수치 약속 없음.

## C-3. 예상 분량

- 만족한 고객: 탭 10회 + 선택 입력 0~2칸 (지금과 사실상 동일)
- 아쉬웠던 고객: 탭 10회 + 필수 1칸 + 조건부 1~3칸 → **개선점이 실제로 들어온다**
- 개방형 총 노출은 최대 5칸이지만 **동시 노출은 2~4개**(리서치 권장 범위 안)

## C-4. 관리자 쪽 (실리의 절반은 여기)

| # | 제안 | 이유 |
|---|---|---|
| D1 | **개선 제안 큐** — `gap` 있음 또는 조건부/내부용 텍스트가 있으면 처리할 일로 등재. 읽음 → 반영/보류 상태 | 지금은 카운트 배너만 있어 아무도 손대지 않아도 티가 안 남 |
| D2 | **텍스트 원문 목록** — 문항·날짜·상품별 필터 | 분포 막대만으로는 무엇을 고칠지 못 정함 |
| D3 | **반복 신호 상위** — 같은 취지 응답이 N건 이상이면 상단 고정 | 1건은 취향, 3건은 결함 |
| D4 | 아침 보고에 **이번 달 개선 신호 N건** 한 줄 | 이미 aiMorningReport가 있으니 한 줄만 추가 |

# D. 제안 — 쿠폰 마이페이지 수령

## D-1. 1단계 (즉시 · GAS+프론트, 외부 계약 불필요) `제안`

| # | 항목 | 내용 |
|---|---|---|
| E1 | **발급 큐 신설** | 설문 완료 && 쿠폰상태 미발급 → `adminHome` 처리할 일에 `커피쿠폰 발급` 등재. 며칠 지나면 배지 승격 |
| E2 | **고객 안내 기한 명시** | 완료 화면에 "영업일 기준 N일 안에 마이페이지에 도착해요"로 교체(막연한 '준비되면' 제거) |
| E3 | **도착 알림 1회** | 발급 순간 고객에게 알림(카톡→SMS→메일 폴백). 마이페이지에 들어와야만 아는 현 구조 보완 |
| E4 | **쿠폰 카드 위치 상향** | 후기 완료 직후 화면 상단에 노출(현재 별도 슬롯) |

## D-2. 2단계 (기프티쇼 비즈 PIN API) `제안 · 결정 필요`

```
후기 제출 → (서버) 쿠폰 발급 요청 → PIN 수신 → 시트에 PIN 저장 → 마이페이지 카드에 표시
                                                    ↘ 실패 시 관리자 큐로 폴백(수동 발급 유지)
```

- **개인정보를 넘기지 않는다**(PIN만 수신) → 처리방침 변경 최소화. MMS 발송 방식은 번호를 넘겨야 해서 위탁 고지가 필요해짐.
- base64 이미지 대신 **PIN 문자열 저장** → B3(셀 용량) 동시 해결.
- 수동 발급 경로는 **남긴다**(API 장애·환불·재발급 대비).

**추가로 설계해야 할 것**: 재발급(분실), 만료 전 안내, 중복 발급 차단(멱등), 발급 로그(누가·언제·얼마), 미사용 회수 정책.

# E. 반영 순서 (배치)

**배치 1 — 후기 문항 개편 (프론트 + GAS 저장 스키마)**
C-2 ①②③④⑤ → 저장 payload에 텍스트 필드 추가 → 관리자 원문 목록(D2)
*이 배치만으로도 "고객이 느낀 것을 직접 듣는다"는 목적의 8할이 달성된다.*

**배치 2 — 관리자 활용 동선**
D1 개선 제안 큐 → D3 반복 신호 → D4 아침 보고 한 줄

**배치 3 — 쿠폰 1단계**
E1 발급 큐 → E2 기한 문구 → E3 도착 알림 → E4 카드 위치

**배치 4 — 쿠폰 2단계(외부 연동)** *결정 후*
기프티쇼 비즈 가입·충전 → PIN API 연동 → 자동 발급 + 수동 폴백

> 순서 근거: 1·2는 외부 의존이 없고, 3은 2가 있어야 큐 자리가 자연스럽다. 4는 계약·비용 결정이 선행.

# F. 리스크

| 리스크 | 대응 |
|---|---|
| 문항이 늘어 응답률이 떨어진다 | 조건부 노출로 만족 고객 화면은 불변. 개편 전후 완료율을 `설문상태` 기준으로 비교 |
| 필수 입력(gap)이 이탈을 만든다 | '있었어요'를 고른 고객만 해당. 그 답을 못 받으면 애초에 문항의 의미가 없음 |
| 공개용 후기가 줄어든다 | 분리하면 공개용은 오히려 쓰기 쉬워진다(불만을 섞을 필요가 없어짐) |
| 보상 문구 변경이 지급 약속 혼선 | 문구는 '제출 시 지급'을 더 명확히 하는 방향뿐, 조건 자체는 불변 |
| PIN 유출 | 마이페이지 세션 인증 안에서만 노출. 로그에 PIN 원문 미기록 |
| 외부 API 장애 | 수동 발급 경로 상시 유지 · 실패 시 큐로 폴백 |
