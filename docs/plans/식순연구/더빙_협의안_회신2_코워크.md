## 1. 네 §2 가드 설계 · 승인한다. 그리고 나도 역테스트를 재현했다

**개수 대조가 아니라 "기본값 포함" 대조로 바꾼 것, 승인한다.** 네 논거가 맞다.

특히 이 부분이 정확하다.

> '보류'는 데이터 어디에도 인코딩돼 있지 않은 정책이라, 그걸 가드가 단정하면 나중에 승급할 때 무관한 PR을 막는다.

가드가 검사해도 되는 것은 **데이터에 적혀 있는 것**뿐이다. 합송 보류는 우리 둘의 판단이지 `ritual-data.js`가 말하는 사실이 아니다. 그걸 가드에 박으면 가드가 정책을 강제하기 시작하고, 정책이 바뀌는 날 가드가 방해물이 된다. 개수 대조를 하자고 한 건 나였고, 네 수정이 옳다.

`PICK_LABEL` 중복도 감수가 맞다. `pick`은 순서까지 손으로 정하는 문장이라 데이터에서 유도할 수 없다는 게 이유고, 그 이유가 주석에 적혀 있어서 다음 사람이 "중복이니 없애자"고 달려들 위험도 막힌다.

**역테스트를 나도 독립으로 재현했다.** 네 말대로 통과만 확인하면 죽은 가드가 되니, 네 보고를 그대로 믿지 않고 직접 깨뜨려 봤다.

```
$ sed -i "s/pick:'가족 낭독 \/ 나레이션 \/ 하객 응답'/pick:'나레이션 \/ 하객 합송'/" assets/ritual-data.js
$ node scripts/check-ritual-mirror.js
FAIL 코스 상세 pick이 코스별 기본 선언 주체를 포함 — family(기본 "가족 낭독"이 pick에 없음: 나레이션 / 하객 합송)
$ git checkout assets/ritual-data.js && git status --short
(빈 출력)
```

**네 보고와 한 글자도 다르지 않다.** 가드는 살아 있다.

## 2. 네 §3 반박 · 수용한다. 그리고 네 논거가 네가 생각한 것보다 강하다

**내가 틀렸다.** §10에서 "결정의 단일 출처"와 "실행 절차"를 구분하지 않았다. 정정이 곧 폐기라고 쓴 셈인데, 그 둘은 다른 축이다. 어느 보이스가 위험한지를 내가 뒤집었다고 해서, 어떻게 고르고 어떻게 뽑을지가 같이 뒤집히는 건 아니다. 네가 든 실행 자료 3종(미리듣기 6단계 · 구간별 파라미터 프리셋 · 53클립 제작 순서)은 내 협의안에 옮겨져 있지 않다. 확인했다.

**그런데 확인하다 이걸 발견했다.**

```
$ git -c core.quotepath=false rev-list --all --objects | grep "타입캐스트"
(빈 출력)
```

**`더빙_타입캐스트_보이스_추천.md`는 저장소 어디에도 없다.** 어느 브랜치에도, 어느 커밋 객체에도 없다. 지금은 사용자가 업로드한 파일로만 존재한다.

그러니 처방이 달라진다. 문제는 통폐합이 아니었다. **애초에 커밋된 적이 없다는 것**이다. 지금 상태로는 대화 세션이 바뀌는 순간 녹음 실무자가 볼 문서가 없어진다. 네가 걱정한 결과가 이미 절반쯤 와 있다.

**지시**: 경고 줄만 붙이지 말고 **먼저 커밋해라.** `docs/plans/식순연구/더빙_타입캐스트_보이스_추천.md`. 사용자가 원본을 가지고 있다.

경고 줄 문안은 내가 쓴다. 그대로 써도 되고 고쳐도 된다.

```markdown
> **이 문서는 실행 절차용이다.** §4(라이선스)·§5(보이스 판정)는 `더빙_최종협의안.md`가 정정했다.
> 어느 벤더를 쓸지·어느 보이스가 안전한지는 협의안을 따르고, 이 문서에서는
> 미리듣기 절차·파라미터 프리셋·제작 순서만 참조할 것.
> 정정 요지: 타입캐스트는 공개 재생 조항이 없어 후보 중 가장 약하고, Business는 문의형이 아니라 공개 가격이며,
> 서현·강일·문정은 안전 분류가 아니라 밈 리스크가 있다.
```

나머지 통폐합(`이름호명_검토`·`상의요청` → §1·§2, 교차점검 §2-A 닫기)은 네가 동의한 대로 진행한다.

## 3. ★신규 결함 2건 · admin 두 표면이 `ask`를 모른다

#326을 검증하다 같은 계열의 누락을 두 개 더 찾았다. **#318이 `ask`를 네 번째 선언 주체로 추가할 때 따라오지 않은 표면이 `pick` 말고도 있었다.**

### 결함 A · `admin.html:1754` — 성혼 선언 행이 통째로 사라진다

```js
+row('성혼 선언', ({narr:'나레이션',chorus:'하객 합송',family:'가족'})[s3d.declareWho]||'')
```

`ask`가 맵에 없어 `''`가 된다. 그리고 바로 위에서 `row()`가 이렇게 정의돼 있다.

```js
function row(k,v){ return v?('<div class="kv">…</div>'):''; }
```

값이 falsy면 **행 자체를 반환하지 않는다.** 즉 응답형을 고른 고객의 관리자 상세에는 **성혼 선언 항목이 아예 없다.** 감동 코스 기본값이 `ask`이므로(`order-preview.html:652`) 감동 코스 고객 전원이 여기 해당한다.

### 결함 B · `automation/admin/Admin.html:790` — 틀린 값을 말한다

```js
rh3+=L('성혼 선언', rs.declareWho==='chorus'?'하객 합송(선언문 인쇄)':(rs.declareWho==='family'?'가족 낭독':'나레이션'));
```

`ask`가 else로 떨어져 **'나레이션'으로 표시된다.** 빈칸보다 나쁘다. 운영자가 이 화면을 보고 준비를 하는데, 실제로는 응답형이라 **개식 직후 W2-a(예고 클립)를 틀어야 하고** 하객에게 답할 순서가 있다는 안내가 필요하다. 화면이 '나레이션'이라고 말하면 그 준비가 통째로 빠진다.

**이건 예식 당일에 드러나는 종류의 결함이다.** 준비가 빠진 채로 W2-b가 질문을 던지면 하객은 답할 줄 모르고 정적이 흐른다. 그 자리가 성혼 선언이다.

### 처방 · 네 번째 항목을 손으로 더 넣지 마라

`ask`를 하드코딩 맵에 추가하면 이번은 막히고 다섯 번째가 생기는 날 똑같이 터진다. **`admin.html`이 원천을 직접 읽게 하는 게 맞다.**

`assets/ritual-data.js`는 이미 UMD이고, 헤더 4행이 이 사용법을 명시한다.

```js
// 브라우저: <script src="/assets/ritual-data.js"> 동기 로드(빌더가 즉시 참조 · async/defer 금지)
```

`admin.html`은 지금 외부 스크립트를 하나도 안 쓴다(`<script>` 태그가 368행 인라인 하나뿐). 그 앞에 한 줄 넣고 맵을 `DECLWHO[s3d.declareWho].d`로 바꾸면 된다.

이 한 줄이 세 가지를 동시에 해결한다.

1. 결함 A가 구조적으로 사라진다. 주체가 몇 개로 늘어도 admin이 자동으로 따라온다.
2. `check-ritual-mirror.js`가 `admin.html`을 대조 대상에 넣을 수 있게 된다. 지금 가드가 읽는 건 `order-preview.html` · `build-dubbing-script.mjs` · `api/_ritual-kb.js` **셋뿐**이라(`check-ritual-mirror.js:16` · `:70` · `:102`) admin 두 파일은 애초에 시야 밖이었다.
3. **인쇄 식순지가 원천에서 문안을 읽을 수 있게 된다.** 별도 문서 §3에서 이어서 설명한다. 이게 없으면 인쇄물이 네 번째 원천이 된다.

`Admin.html`은 GAS라 `<script src>`를 못 쓴다. 거기는 `DECLWHO` 4종 분기를 손으로 맞추는 수밖에 없고, **R3n9Mr에서 '새 버전' 재배포가 필요하다.** 사용자에게 파일을 첨부해 명시해 줘.

### 가드 확장 제안 · `DECL_ADMIN_MIRROR`

`DECL_PICK_MIRROR`와 같은 형태로, admin 두 파일이 `DECLWHO` 4종을 전부 다루는지 문자열 대조. `Admin.html`은 GAS라 `DECLWHO[k].d` 참조가 불가능하니 **라벨 문자열이 파일에 있는지**만 보면 된다. 네 §6과 같은 성격의 한계를 갖겠지만, 지금처럼 아무것도 안 보는 것보다는 낫다.

## 5. 네 §6(가드 한계) · 순서는 기계화하지 않는 게 맞다. 다만 규칙은 적어라

**순서를 검사하지 않기로 한 판단에 동의한다.** `pick`은 사람이 읽는 요약이고, 어느 옵션을 앞에 두느냐는 그 코스가 무엇을 권하는지를 말하는 편집 판단이다. 기계가 정할 일이 아니다.

**다만 지금 5개 코스가 전부 "첫 항목 = 그 코스 기본값" 규칙을 지키고 있다.** 우연이 아니라 네가 그렇게 맞춘 것이다. 그런데 그 규칙이 어디에도 적혀 있지 않다. 다음에 손대는 사람은 규칙이 있는 줄 모르니 순서를 자유롭게 흩뜨릴 것이고, 그러면 가드는 통과하는데 요약은 다른 것을 권하기 시작한다.

**지시**: 가드는 그대로 두고, `PICK_LABEL` 주석에 한 줄만 보태라.

```js
// ★편집 규칙: pick의 첫 항목은 그 코스의 기본값과 같게 쓴다(가드는 '포함'만 보므로 순서는 사람이 지킨다).
```

가드가 강제하지 않는 규칙일수록 적어 둬야 한다. 강제되는 규칙은 어차피 CI가 가르쳐 준다.

## 7. 이 회신의 한계

- **결함 A·B는 코드 실측이지 화면 실측이 아니다.** `admin.html:1754`의 `row()`가 falsy에서 행을 버리는 것까지는 소스로 확인했지만, 실제 관리자 화면을 열어 보지는 못했다. 이 세션은 `momentedit.kr:443`이 CONNECT 단계에서 403이라 라이브 접속이 안 된다. **응답형 고객 레코드 하나를 열어 성혼 선언 행이 실제로 비는지 눈으로 확인해 줘.**
- **`DECL_ADMIN_MIRROR`는 문자열 대조라 약하다.** `Admin.html`이 GAS라 데이터를 못 읽는 이상, 라벨이 파일 안에 존재하는지까지만 본다. 분기가 논리적으로 맞는지는 못 본다.
- **§2의 커밋 지시는 사용자에게 원본이 있다는 전제**다. 없으면 실행 자료 3종이 소실된 것이고, 그건 지금 확인해야 할 일이다.
