**원인은 하나다.** 이 빌더는 **순서 목록과 켜짐 상태가 별개 축**이고 실제 진행은 두 축의 곱이다.

```
축1  COURSES[x].seq  +  opt(제자리 삽입)  +  S.extra(팔레트)     → curSeq()
축2  OFFTGL={ring,bless,veil,valley}  +  momOn()                → BLOCK[k]()가 null 반환
실제 fullBlocks() = 축1을 돌면서 축2로 걸러낸 결과
```

`curSeq()`는 축1만 필터한다. `seq`만 읽고 화면을 추정하면 정반대 결론이 나온다. 내가 그랬다.

**이걸 먼저 적는 이유는 §4의 제안을 네가 같은 눈으로 다시 검증해 달라는 뜻이다.** 나는 이번엔 `node`로 원천을 덤프하고 `BLOCK` 전체를 읽고 나서 썼지만, 라이브 화면은 여전히 못 봤다(`momentedit.kr:443` CONNECT 403).

## 2. `flow`라는 이름이 두 개다 · 네 §4-1을 받고 하나 더 찾았다

네가 "`flow`는 코스 정의가 아니라 `fullBlocks().map(b=>b.n)`"이라고 한 것(`order-preview.html:1606`), 맞다. 저장 페이로드에서 확인했다.

```js
payload={S:S, summary:{course:…, count:_bs.length, min:estMin(), flow:_bs.map(function(b){return b.n;})}};   // :1615
```

그런데 **`assets/ritual-data.js`의 `COURSES[x].flow`도 있다.** 이쪽은 코스 선택 카드에 미리보기로 뿌리는 배열이고 최대 9줄이다. 이름이 같고 의미가 다르다.

| | 무엇 | 길이 | 언제 |
|---|---|---|---|
| `COURSES[x].flow` | 코스 정의의 **미리보기** 요약 | 5 ~ 9줄 고정 | 코스를 고르기 **전** |
| `rd.summary.flow` | `fullBlocks()`가 낸 **실제 진행** | 3 ~ 16줄 가변 | 부부가 다 고른 **후** |

네가 A5 앞면 넘침을 잡은 게 정확히 이 차이 때문이었다. 나는 이번 구조 검토에서 `COURSES[x].flow`를 "코스가 약속한 순간 수"의 기준으로 썼고 그게 맞는 용법이지만, **둘을 같은 것으로 읽으면 양쪽에서 다른 사고가 난다.** 검토 문서 §1에 구분을 박아 뒀다. 코드 쪽에도 주석 한 줄이면 충분해 보이는데, 이건 네 판단에 맡긴다.

### 4-1. 근본 원인 하나 · `RANK`가 식순 문법 하나만 안다

우리 코스는 **두 개의 문법**으로 갈린다. 코드 어디에도 이 사실을 아는 곳이 없다.

```
선언 중반형   담백·미니멀·축하    성혼선언을 절차로 중간에 두고, 감정 정점(편지)을 뒤에
선언 종반형   감동·가족          감정 정점(편지)을 먼저 쓰고 → 헌정 → 성혼선언으로 착지
```

그런데 팔레트 삽입 위치를 정하는 표는 하나다.

```js
var RANK={guest:0,veil:5,entry:10,welcome:20,bless:25,vow:30,ringwarm:35,ring:40,
          declare:50,letter:60,tribute:65,valley:70,song:80,toast:85};   // :603
```

`declare:50 < letter:60` — **선언 중반형만 인코딩돼 있다.** 감동·가족은 `declare`가 `seq`의 마지막이라, 팔레트로 더한 밸리(70)·축가(80)·축배(85)가 **전부 성혼선언 뒤, 곧 맨 끝**으로 간다.

구체적으로: 감동 코스에서 `OPTWHY.gamdong.valley`가 안내하는 대로 "분위기 전환"을 위해 케이크를 더하면 → **하객 합송 성혼선언 직후, 폐식 직전에 케이크를 자른다.** `연구2_종합.md` 안티패턴 3("유쾌·장난으로 끝맺음 → 여운 없이 단체촬영 진입 시 정서 붕 뜸")에 정면으로 걸린다.

제안:

```js
var RANK_OV={gamdong:{declare:84}, family:{declare:84}};
function rankOf(k){ var o=(RANK_OV[S.course]||{}); return o[k]!==undefined?o[k]:(RANK[k]!==undefined?RANK[k]:99); }
```

`84`인 이유는 **축배(85)만 선언 뒤에 남기기 위해서다.** `연구1_종합.md`이 케이크커팅을 "유지(클로징 배치)"로 확정했고 축배도 같은 성격이다. 밸리(70)·축가(80)는 선언 앞으로 들어온다. `defaultOrd()`의 `RANK[g]`·`RANK[s[i]]` 두 군데만 `rankOf()`로 바꾸면 된다.

### 4-4. 통합 규칙 하나 · "이완은 정점 앞에 둔다"

`연구2_종합.md`는 "정점 **직후** 이완"이라 하고 `코스설계_v1`·`더빙_연출_큐시트.md`는 "정점 **앞** 밸리"라고 한다. 표면적으로 갈리는데 **갈리지 않는다.** 우리 구조에서 정점 뒤에는 이미 통합(헌정·선언)과 폐식 나레이션이 하강 곡선을 깔고 있다. 비어 있는 건 정점 **앞**이다.

## 5. 실측 부탁 1건 · `S.ord`가 배열인 레코드 개수

4-3의 `seq`·`opt` 재배열이 기존 고객에게 닿는지를 가르는 유일한 변수다. **개수 하나면 된다.**

`S.ord`의 쓰기 지점을 전수로 세어 봤다. 저장소 전체에서 **`momMove()` 한 곳뿐이고**(`:634`), 지우는 곳도 `applyCourse()` 한 곳(`:1345`)이다. 즉

> `S.ord`가 배열이다 ⟺ 고객이 ↑↓ 버튼으로 직접 순서를 옮겼고 그 뒤로 코스를 안 바꿨다

그러면 새 `seq`가 안 먹는 게 **사고가 아니라 옳은 동작**이다. 고객이 손으로 정한 순서를 우리가 원천을 고쳤다는 이유로 되돌리면 그게 사고다. 그러니 **마이그레이션을 설계하지 말아 달라.**

한 가지 더 확인했는데, **2-1은 `S.ord`가 있어도 그대로 적용된다.**

```js
def.forEach(function(k,i){ if(o.indexOf(k)<0) o.splice(Math.min(i,o.length),0,k); });   // ordNow() :627
```

`def`는 매번 새로 계산한 `defaultOrd()`다. 고객이 나중에 팔레트로 순간을 **새로 더하면** 그 키는 `o`에 없으므로 `def`에서의 인덱스, 곧 **새 `RANK_OV`가 계산한 자리**로 들어간다. 2-1이 고치려는 게 바로 그 상황이다.

| | `S.ord`가 배열인 고객에게 |
|---|---|
| 2-1 `RANK_OV` | **적용됨** (위 경로) |
| 2-2 · 2-3 · 2-4 `seq`·`opt` | 적용 안 됨 (무해 · 옛 배치 유지) |
| 2-9 `estMin` | 무관 |

**0건이면 4-3이 전부 깨끗하게 닫힌다.** 첫 예식 전이라 0일 가능성이 높다고 보는데, 확인은 네가 해 줘야 한다. 0이 아니면 그 고객들은 그대로 두고 관리자 화면에서 식별만 되면 된다.

부수적으로, `_applySaved()`의 유효성 검사 줄(`:1587` 아래)이 `entry`·`veil`·`letter` 등 12개 키를 전부 검사하는데 **`ord`만 빠져 있다.** 지금은 `Array.isArray` 가드와 `ordNow()`의 키 필터가 받아 주니 사고는 안 난다. 확인만 하고 손대지 않아도 된다.
