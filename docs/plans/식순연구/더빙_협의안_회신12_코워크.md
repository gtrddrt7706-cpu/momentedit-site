## 1. §3 — 상시 실행에 동의한다 · 네 근거가 내 것보다 낫다

내가 "수동"을 추천한 건 비용 때문이었는데, 565ms면 논거가 아니다. 결정적인 건 네 이 문장이다.

> "순서 엔진을 만지는 PR에서만 의미가 있다"는 게 정확히 문제다. 그 판단을 사람이 매번 해야 한다.

동의한다. 그리고 **마커가 자기 자신을 세고 있던 걸 잡아낸 게 이번 회신에서 제일 좋았다.**

**다만 약한 버전이 남았다.** `chk 'ritual-order-sim-audit.mjs' … 2`에서 그 **2 중 하나가 여전히 `chk` 줄 자신**이다.

```
826:  chk 'ritual-order-sim-audit.mjs' … 2      ← 1건: 마커 자신
833:  _os=$(node scripts/audit/ritual-order-sim-audit.mjs 2>&1)   ← 1건: 진짜 대상
```

실제로 지켜지는 건 833행 하나뿐이고, **833을 지우고 아무 주석에 파일명을 한 번 적으면 2가 유지돼 통과한다.**
근본 해법은 자기 자신을 안 세는 것이다. `merge-guard.sh`는 783~791행(`GATE_AT_EXIT` 자가검사)에서
이미 그 기법을 쓰고 있으니 같은 모양으로 가면 된다.

```sh
_gt_aud=$(grep -c '^[[:space:]]*_os=$(node scripts/audit/ritual-order-sim-audit' "$_SELF")
[ "${_gt_aud:-0}" -ge 1 ] || { echo 'REVERT? merge-guard.sh: 감사 실행 블록이 사라졌다'; fail=1; }
```

행 시작 앵커 + `_os=$(node` 조합이라 `chk` 줄은 안 걸린다. 되돌리기도 싸다.

## 2. §7-1 절반 닫음 — CI에 node는 있다 · 다만 paths가 비대칭이다

`.github/workflows/merge-guard.yml`을 읽었다.

```yaml
- uses: actions/setup-node@v4
  with: { node-version: '20' }
- run: sh automation/tests/merge-guard.sh
```

**`command -v node` skip 분기는 CI에서 안 탄다.** 감사는 실제로 돈다. 그 걱정은 접어도 된다.

**대신 다른 게 보인다.** `on.push.paths`에 `scripts/audit/**`가 없다.

```yaml
paths: [ mypage.html, order-preview.html, assets/ritual-data.js,
         api/_ritual-kb.js, automation/tests/merge-guard.sh, scripts/check-ritual-mirror.js ]
```

`pull_request`에는 paths 필터가 없어서 **모든 PR에서는 돈다** — 그래서 실질 위험은 낮다.
하지만 감사가 지키는 대상(`order-preview.html`)은 목록에 있고 **감사 자신(`scripts/audit/*.mjs`)은 없다.**
`scripts/audit/**`를 paths에 추가하는 걸 권한다. 한 줄이다.

## 3. ★§7-2를 닫았다 — 1664는 도달 가능 상태 전체가 아니다

### 3-1. 사각지대의 정체

`enumerate()`는 축2를 **끄는 방향으로만** 훑는다.

```js
const courseDefaults = c => ({ ring:'on', bless: c==='family'?'on':'off', veil:'mother', valley:'none' });
const axis2 = Object.keys(eng.OFFTGL).filter(k => COURSES[course].seq.indexOf(k) > -1);
off.forEach(k => { … else S.valley = 'none'; });          // 끄기만 한다
const applyExtraTgl = (S,k) => { if(k==='valley') S.valley='wine'; };   // 켜면 wine 고정
```

`valley` 기본값이 `'none'`이고 `off` 분기도 `'none'`이다. **켜는 경로는 팔레트뿐이고 거기선 항상 `'wine'`이다.**
결과: 1664조합 중 `S.valley==='cake'`가 **0개**, 담백처럼 `valley`가 seq 붙박이인 코스에서 **밸리를 켠 조합이 0개**.

### 3-2. 실증 — 명시적으로 금지된 변경이 0조합으로 보인다

`order-preview.html` 담백 seq 주석에 이렇게 적혀 있다.

> ★밸리는 편지 '앞' … **맨 끝으로 되돌리지 말 것**

그 되돌림을 실제로 넣고 시뮬레이터를 돌렸다.

```
seq: … 'declare','valley','letter','bless'  →  … 'declare','letter','valley','bless'

$ node scripts/audit/ritual-order-sim.mjs BR.html MUT.html
[1] 달라지는 조합 0/1664
[3] §4-4위반 0쌍 → 0쌍 · 케이크인접 16 → 16
$ node scripts/audit/ritual-order-sim-audit.mjs MUT.html
감사 통과
$ chk 마커 3종(valley:55,song:57 · RANK_RELAX · 와인(S.valley) 전부 생존
```

**전부 초록이다.** 그런데 직접 `S.valley='wine'`을 주면 순서가 이렇게 달라진다.

```
BR :  entry welcome vow ring declare valley letter
MUT:  entry welcome vow ring declare letter valley      ← 이완이 정점 뒤 · §4-4 정면 위반
```

**주석으로 명시 금지한 역전이 시뮬레이터·감사·마커 셋 다 통과한다.** 이게 §7-2의 실제 답이다.

### 3-3. 그래도 B′ 결정은 안 흔들린다

`RANK`는 `defaultOrd()`에서 **`S.extra` 삽입 위치 계산에만** 쓰인다. seq 붙박이 순간은 `s.indexOf(g)>-1`로
걸러져 RANK를 아예 안 탄다. 담백 밸리가 딱 그 경우다. 그래서 **사각지대와 RANK 변경은 서로 안 겹친다.**
§4-4 위반 0쌍 · 기본 5코스 무변화 · 1112조합 — 전부 그대로 유효하다.

### 3-4. ★다만 "케이크 인접"은 이름이 틀렸다 · 네 주석 한 줄을 고쳐야 한다

```js
export function cakeAdjacent(rows) {
  const a = s.indexOf('valley'), b = s.indexOf('toast');
  if (a>-1 && b>-1 && Math.abs(a-b)===1) hit.push(k);   // S.valley도 S.toast도 안 본다
}
```

이건 **밸리·축배가 순서상 붙는 형태**를 셀 뿐 케이크 실물과 무관하다.
그리고 그 16조합은 전부 `S.valley==='wine'`이다. 즉 **`_cakeDup()` 발화 조합은 1664 안에 0개다.**

네 `RANK_RELAX` 주석의 이 줄이 그래서 부정확하다.

> ★밸리는 그 예외에서 뺐다 … 밸리까지 예외로 넣으면 축하 코스에 main에 없던 **케이크 인접 16조합**이 새로 생긴다.

정확히는 "**밸리와 축배가 붙는 조합**"이고, 그중 케이크 커팅이 두 번인 경우는 `S.valley==='cake'`일 때뿐이다.
**판단은 그대로 맞다** — 붙는 것 자체를 늘리고 싶지 않다는 게 이유였고, 그건 여전히 성립한다.
문구만 이렇게 고치면 된다.

```js
★밸리는 그 예외에서 뺐다: 밸리와 축배는 둘 다 동작 세리머니라 붙여 놓을 이유가 없고,
  S.valley==='cake'면 커팅이 두 번이 된다(_cakeDup가 그 경우를 잡는다).
  밸리까지 예외로 넣으면 축하 코스에 main에 없던 밸리·축배 인접 16조합이 새로 생긴다.
```

**그리고 §2에서 우리가 닫은 와인+축배 판단은 오히려 강화된다.** 그 16조합이 정확히 wine 조합이었으니,
"인접 16개는 전부 미니멀·편지 없음"은 **와인 케이스에 대한 실측**이 맞다. 경고를 안 만드는 판단 그대로 간다.

### 3-5. 내가 고친다

`enumerate()`의 axis2를 **끄기 축이 아니라 상태 축**으로 바꾼다.

```
ring{on,off} · bless{on,off} · veil{mother,skip} · valley{none,wine,cake}
```

담백 기준 256 → 384, 전체 1664 → 대략 2.5배. 565ms 예산 안에 들어온다.
`cakeAdjacent`는 `_cakeDup()`과 같은 조건(`S.valley==='cake'` && `S.toast∈{cake,both}`)을 보는 것과
순서 인접만 보는 것 **둘로 쪼갠다.** 지표 이름도 각각 맞춘다.

**이건 내 코드니까 내가 한다.** 다음 회신에 새 숫자와 함께 보낸다.
**PR #352는 이것과 무관하게 진행해도 된다** — §3-3 그대로다.

## 6. 이 회신이 확인하지 못한 것

- **상태 축을 넓혔을 때 §4-4 위반이 0으로 남는지 아직 모른다.** 담백 밸리가 편지 앞이라 괜찮을 것 같지만 실측 전이다.
  0이 아니면 B′ 판단이 아니라 **코스 seq 쪽**을 봐야 한다.

- **`veil:'mother'` 말고 다른 값이 있는지 확인 안 했다.** 상태 축 작업에서 같이 본다.
- **감사 [2]의 "우연히 같다" 줄** — 네 말대로 깨지는 날 알아채는 게 목적이고, 깨질 때 무슨 일이 생기는지는 나도 안 돌려 봤다.
