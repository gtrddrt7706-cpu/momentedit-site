### 3-1. `rankOf`의 기본값을 하나로 두면 기존 삽입 결과가 바뀐다

네 제안 그대로 쓰면 이렇게 된다.

```js
function rankOf(k){ … return o[k]!==undefined?o[k]:(RANK[k]!==undefined?RANK[k]:99); }
for(var i=0;i<s.length;i++){ if(rankOf(s[i]) > gr){ pos=i; break; } }
```

원래 코드는 **두 자리의 기본값이 다르다.**

```js
var gr=(RANK[g]!==undefined?RANK[g]:99);      // 끼울 순간: 모르면 99 → 맨 뒤
if((RANK[s[i]]||0) > gr){ … }                 // 훑는 쪽:   모르면 0  → 건너뜀
```

`rankOf`로 양쪽을 99로 통일하면, `s`에 `RANK`에 없는 키가 하나라도 생기는 날 새 순간이 **그 키 앞에** 꽂힌다(원래는 뒤). 지금은 `s`의 전 키가 `RANK`에 있어 결과가 같지만, 조용히 바뀌는 종류의 차이라 남기지 않았다. 호출부가 기본값을 정하게 했다.

```js
function rankOf(k,dflt){ var o=(RANK_OV[S.course]||{}); if(o[k]!==undefined) return o[k];
  return RANK[k]!==undefined?RANK[k]:(dflt!==undefined?dflt:99); }
…
var gr=rankOf(g);                              // 99
if(rankOf(s[i],0) > gr){ … }                   // 0
```

### 3-3. ★네 제안이 만드는 의도 밖 변경 2건

시뮬레이션에서 **네 문서 어디에도 없는 변경 2건**이 나왔다. 둘 다 팔레트 경로다.

**(가) 담백 + 헌정(팔레트) — 헌정이 편지 앞으로 갔다**

```
전:  ★선언 ◆편지 헌정
후:  ★선언 헌정 ◆편지
```

`2-2`의 `seq` 재배열 부작용이다. `tribute`(65)가 자리를 찾을 때 첫 번째로 만나는 더 큰 rank가 전에는 `valley`(70·맨 끝)였는데, 밸리를 앞으로 옮기면서 `valley`가 `letter` 앞에 오게 됐다. 그래서 헌정도 따라 올라간다.

**이건 되돌리는 쪽이 맞다고 본다.** 감동·가족의 확정 골격이 `편지 → 헌정 → 선언`이고, 헌정은 이완이 아니라 **통합** 순간이다. 담백에서만 `헌정 → 편지`가 되면 코스 간 문법이 하나 더 갈린다.

**(나) 축하 + 밸리(팔레트) — 밸리가 편지 뒤로 갔다**

```
전:  ★선언 밸리 ◆편지 축배
후:  ★선언 ◆편지 밸리 축배
```

`2-4`의 `at:6,6 → 7,7` 부작용이다. 팔레트 밸리(70)는 `song`(80) 앞에 꽂히는데, `song`이 뒤로 밀리면서 밸리도 따라 밀렸다.

**이건 §4-4 통합 규칙("이완은 정점 앞")과 정면으로 어긋난다.** 그리고 전 상태가 우연히 규칙에 맞고 있었다.

### 3-4. 두 건의 뿌리가 같다 · 제안

둘 다 **`RANK`가 이완(밸리 70·축가 80)을 정점(편지 60)보다 뒤에 두고 있어서** 생긴다. `RANK_OV`는 `declare`만 옮겼을 뿐 이 관계는 그대로다. 즉 §4-4의 규칙이 `seq`·`opt`에는 반영됐는데 **팔레트 표에는 아직 안 들어갔다.**

`RANK`에서 이완 둘을 정점 앞으로 내리면 두 건이 같이 닫힌다.

```js
// 현재
valley:70, song:80, toast:85     (letter:60 · tribute:65 뒤)
// 제안
valley:55, song:57               (letter:60 앞 · toast:85는 그대로 — 밝은 착지라 클로징 유지)
```

검산(제안 적용 시):

```
담백+밸리      ★선언 밸리 ◆편지            (2-2 목표 유지)
담백+헌정      ★선언 ◆편지 헌정            ← (가) 해소
축하+밸리      ★선언 밸리 ◆편지 축배        ← (나) 해소
축하+축가      ★선언 축가 ◆편지 축배        ← ★여기가 문제다
감동+축가      …반지 축가 ◆편지 헌정 ★선언   (선언 앞 유지)
```

**그런데 `축하+축가`가 네 `2-4` 목표(`◆편지 → 축가 → 덕담 → 축배`)와 반대가 된다.** 여기서 네 문서 두 곳이 서로 다른 말을 한다.

- **§4-4 통합 규칙**: 이완은 정점 **앞**. 정점 뒤는 통합·폐식 나레이션이 이미 하강을 담당한다
- **§4-3 2-4 근거**: 축하는 `정점(편지) → 이완(축가) → 여운(덕담) → 밝은 착지(축배)`가 연구2 아크와 일치

**나는 축하만 예외로 보는 게 맞다고 본다.** 축하는 착지가 `축배`(밝은 마무리)여서 정점 뒤 구간이 다른 코스와 다르다. 다른 코스는 정점 뒤가 하강 전용인데 축하는 상승으로 끝난다. 그러면 정점과 착지 사이가 비고, 거기가 이완 자리다. `축배는 예외`라고 네가 이미 적었는데, 그 예외가 사실 **`toast`라는 키 하나가 아니라 축하 코스의 착지 구조 전체**에 걸린다.

그래서 제안은 이렇게 된다.

```js
var RANK={…, valley:55, song:57, letter:60, tribute:65, toast:85};
var RANK_OV={
  gamdong:{declare:84},
  family:{declare:84},
  festive:{valley:70, song:80}    // ★축하만 이완을 정점 뒤로 — 착지가 상승(축배)이라 정점 뒤 구간이 비어 있다
};
```

**다만 이건 네 승인 없이는 안 넣었다.** `RANK` 본표를 건드리는 건 다섯 코스 전부의 팔레트 동작을 바꾸는 일이고, 위 두 건보다 훨씬 넓다. 지금 브랜치에는 **네가 명세한 것만** 들어 있고 (가)·(나)는 그대로 남아 있다. 셋 중 하나를 골라 달라.

| 안 | 내용 |
|---|---|
| **A** | 지금 그대로 병합 — (가)·(나)를 받아들인다 |
| **B** | `RANK` 이완 하향 + `festive` 오버라이드 (위 제안 · 내 추천) |
| **C** | (가)만 따로 막는다 — `damback:{tribute:75}` 한 줄. (나)는 남는다 |

## 4. 2-9 · A안은 쓸 수 없다 (전제가 틀렸다)

## 5. §5 실측 · 내가 직접 못 한다 · 함수를 만들어 넘겼다

`S.ord`는 시트(`Customers`의 `제작_ritual` 열)에 있고, 이 세션은 GAS·라이브 둘 다 막힌다(`script.google.com:443` CONNECT 403). 그래서 **읽기 전용 진단 함수**를 만들어 사용자에게 실행을 요청했다.

```
checkRitualOrdOverride()   ·   automation/platform/80_production.gs
```

- 아무것도 쓰지 않는다 · 재실행 무한 안전
- 출력: `식순 초안 N건(그중 _v3 M건) · S.ord가 배열인 레코드 K건` + 해당 고객의 코드·코스·순서
- **0건이면** 2-2·2-3·2-4가 전 고객에게 적용된다
- **0이 아니면** 그 고객은 그대로 둔다. 주석에 `★마이그레이션을 만들지 말 것`을 박아 뒀다 — 네 §5 논지("고객이 손으로 정한 순서를 원천 고쳤다고 되돌리면 그게 사고다")를 코드 옆에 남겨야 다음 세션이 반대로 안 간다

`CLAUDE.md` 실행 함수 위치표에도 올렸다. **결과가 나오면 그때 §3의 A/B/C 결정과 함께 병합한다.**

부수 확인 — `_applySaved()`의 유효성 검사에 `ord`가 빠져 있는 것, 맞다. `ordNow()`가 `Array.isArray` 아니면 기본 순서를 반환하고 배열이어도 코스에 없는 키를 걸러내므로 사고는 안 난다. 손대지 않았다.

## 8. 이 회신이 확인하지 못한 것

- **시뮬레이션은 순서 엔진만 떼어 돌린 것이다.** `BLOCK`을 실제로 호출한 게 아니라 `OFFTGL`/`momOn`으로 켜짐 축을 재현했다. `fullBlocks()`와 판정 기준은 같지만 `BLOCK` 내부의 `null` 반환 조건이 그 둘과 다른 곳이 있으면 결과가 갈린다. 확인한 범위는 `ring`·`bless`·`veil`·`valley` 넷이다.
- **`S.ord`가 있는 고객의 실제 화면은 못 봤다.** `ordNow()` 경로는 코드로만 읽었다.
- **`RANK` 이완 하향(§3-4 B안)은 검산만 했고 코드에 안 넣었다.** 위 표의 4줄은 `defaultOrd()` 로직을 손으로 따라간 값이지 시뮬레이션 출력이 아니다. 승인이 나면 그때 돌려서 확인한다.
- **인쇄 식순지에 `bless` 큐가 실제로 어떻게 찍히는지 못 봤다.** `BLESS_CUE_BYPOS`는 화면 큐를 고친 것이고, 인쇄물 쪽은 `rd.summary.flow`(순서 이름)만 쓰지 큐를 안 싣는다. 네가 "이 큐는 인쇄 식순지에도 들어간다"고 했는데, 내가 구현한 `_orderSheetDoc()`에는 큐가 없다. 연습 공간(`renderRehearse`)과 관리자 상세에는 들어간다. 인쇄물에도 큐를 넣을 생각이면 별건으로 얘기하자.
