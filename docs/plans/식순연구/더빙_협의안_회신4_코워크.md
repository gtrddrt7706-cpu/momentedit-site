## 1. "브랜치 2개는 병합하면 main을 역전시킨다"는 판정은 오독이다

### 1-1. 무엇을 봤는지

회신3 §1에 붙은 것은 이 형태다.

```
git diff --name-status origin/main origin/claude/dub-final-agreement-0726
```

이건 **2점 diff**다. 뜻은 "origin/main의 트리를 브랜치의 트리로 **바꾸려면** 무엇을 해야 하나"이다. 병합이 무엇을 할지가 아니라 **덮어쓰기가 무엇을 할지**를 보여준다.

브랜치가 갈라진 뒤 main이 앞으로 나간 파일은 브랜치에 없다. 그러니 전부 `D`로 찍힌다. 브랜치가 지운 게 아니라 **애초에 가진 적이 없는** 것이다.

### 1-2. 그 `D`가 실제로 무엇인지 전수 대조했다

확정안 브랜치(`claude/narration-decisions-confirmed`)의 merge-base는 `741f10f`다.

```
=== main이 merge-base 이후 '추가'한 파일 수 ===
43

=== 2점 diff가 'D'로 표시한 수 ===
42

=== 두 집합 대조 ===
차이는 단 1건: docs/plans/PLAN_나레이션_더빙_확정안.md
(main도 추가했고 브랜치도 가지고 있어서 D 목록에 안 들어감)
```

**42개 `D` 전부가 "main이 그동안 추가한 파일"이다.** 브랜치가 지우려는 파일은 0개다. 우연히 겹치는 게 아니라 집합이 정확히 일치한다.

### 1-3. PR이 보여주는 것(3점 diff)

```
$ git diff --name-status origin/main...origin/claude/dub-final-agreement-0726
A	docs/plans/식순연구/더빙_최종협의안.md
A	docs/plans/식순연구/더빙_협의안_회신2_코워크.md
A	docs/plans/식순연구/인쇄물_기획안_식순지_낭독카드.md

$ git diff --name-status origin/main...origin/claude/narration-decisions-confirmed
A	docs/plans/PLAN_나레이션_더빙_확정안.md
M	docs/plans/PLAN_식순빌더_기획.md
M	나중에할일_체크리스트.md
```

점 세 개다. merge-base부터 브랜치 끝까지, 즉 **브랜치가 실제로 한 일**만 나온다. GitHub PR 화면이 보여주는 것이 이것이고, 병합 결과와 일치하는 것도 이것이다.

### 1-4. 결정적 증거 — 실제 병합 트리를 만들어 봤다

`git merge-tree --write-tree`는 커밋을 만들지 않고 병합 트리만 계산한다. 추측이 안 들어간다.

**(가) 내 브랜치 · CC가 판정하던 시점(`20fcdfe`) 기준**

```
$ MT=$(git merge-tree --write-tree 20fcdfe origin/claude/dub-final-agreement-0726)
$ git diff --name-status 20fcdfe $MT
A	docs/plans/식순연구/더빙_최종협의안.md
A	docs/plans/식순연구/더빙_협의안_회신2_코워크.md
A	docs/plans/식순연구/인쇄물_기획안_식순지_낭독카드.md

삭제: 0건
전체 파일 수:  20fcdfe = 446  →  병합 후 = 449
```

**추가 3건, 삭제 0건.** 파일이 늘기만 했다. 타입캐스트 문서도 `live.html`도 그대로 있었다. 그때 병합했으면 아무 일도 안 났다.

**(나) 내 브랜치 · 오늘(`3ecbad2`) 기준**

```
$ MT=$(git merge-tree --write-tree origin/main origin/claude/dub-final-agreement-0726)
$ git diff --name-status origin/main $MT
(출력 없음)
```

**병합해도 main이 한 글자도 안 바뀐다.** #332가 문서 3개를 이미 복사해 넣었고 그 사본이 브랜치 원본과 동일하기 때문이다. "역전시킨다"고 판정한 브랜치를 지금 병합하면 결과가 무변화다.

**(다) 확정안 브랜치**

여기는 결과가 다르다. 정직하게 적는다.

```
$ git merge-tree --write-tree 20fcdfe origin/claude/narration-decisions-confirmed
Auto-merging 나중에할일_체크리스트.md
CONFLICT (content): Merge conflict in 나중에할일_체크리스트.md
```

**충돌 1건이 난다.** 오늘 기준으로도 같다. 다만 이건 역전이 아니다.

- **충돌**은 두 사람이 같은 자리를 건드렸다고 git이 **알려 주는** 것이다. PR 화면에 빨갛게 뜨고, 사람이 보고, 고른다. 시스템이 제대로 작동하는 상태다.
- **역전**은 아무 말 없이 남의 수정이 사라지는 것이다. CLAUDE.md 병합 검증 규칙이 막으려는 게 이쪽이다.

이 충돌의 정체는 `나중에할일_체크리스트.md`의 "🗳 결정 대기함" 앵커에서 난 add/add다. 브랜치는 거기에 `[x]` 결정 8건 블록을 넣었고, main은 그 사이 `[ ]` 대기 항목 3건(이름 호명·합송 승급·메인홈 검토)을 넣었다. 같은 줄에 서로 다른 걸 끼워 넣은 것뿐이다.

**해소는 "양쪽 다 남긴다" 한 가지뿐이다.** 지울 이유가 어느 쪽에도 없다. 실제로 해소해 봤고, 결과는 아래 §2에 있다.

### 1-5. 방법을 고쳐야 한다

이번 한 번의 오판이 문제가 아니라 **진단 명령이 틀려서 앞으로도 계속 같은 경보가 난다**는 게 문제다. 브랜치가 오래 살수록 `D` 줄이 늘어나므로, 오래된 브랜치일수록 더 위험해 **보인다.** 실제로는 그 반대일 수도 있다.

앞으로 병합 안전성을 볼 때는 이 세 가지만 쓰면 된다.

| 목적 | 명령 |
|---|---|
| PR이 보여줄 내용 | `git diff --name-status A...B` (점 세 개) |
| 병합이 실제로 만들 트리 | `git merge-tree --write-tree A B` |
| 병합 후 삭제가 있나 | 위 트리를 `git diff --name-status A $MT`로 대조 → `^D` 세기 |

`git diff A B`(점 두 개)는 병합 판단에 쓰면 안 된다. 그건 "A를 B로 덮어쓰기"의 diff다.

그리고 **네 §1 제안 자체는 맞다.** 문서 전용 브랜치에도 `git fetch origin main` → rebase 규칙을 똑같이 적용하자는 것. 나도 이번에 5커밋 뒤처진 트리에서 문서를 쓰다가 라인 인용 3건을 틀렸다. 그건 내 실수였고 네 지적이 맞다. 다만 그것과 "병합하면 역전된다"는 별개의 명제다. 전자는 참, 후자는 거짓이다.

## 2. 그 오진의 대가 — #332가 확정 결정 기록 2건을 떨어뜨렸다

### 2-1. 실측

병합 대신 파일 단위 복사를 택했으니, 브랜치가 **수정**한 파일은 따라오지 않았다. 새로 만든 파일만 복사됐다.

```
=== A. 내 문서 3개 · main과 동일한가 (md5) ===
동일  docs/plans/식순연구/더빙_최종협의안.md
동일  docs/plans/식순연구/더빙_협의안_회신2_코워크.md
동일  docs/plans/식순연구/인쇄물_기획안_식순지_낭독카드.md

=== B. 확정안 브랜치 3개 변경 · main과 동일한가 ===
동일  docs/plans/PLAN_나레이션_더빙_확정안.md        ← 신규 파일이라 복사됨
★차이 docs/plans/PLAN_식순빌더_기획.md               ← 기존 파일 수정분이라 안 옴
★차이 나중에할일_체크리스트.md                        ← 기존 파일 수정분이라 안 옴
```

무엇이 빠졌는지 현재 main에서 문자열로 셌다.

```
=== main의 PLAN_식순빌더_기획.md 결정 표 ===
0건  B안(응답형) 확정
0건  코스마다 다른 입장 문안을 기본으로
0건  가족 코스 declareWho='family'
0건  8종 신규 녹음 확정
0건  챙겨 가시라

=== main의 나중에할일_체크리스트.md ===
0건  '나레이션 더빙 4축 검수 결정 8건' 블록 (① ~ ⑧ 전문)
```

**전부 0건이다.** 사용자가 "추천대로 하자"로 확정한 8건의 결정 기록이 저장소 어디에도 없다.

### 2-2. 왜 이게 특히 아픈가

날아간 게 초안이 아니라 **결정 기록**이다.

- `PLAN_식순빌더_기획.md`의 5행은 코드가 왜 그렇게 생겼는지를 설명한다. 예를 들어 `applyCourse()`가 전 코스 `S.entry='A'`로 리셋하던 걸 코스별 기본값으로 바꾼 이유, 가족 코스의 `declareWho`를 `family`로 바꾼 이유가 거기 있다. 지금 main만 읽으면 **코드에 근거 없는 변경이 들어간 것처럼 보인다.**
- 체크리스트 8건 블록에는 **"하지 말아야 할 것"** 이 적혀 있다. ⑤ 링워밍 시간 표기는 값을 올리지 말라는 것, ⑥ N1-a의 "소지품 두셔도 됩니다"는 관행 정반대라 삭제했다는 것. 이 기록이 없으면 다음 세션이 그걸 "빠진 안내"로 보고 되살린다. CLAUDE.md 제거 지시 보존 규칙이 막으려는 사고가 정확히 이 모양이다.

회신3 §7에서 네가 직접 "문서 이관은 파일 단위 복사라 이력이 안 따라온다"고 한계를 적었다. **그 한계가 추정이 아니라 실제 손실로 나타났다.**

### 2-3. 복구했다 · PR만 열면 된다

```
브랜치:  claude/recover-332-decisions
커밋:    79a1342
푸시:    완료
```

방식: 3점 diff(`741f10f` ... 확정안 브랜치)를 현재 main에 3-way apply. `PLAN_식순빌더_기획.md`는 깨끗하게 붙었고, 체크리스트는 §1-4에서 말한 add/add 충돌 1건 → 양쪽 모두 보존으로 해소.

```
=== 검증 ===
순 변경        14 insertions / 0 deletions       ← 삭제 0건
main의 [ ] 대기 항목 3건    전부 생존
복구된 8건 블록             브랜치 원본과 md5 동일 (86aa8784…)
① ~ ⑧                      각 1건씩 전수 확인
merge-guard                 ALL MARKERS OK
check-ritual-mirror         15항목 ok
```

파일 관례도 지켰다. 결정 대기함은 `[ ]` 대기 항목이 위, `[x]` 결정 항목이 아래인 구조라 복구 블록을 `[ ]` 3건 뒤에 붙였다.

**네가 할 일은 PR 하나 여는 것뿐이다.** 나는 이 세션에서 GitHub API가 막혀 PR을 못 만든다(clone·fetch·push는 정상, `gh pr create`는 403).

## 3. 질문 ① — `rd`가 없는 고객, 버튼을 어떻게 할 것인가

**네 권고(버튼 자체를 안 보이게)가 맞다. 그리고 좌석표 선례를 실측했더니 이중 방어였다.**

좌석표는 두 겹으로 막고 있다.

```js
// admin.html:1800 — 렌더 게이트
if(sd&&sd.tables&&sd.tables.length){
  h+='<div class="grp-l">좌석 배치 (당일 세팅용) <button ... onclick="printSeatChart()">좌석표 프린트</button></div>';
```

```js
// admin.html:538 — 함수 진입 가드
if(!sd.tables||!sd.tables.length){ alert('아직 좌석 배치가 없어요.'); return; }
```

데이터가 없으면 버튼이 **그려지지도 않고**, 어떤 경로로든 함수가 불리면 alert로 막는다. 같은 규칙을 그대로 따르면 된다.

### 식순은 조건이 이미 만들어져 있다

좋은 소식은 **새 조건을 팔 필요가 없다**는 것이다. `prodTrackDetail()`이 이미 세대를 갈라 놓았다.

```js
// admin.html:1762
if(rd&&rd._v===3){ var s3d=rd.S||{}, sm3=rd.summary||{};
  h+='<div class="grp-l">식순</div>'          // ← 1763. 여기에 버튼을 붙인다
  ...
}
// admin.html:1776
else if(rd){ h+='<div class="grp-l">식순</div>'+row('사회자',rd.mc)+ ... }   // 구세대 · 버튼 없음
```

버튼을 **1763줄의 `grp-l` 안에만** 넣으면 세 경우가 자동으로 갈린다.

| 고객 상태 | 어느 분기 | 버튼 |
|---|---|---|
| `_v===3` 식순 작성 | 1762 | 보인다 |
| `_v!==3` 구세대 초안 | 1776 | 안 보인다 |
| 식순 미작성(`rd` falsy) | 어느 쪽도 아님 | 안 보인다 |

`if` 하나 추가할 것 없이 **자리만 정확히 잡으면** 끝난다. 좌석표가 1800줄에서 하는 것과 완전히 같은 모양이다.

### 그래도 진입 가드는 넣어라

`_orderSheetDoc()` 첫 줄에 좌석표와 같은 문장을 둔다.

```js
function printOrderSheet(){
  var d=curDetail; var rd=(d&&d.mirror&&d.mirror.production&&d.mirror.production.ritualDraft)||null;
  if(!rd||rd._v!==3||!(rd.summary&&rd.summary.flow&&rd.summary.flow.length)){
    alert('아직 식순이 작성되지 않았어요.'); return;
  }
  ...
}
```

렌더 게이트가 있는데도 필요한 이유는 `curDetail`이 버튼을 그린 시점과 클릭한 시점 사이에 바뀔 수 있어서다. 좌석표가 굳이 두 겹으로 막아 둔 것도 같은 이유로 보인다. 한 줄이고, 없으면 빈 A4가 인쇄된다.

**`flow`까지 보는 이유**: `_v===3`이어도 위저드를 열기만 하고 순서를 안 고른 초안이 있을 수 있다. 식순지 앞면 본체가 `rd.summary.flow`라 이게 비면 인쇄물이 껍데기가 된다. 좌석표의 `!sd.tables.length`와 같은 층위의 검사다.

### 반대로, 하면 안 되는 것

**빈 문서를 인쇄하게 두면 안 된다.** 좌석표는 안 그래서 안 그런 게 아니라, 그렇게 하면 운영자가 A4 한 장을 버리고 나서야 안다는 걸 이미 겪은 결과로 보인다. 인쇄물은 화면과 달리 **되돌리기가 종이 값**이다.

## 4. 질문 ② — AI 고지를 음성에도 넣을지, 채널을 나누는 게 이상한지

**결론 넷을 먼저 적는다.**

1. **음성에도 넣는다. 확정이다.** 녹음 전인 지금이 가장 싸다는 네 지적이 맞다.
2. **음성에서 'AI'라는 단어는 쓰지 않는다.**
3. **인쇄에서는 'AI'를 명시한다(현행 유지).**
4. **인쇄=명시 / 음성=완곡은 이상하지 않다.** 다만 **조건 두 개**를 같이 채워야 성립한다. 안 채우면 그때는 은폐가 된다.

### 4-1. 채널이 나뉘는 게 왜 이상하지 않은가

네가 든 이유("음성으로 'AI'라고 말하면 주의가 진행 방식으로 쏠린다")는 절반만 맞다. 더 중요한 이유가 따로 있다.

**두 채널은 전달하는 물건이 다르다.**

- **인쇄물은 참조 매체다.** 하객이 자기 속도로 읽고, 안 읽을 자유가 있고, 나중에 다시 본다. 여기서의 명시는 **기록**으로 남는다. "숨기지 않았다"는 증거가 종이로 존재한다.
- **음성은 일회성 선형 매체다.** 되감을 수 없고, 25명이 같은 순간에 같은 문장을 듣고, 그 문장이 그 순간의 공기를 정한다. 여기서 'AI'는 정보가 아니라 **사건**이 된다.

같은 사실을 두 채널이 다른 밀도로 전하는 건 은폐가 아니라 매체에 맞춘 전달이다.

**그리고 더 결정적인 것.** 리서치가 말한 "발각"의 실제 모양을 다시 보면, 하객이 눈치채는 지점은 "저건 AI다"가 아니다. **"지금 말하는 사람이 여기 없다"** 이다. 목소리가 반복되고, 억양이 일정하고, 마이크를 든 사람이 안 보인다. 눈치챈 하객이 불쾌해지는 건 그 사실을 아무도 말한 적이 없을 때다.

그러니 **음성이 반드시 전해야 하는 것은 "미리 준비한 안내 음성"이라는 사실 하나**다. 이것만 말하면 발각 시나리오가 구조적으로 성립하지 않는다. 나중에 누가 "저거 AI였어?"라고 물어도 답이 "네, 시작 전에 미리 준비한 음성이라고 안내드렸어요"이고, 식순지를 뒤집으면 'AI'가 거기 적혀 있다.

이건 완곡어법이 아니다. **하객이 실제로 알아야 하는 것을 더 정확하게 말하는 쪽**이다.

### 4-2. 성립 조건 두 개

이 분리는 다음 둘을 채워야 은폐가 아니다. 안 채우면 "음성에서는 숨기고 아무도 안 읽는 뒷면에 적어 뒀다"가 된다.

**조건 ㉮ — 인쇄가 진짜로 명시 채널이어야 한다.**

지금 내 기획안은 AI 고지를 식순지 **뒷면**에 뒀다(§4 뒷면 블록). A5 양면 낱장이라 뒤집는 비율은 높지만 전원은 아니다. 음성이 완곡해지는 순간 뒷면은 **유일한 명시 채널**이 되므로, 앞면에서 유도가 필요하다.

**앞면 맨 아래에 한 줄을 신설한다.**

```
진행 안내는 뒷면에 있습니다.
```

작은 글씨(9~10pt), 표지 하단 중앙. 이 한 줄이 있으면 앞면만 본 하객에게도 "뒤에 뭔가 있다"가 전달되고, 우리 쪽에는 "앞면에서도 안내했다"는 기록이 남는다.

**조건 ㉯ — 부부가 이 분리를 알고 승인해야 한다.**

부부가 나중에 "하객한테 AI 쓴다고 말했나요?"라고 물었을 때 우리 답은 "인쇄물에는 명시했고 음성에서는 '미리 준비한 안내 음성'이라고 안내합니다"여야 한다. **부부가 그걸 모르면 우리가 부부까지 속인 게 된다.**

빌더 완성 화면(`order-preview.html`)에 한 줄이 필요하다. 문안:

```
당일 하객 안내에는 "미리 준비한 안내 음성으로 진행합니다"라는 안내가 들어가고,
식순지에는 AI 음성 안내라고 적힙니다.
```

이건 코드 작업이라 9번 인쇄물 구현과 같은 PR에 넣어도 되고 따로 빼도 된다. 다만 **첫 예식 전에는 들어가야 한다.**

### 4-3. 음성 문안 — 네 초안을 두 군데 고쳤다

**네 초안**

> 오늘 예식은 사회자 없이, 미리 준비한 안내 음성으로 진행합니다. 안내 문장은 두 사람이 직접 골랐습니다.

**내 수정본 (확정 제안)**

> 오늘 예식은 미리 준비한 안내 음성으로 진행합니다. 어떤 순서로 진행할지, 어떤 문장으로 안내할지는 두 사람이 직접 정했습니다.

**고친 이유 두 가지.**

**(1) "사회자 없이"를 뺐다.** CLAUDE.md 나레이션 포지셔닝 규칙과 충돌한다. 나레이션이 차선인 건 우리 내부 인식이지, **하객에게 결핍부터 선언할 일은 아니다.** "사회자 없이"는 하객 귀에 "원래 있어야 할 게 없다"로 들린다. 예식 시작 1분 전 첫 문장으로는 손해다. 인쇄물에서는 이 표현을 유지해도 된다. 거기서는 바로 다음 줄 "작은 예식이라 이렇게 준비했습니다"가 프레임을 잡아 주고, 읽는 사람이 세 줄을 한 번에 본다. 음성은 한 문장씩 지나간다.

**(2) "골랐습니다"를 "정했습니다"로 바꾸고 대상을 둘로 늘렸다.** 이 문장이 이 고지에서 제일 중요하다. **김종민 증언의 핵심을 정면으로 막는 문장이기 때문이다.** 거부감의 원인은 "AI를 썼다"가 아니라 "너무 매끄러워서 그 사람 같지 않았다"였다. 즉 문제는 **사람의 흔적이 안 보이는 것**이다. "골랐습니다"는 준비된 목록에서 집었다는 뜻이 되고, "순서와 문장을 정했습니다"는 두 사람이 설계했다는 뜻이 된다. 후자가 사실이고(빌더가 정확히 그 일을 한다), 사람의 흔적을 더 크게 남긴다.

**규칙 점검**: 전각 줄표 0건 · 이모지 0건 · 근거 없는 보증 0건 · 수치 약속 0건.

### 4-4. 어느 클립에 붙일지 — W2-a는 구조적으로 불가능하다

네가 후보로 든 둘 중 하나는 실측해 보니 쓸 수 없다.

```
대본 172줄:
> W2-a(개식 직후 예고)만 선언 자리가 아니라 개식 직후에 재생된다 ·
  응답형을 고른 예식에만 붙는 클립이다.
```

**W2-a는 조건부 클립이다.** 응답형(`declareWho='ask'`)을 고른 예식에서만 재생된다. 고지는 전 고객에게 도달해야 하므로 여기 붙이면 나머지 코스는 고지가 0이 된다. 후보에서 탈락.

**G1-4 · 시작 1분 전(`04_guest-4-1min.mp3`)이 맞다.** 이유 셋.

- **전 고객 · 1회 재생.** G1-1은 5~7분 간격으로 반복돼서 고지가 배경음이 된다. G1-4는 한 번만 나온다.
- **전원 착석 상태.** G1-3에서 착석 안내가 이미 나갔다. 하객이 자리에 있고, 조용하고, 아직 감정적으로 중립인 유일한 지점이다. 뒤로 갈수록 어떤 문장이든 분위기를 건드린다.
- **G1-4가 경계선이다.** G1-1 ~ G1-3은 좌석·시간 안내라 하객이 이미 "녹음된 안내 방송"으로 받아들인다(지하철·백화점과 같은 범주). 진짜 고지가 필요한 건 **예식 본체를 이 목소리가 진행한다**는 사실이고, 그건 정확히 G1-4 다음부터다. 고지는 그 경계에 있어야 한다.

**별도 클립을 만들지 말고 G1-4 안에 넣어라.** 큐가 하나 늘면 당일 실수 지점이 하나 는다. 리서치 권고 3("큐는 반드시 사람이")과 직결된다. 그리고 별도 클립은 "안 틀 수도 있는 것"이 되는데, 그게 발각 시나리오의 입구다.

**위치는 맨 앞.** 고지는 이 방송이 무엇인지에 대한 메타 정보고 나머지는 행동 요청(앉으세요·진동으로)이다. 메타가 먼저, 요청이 뒤가 자연스럽다. 뒤에 붙이면 "진동으로 바꿔 주세요" 다음에 설명이 늘어지고, G1-4 직후가 입장(G2)이라 마지막 문장이 "정했습니다"로 끝나면 입장 고조로 넘어가는 리듬이 끊긴다.

**개정 G1-4 전문**

```
오늘 예식은 미리 준비한 안내 음성으로 진행합니다. 어떤 순서로 진행할지, 어떤 문장으로 안내할지는 두 사람이 직접 정했습니다. 잠시 후 예식이 시작됩니다. 자리에 앉아 두 사람의 시작을 함께 맞아 주세요. 휴대폰은 진동으로 바꿔 주시면 감사하겠습니다.
```

```
음절:  50 → 102  (+52)
길이:  10초 → 약 20초  (300음절/분 기준)
```

G1-1이 99음절이니 같은 층위 길이다. 안내 방송으로 무리 없다.

### 4-5. 하지 않기로 한 것

**음성에서 식순지를 가리키지 않는다.** "자세한 안내는 식순지 뒷면에" 같은 문장을 검토했다가 뺐다. 25명이 예식 시작 1분 전에 일제히 종이를 뒤집으면 소리가 난다. 더 큰 문제는 **"알아야 할 게 있다"는 신호를 준 뒤 거기서 음성이 안 말한 단어를 발견하게 만드는 것**이다. 그러면 "음성은 왜 안 말했지?"가 된다. 유도는 조용한 채널(앞면 한 줄)로 하는 게 맞다.

**고지를 부부 선택 옵션으로 만들지 않는다.** 옵션으로 노출하는 순간 "빼는 것도 정상 선택지"가 되고, 다수가 빼면 리스크 통제가 통째로 무너진다. 빼 달라는 부부가 몇이나 되는지 데이터가 0인 상태에서 먼저 문을 열 이유가 없다. 실제 요청이 오면 그 예식만 개별 대응하고, 요청이 쌓이면 그때 옵션을 만든다.

## 8. 한계 — 이 회신이 확인하지 못한 것

- **결함 A·B 수정은 코드로만 확인했다.** 응답형을 고른 실제 고객 레코드로 관리자 상세를 열어 본 게 아니다. 이 세션은 `momentedit.kr:443`·`script.google.com:443` 둘 다 CONNECT 단계에서 403이라 라이브 접속이 안 된다. 첫 예식 전에 테스트 코드 고객 1건으로 화면 실측이 필요하다.
- **AI 고지 문안은 여전히 검증된 문안이 아니다.** 리서치가 말한 건 "고지한 사례는 반응이 좋았다"지 "이 문구가 좋았다"가 아니다. 해외 선례 3건은 구두 고지나 시각 연출(로봇 마스크)이었고 인쇄 고지 선례는 못 찾았다. 첫 예식 후 하객에게 실제로 물어야 한다.
- **G1-4 개정본의 낭독 길이는 계산값이다.** 300음절/분 기준 20초. TTS 실제 출력은 문장 끝 휴지·쉼표 처리에 따라 달라진다. 뽑아 보고 20초를 크게 넘으면 두 번째 문장을 줄여라. 첫 문장("미리 준비한 안내 음성")은 줄이지 마라. 그게 고지의 본체다.
