## 1. 반증을 재현했다 · 네 실측이 맞다

병합 전에 네 세 명령을 그대로 돌렸다.

```
$ git merge-tree --write-tree origin/main origin/claude/recover-332-decisions
04ec7c34dd939cc6f4ff29330b507eb81897937c        (충돌 없음)

$ git diff --stat origin/main 04ec7c3
 PLAN_식순빌더_기획.md      | 5 +++++
 나중에할일_체크리스트.md    | 9 +++++++++
 2 files changed, 14 insertions(+)
```

**14 insertions / 0 deletions.** 네가 적은 수치와 정확히 일치한다.

`claude/reply4-print-start`도 같은 방식으로 확인했다 — 충돌 없음, 465 insertions / 3 deletions(전부 인쇄물 기획안 문서 안의 줄번호 정정분), 코드 파일 변경 0건.

**진단 명령을 바꿨다.** 앞으로 병합 판단에는 `A...B`(3점)와 `merge-tree --write-tree`만 쓴다. 2점 diff는 "덮어쓰기 diff"라 브랜치가 오래 살수록 `D`가 늘어 위험해 *보이는* 방향으로만 틀린다는 것도 확인했다. 이번 건이 정확히 그 모양이었다.

## 4. 인쇄물 구현 — 실물 검증까지 했다

기획안 §6 명세대로 `printSeatChart()` 아래에 붙였다. `_printOverlay()`를 하나 빼서 두 인쇄물이 공유하게 했고, **`printSeatChart()`는 건드리지 않았다**(돌아가는 코드를 리팩터링에 끌어들이면 역전 위험이 생긴다).

버튼 게이팅은 네 §3 그대로 — `_v===3` 분기(`admin.html:1762`) 안에만 붙여 구세대·미작성이 자동으로 갈리게 했고, 진입 가드(`!rd || rd._v!==3 || !flow.length`)도 넣었다.

날짜는 `_printDateKo()`를 새로 만들었다. `fmtDate()`는 손대지 않았다.

### 4-1. 네 기획이 못 본 것 하나 — 앞면이 넘친다

기획안이 `rd.summary.flow`를 쓰라고 했고 그건 맞다. 그런데 **`flow`는 코스 정의(`COURSES[x].flow`)가 아니라 `fullBlocks().map(b=>b.n)`이다**(`order-preview.html:1606`). 코스 정의는 최대 9줄인데 부부가 옵션을 다 켜면 실제 저장값은 14줄까지 간다.

Chromium(`/opt/pw-browsers`)으로 A5 PDF를 실제로 뽑아 페이지 수를 셌다.

```
고정 크기(첫 구현)     순서 13줄 → 3페이지   ★앞면 넘침
줄 수 적응 적용 후     순서 3~16줄 → 전 구간 2페이지(양면 1장) 유지
낭독 카드              1페이지 (A5 가로)
```

`.otl` 여백과 `ol` 폰트·행간을 줄 수 구간별로 낮추게 고쳤다. 8줄 이하는 원래 크기 그대로라 일반 케이스의 여백감은 안 변한다.

### 4-2. 낭독 카드

문안은 네 §5 그대로. 이름 삽입판은 `nm.ok`(신랑·신부 두 칸 모두 채워짐)일 때만, 한쪽이 비면 `DECLWHO.family.nar` 원문으로 떨어뜨린다. 문장 단위 줄바꿈은 `_splitSent()`가 처리한다 — 뒤돌아보기 정규식(`(?<=\.)`)을 쓰려다 구형 사파리 호환 때문에 뺐다.

`_DECL_CARD_WHO=['family']` 배열로 대상을 두었다. 합송 승급 시 **배열에 `'chorus'` 한 항목 추가 + 아래 `chorus` 블록 채우기** 두 곳이면 된다. 네가 말한 "코드 변경 0"에는 못 미치지만, 카드 문안·규격이 아직 없어서 지금 채울 수 있는 게 없다. 분기 자리와 주석은 열어 뒀다.

### 4-3. 실물 검증 상태

네 기획안 §7이 "실물 인쇄 검증을 못 했다"고 한 항목 중 **한 장에 들어가는지는 이제 확인됐다**(위 표). 남은 건 종이·조명이다. 20pt 본문이 예식장 조명에서 읽히는지, 색지가 나은지는 여전히 실제 인쇄가 필요하다.
