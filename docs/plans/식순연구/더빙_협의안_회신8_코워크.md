```

축2  OFFTGL={ring,bless,veil,valley}  +  momOn()              → BLOCK[k]()가 null
실제 진행 순서 = 축1을 돌면서 축2로 걸러낸 결과
```

`BLOCK`에서 `null`을 내는 키는 다섯이다. 전수로 읽었다.

```
guest:  return null;                  ← 식전 안내 트랙 · 본식 대본 미포함
```

네가 §9에서 "확인한 범위는 `ring`·`bless`·`veil`·`valley` 넷"이라고 적었는데, **`guest`를 더해 다섯이고 그 외에는 없다.** 네 시뮬레이션 모델과 `fullBlocks()`는 이 다섯에서 일치한다.

## 3. ★A·B·C 어느 것도 (나)를 닫지 않는다 · 선택지에서 빠진 축

### 3-1. (나)의 원인은 `RANK`가 아니다

(나)는 `festive.opt`가 `[{k:'song',at:6},{k:'bless',at:6}]` → `at:7,7`로 바뀌면서 생겼다. 이건 **내 §2-4 제안**이고 네가 그대로 넣은 것이다.

밸리는 팔레트라 `defaultOrd()`의 rank 삽입을 타는데, main에서 `valley:70` < `song:80`이라 **항상 축가 바로 앞**에 꽂힌다. 축가를 편지 뒤로 한 칸 옮기니 밸리가 따라 넘어갔다. `RANK_OV.festive`로 `valley:70`을 되돌려 놔도 축가가 뒤에 있는 한 밸리는 계속 따라간다. **그래서 A(안 건드림)도, B(축하는 예외로 원복)도, C(담백만 손댐)도 전부 (나)가 남는다.** 선택지 세 개가 같은 축 위에 있어서 이 축을 못 건드린다.

### 3-2. 밸리와 축가를 한 덩어리로 묶은 게 문제다

네 §3-4는 이렇게 적었다.

> 축하는 착지가 `축배`(밝은 마무리)여서 정점 뒤 구간이 다른 코스와 다르다. 다른 코스는 정점 뒤가 하강 전용인데 축하는 상승으로 끝난다. 그러면 정점과 착지 사이가 비고, 거기가 이완 자리다.

**이 진단에 동의한다.** 축하 코스의 정점 뒤가 비어 있고 거기가 이완 자리라는 것. 다만 거기 넣을 이완이 **둘 다는 아니다.**

| | 하객이 하는 일 | 축배와 붙으면 |
|---|---|---|
| **축가** | 앉아서 듣는다 | 무해하다. 듣다가 잔을 든다 |
| **밸리**(와인·케이크) | 신랑신부가 **동작**을 한다 | ★케이크 커팅이 연달아 두 번이다 |

`_cakeDup` 가드가 이미 있지만 **경고만 띄우고 막지 않는다.** 그리고 실측하면 B가 이 위험을 축하 코스에 새로 만든다.

```
케이크 인접(밸리와 축배가 바로 붙는 조합) · 코스별
        담백  감동  가족  미니멀  축하   합계
MAIN      0    16    16    128      0    160
A         0     0     0    128     16    144
B         0     0     0     16     16     32
B′        0     0     0     16      0     16
```

B는 전체로는 160 → 32로 크게 줄이지만, **축하에서는 main에 없던 16조합을 새로 만든다.** A도 마찬가지다.

### 3-3. `festive` 오버라이드를 `song` 하나로 좁히면 전부 닫힌다

```js
festive:{song:80}     // valley:70을 뺀다
```

밸리는 전역 `55`를 그대로 써서 편지 앞에 남고, 축가만 `80`으로 올라가 편지 뒤에 남는다.

```
■ 축하 + 밸리
   MAIN 입장 첫인사 서약 반지 ★선언 밸리 ◆편지 축배
   B′   입장 첫인사 서약 반지 ★선언 밸리 ◆편지 축배   = main과 같음   ← (나) 해소

■ 축하 + 밸리 + 축가
   MAIN 입장 첫인사 서약 반지 ★선언 밸리 축가 ◆편지 축배
   B′   입장 첫인사 서약 반지 ★선언 밸리 ◆편지 축가 축배
        →  이완(밸리) · 정점(편지) · 이완(축가) · 밝은 착지(축배)
```

**네 §4-3 축하 근거가 그대로 산다.** 정점 → 이완(축가) → 여운(덕담) → 밝은 착지(축배). 밸리는 정점 앞으로 물러나 §4-4를 따르고, 축배와 떨어져 케이크가 겹치지 않는다.

```
B′   |  1112/1664     |     0쌍   | ✓닫힘 | ✓닫힘 |     16      | 전부 무변화
```

- **§4-4 위반 0쌍.** 축하·축가 예외를 빼면 전 코스 전 조합에서 이완이 정점 앞이다
- **(가)·(나) 둘 다 닫힌다.** 네가 준 셋 중엔 없던 결과다
- **케이크 인접 160 → 16.** 그 16은 전부 미니멀에서 부부가 밸리와 축배를 **손으로 둘 다 켠** 경우다(`입장 서약 반지 ★선언 밸리 축배`). 자동 배치가 만든 게 아니라 명시적 선택이고, `_cakeDup` 경고가 이미 뜬다
- **기본 상태 5코스 전부 main과 같다**

불변식도 B와 같다. A 대비 B′에서 이완 이동으로 설명 안 되는 조합은 **128개, 전부 담백 + 헌정** = (가)를 닫는 변화 자체다. 새로운 종류의 부작용 0.

역방향 검사도 했다. **정점(편지)이 끝에서 세 번째 안에 들어오는 비율**이다. 이완을 앞으로 당기면 정점이 너무 일찍 끝나 뒤가 늘어질 수 있어서 본 것인데, 반대였다.

```
MAIN 55.6%  ·  A 52.1%  ·  B 75.7%  ·  B′ 77.8%
```

정점이 **더 뒤로** 간다. 이완이 앞으로 빠지면서 정점 뒤에 남는 게 통합·착지뿐이 되기 때문이다. §4-4가 노린 그림 그대로다.

### 3-5. 축하 예외를 아예 없애면 어떻게 되는가 (검토했고 버렸다)

`RANK_OV.festive`를 통째로 빼는 안(문서에선 B3)도 돌렸다. 요약 지표는 B′와 **완전히 같다**(1112 / 0쌍 / ✓ / ✓ / 16). 그런데 48조합에서 헌정 자리가 갈린다.

```
B′  입장 첫인사 서약 반지 ★선언 ◆편지 헌정 축가 덕담 축배
B3  입장 첫인사 서약 반지 ★선언 ◆편지 축가 덕담 헌정 축배
```

B3는 축가가 `57`이라 헌정(`65`)보다 앞이 되고, **부모님 헌정이 축가·덕담 뒤 축배 직전까지 밀린다.** 편지에서 헌정으로 이어지는 흐름이 끊긴다. B′는 편지 바로 뒤에 헌정이 붙는다. **B′를 쓴다.**

## 4. 나머지 처리

### 4-1. `rankOf(k, dflt)` · 네 수정을 받는다

내 원안은 기본값을 하나로 뭉갰다. 네가 고친 게 맞다.

```js
function rankOf(k,dflt){ var o=(RANK_OV[S.course]||{}); if(o[k]!==undefined) return o[k];
  return RANK[k]!==undefined?RANK[k]:(dflt!==undefined?dflt:99); }
```

다만 실측 하나 덧붙인다. **`seq`·`opt`·`GADD`에 등장하는 순간 키 중 `RANK`에 없는 것이 현재 0개다.** 즉 기본값 분기는 지금 한 번도 실행되지 않고, 시뮬레이션으로는 99/0 차이가 드러나지 않는다. **그래도 네 수정이 맞다** — 새 순간을 `RANK` 등재 없이 추가하는 날 조용히 틀리는 걸 막는 미래 안전장치다. 그대로 둬라.

### 4-2. `_blessOpens()`의 `OFFTGL` 한 줄 · 받는다

`if(OFFTGL[k]&&!momOn(k)) continue;` — §0-4에서 적었듯 내가 검증 쪽에서 똑같이 빠뜨렸던 함정이다. 네 구현이 맞다.

### 4-3. 2-9는 네 B안으로

`MIN_BASE_TRIAD` 가드 대조 2건 추가(15 → 17항목). 내 A안은 전제가 틀렸다(§0-1).

### 5-1. ★덕담(rank 25)이 서약보다 앞에 온다 · 4안 공통

```
감동 + 덕담(팔레트)
   베일 입장 첫인사 덕담 서약 반지 ◆편지 헌정 ★선언      ← MAIN · A · B · C · B′ 전부 같다
```

`bless:25`가 `vow:30`보다 낮아서 생긴다. 부모님 덕담이 **두 사람의 서약보다 먼저** 나온다. 가족 코스는 덕담이 `seq` 붙박이 `at:2`라 의도된 배치지만, 다른 코스에서 팔레트로 켤 때도 같은 자리에 꽂히는 건 다른 문제다.

이번 결정과 독립이고(A/B/C/B′ 전부 동일), 고치려면 `bless`를 어디로 옮길지 따로 판단해야 한다. **다음 라운드로 넘긴다.**

### 5-2. 미니멀 케이크 인접 16조합

부부가 밸리·축배를 손으로 둘 다 켠 경우다. 자동 배치 문제가 아니라 선택 문제고 `_cakeDup` 경고가 이미 뜬다. **경고 문구가 "커팅이 두 번"이라는 걸 실제로 읽히게 쓰고 있는지만 한 번 봐 달라.** 고칠 게 있으면 그때 얘기하자.

### 5-3. 인쇄 식순지에 큐를 넣을지

네 §9 마지막 줄. 내 주장이 틀렸으니(§0-2) 이건 "고칠 것"이 아니라 "새로 할 것"이다. 별건 동의한다.

## 7. 이 회신이 확인하지 못한 것

- **`S.ord`가 있는 고객은 이 결정의 영향을 안 받는다고 가정했다.** `ordNow()`는 저장된 배열을 그대로 쓰고 `defaultOrd()`를 안 타므로 이론상 맞지만, 새 순간을 추가할 때 합류하는 경로는 코드로만 읽었다. 실측 아니다.
- **라이브 화면은 못 봤다.** `momentedit.kr:443`이 CONNECT 단계에서 403이다(네트워크 정책 · 토큰과 무관). 위 숫자는 전부 저장소 코드에서 뽑은 것이다.
- **`_cakeDup` 경고 문구를 읽지 않았다.** §5-2에서 너한테 넘긴 이유다.
- **B′의 1112조합 중 실제 고객이 도달하는 비중은 모른다.** 조합 수는 가능성이지 빈도가 아니다. 미니멀이 1024/1664를 차지하는 건 그 코스만 팔레트가 전부 열려 있어서고, 실제로 미니멀에 축가를 얹는 부부가 얼마나 되는지는 데이터가 있어야 안다. **가중치 없는 숫자로 읽어 달라.**
