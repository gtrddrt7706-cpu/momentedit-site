### 역전 1 (v0.2 · 유지) · 본체는 미리듣기가 아니라 **당일 콘솔**이다

- **실측: 당일 클립을 트는 수단이 저장소·문서 어디에도 없다.** `<audio>`/`new Audio` 사용처는 order-preview.html(샘플 1곡)·parents.html(어른 안내 1클립)뿐. 큐시트 30행은 "디렉터가 수동 '준비→발사'"라고만 적었고 **도구는 미정의.** 클립 파일명이 `01_`~`53_` 번호 체계인 것은 폴더 수동 재생을 암시하는 설계 흔적이다.
- 폴더 수동 재생으로 첫 예식을 치를 수는 있다(번호순 더블클릭). 그러나 그 방식엔 더킹(-6~-18dB 차등)·클립 간 1.5~2.5초 간격·N4~N6 브릿지 즉시 호출·고객 S 자동 로드가 전부 없다. **사고 복구 수단이 가장 필요한 순간에 도구가 가장 허술하다.**
- 판정: **콘솔이 첫 예식의 운영 필수품(본체)이고, 고객용 미리듣기는 같은 엔진의 자동 모드 스킨이다.**
- 폴더 수동 재생은 폐기가 아니라 **플랜 B(백업)로 강등**: 보조 기기에 번호 파일 폴더 상비.

### ★철회 · v0.2 '역전 2'(배역 AI 음성 제외 추천)를 **취소한다**

**2026-07-31 사용자 결정: 배역별 AI 음성 채택.** 아래는 철회 사유의 정직한 기록이다.

**1) 내 논거 하나가 사실이 아니었다 (실측 오류).**
v0.2 §1은 "실제 상품 구조는 나레이션만 녹음 · 사람 파트는 사람인데, 데모가 사람 파트까지 AI로 채우면 상품 구조를 데모가 거짓말하게 된다"고 썼다. **틀렸다.** 상품에 이미 당사자 목소리 트랙이 두 개 있다:

```javascript
// order-preview.html:416  기본값
guestVoice:'nar', entryVoice:'nar', ...
// order-preview.html:1501  ★'녹음·AI' 명시
return {n:'신랑·신부 입장', nar:eCouple?ENTRY[S.entry].self:ENTRY[S.entry].nar,
        self:eCouple?'두 분 목소리로 인사 (녹음·AI)':null, ...};
// order-preview.html:1595-1596  D-7 준비물
if(S.entryVoice==='couple') p.push(['D-7','입장 인사 녹음 파일 올리기(mp3/m4a)']);
if(S.guestVoice==='couple') p.push(['D-7','하객 맞이 안내 녹음 4개 올리기(mp3/m4a)']);
```

즉 `guestVoice='couple'`·`entryVoice='couple'`은 **하객 맞이 안내와 입장 멘트를 두 분 목소리로 바꾸는 판매 중인 옵션**이고, 코드가 그 수단으로 **AI 생성을 명시하고 있다.** 데모에서 당사자 목소리가 나오는 것은 상품 구조와 어긋나지 않는다 — 오히려 **이 두 옵션의 판매 도구**가 된다. 손님이 "두 분 목소리로 하면 이렇게 들리는구나"를 계약 전에 들어볼 수 있다.

**2) 내 대안(텍스트 카드만)은 목적을 못 이룬다.**
사용자 목적은 "흐름을 감으로 익히게 하기"인데, 사람 파트를 전부 화면 글자로 두면 클립 → 침묵 → 눈으로 읽기 → 클립이 반복된다. **미리'듣기'가 아니라 미리'읽기'가 되고, 흐름 체감이라는 목적 자체가 사라진다.** 시뮬레이션 실측상 본식의 86%가 사람·음악·침묵 구간이므로, 그 86%를 무음으로 두면 남는 건 14%뿐이다.

**3) 남는 리스크는 유효하되, 설계로 해소 가능하다.**
진짜 위험은 "AI가 읽는 것"이 아니라 **"AI가 신랑인 척 연기하는 것"**이다(오디오북 ↔ 드라마CD 차이). 사용자 원안의 표현도 "마치 오디오북처럼"이었다. → §2-B 안전장치 4개로 처리.

**4) 밈 필터 ×4 부담은 실재한다** → 순서로 해소: 나레이션 1종을 먼저 확정해 병목을 풀고, 배역 4종은 그 뒤에 태운다(§5).

## 2. 새 큰틀: 엔진 하나 · 쓰임 셋

```
[엔진] 클립 시퀀서
  입력: S(코스·옵션·순서) → curSeq() → 클립 목록
  재생: 순서 재생 · 클립 간 간격(1.5~2.5초) · BGM 트랙 + 자동 더킹
  폴백: 오디오 없는 클립은 텍스트 카드 + 무음 → 오디오가 0개여도 전체 작동

[쓰임 A · 본체] 당일 디렉터 콘솔 — 수동 모드 · 첫 예식 전 필수
  - 수동 '다음' 4곳(서약·반지·편지·덕담) = 큰 버튼 하나
  - N4~N6 브릿지(감정 대기·준비 대기·재개) 원터치 — 시뮬레이션 갭 1 해소
  - BGM 더킹 자동(순간별 -6~-18dB 차등 · 큐시트 수치 이관)
  - 고객 S 자동 로드 → 예식마다 큐 프로그래밍 0분
    ★배역 예시 클립은 당일 콘솔에서 재생하지 않는다(미리듣기 전용 트랙)
    — 단, guestVoice/entryVoice='couple' 고객의 실제 업로드 음원은 당일 재생 대상이다

[쓰임 B] 코스 기본형 미리듣기 — 자동 모드 + 코스 기본 S
[쓰임 C] 커스텀 미리듣기 — 자동 모드 + 고객 ritualDraft.S
```

### 2-A. 배역 음성은 '코스별 완성 mp3'가 아니라 **블록 단위 클립 라이브러리**다

이것이 v0.1과의 결정적 차이다. 코스별 완성본 3개를 만들면 커스텀(쓰임 C)에 대응할 수 없다 — 순서 축만 13,632조합이다. **나레이션 53클립과 똑같이 블록 단위로 쪼개 두면 엔진이 고객 S대로 조합 재생한다.** 사용자 원안의 "코스를 커스텀 완성하면 그거에 맞춰진 오디오북이 완성"을 실제로 충족시키는 유일한 방법.

발화 블록 실측(`order-preview.html:1500-1552` `self` 필드 기준) — 배역 클립 필요분:

| 블록 | 화자 | 클립 | 비고 |
|---|---|---|---|
| `guest`(guestVoice=couple) | 신랑·신부 | 4 | 상품 옵션 존재 · D-7 업로드 4개와 1:1 |
| `entry`(entryVoice=couple) | 신랑·신부 | 1 | 상품 옵션 존재 |
| `welcome` | 신랑·신부 | 2 | 항상 두 분 직접(고정 · `S.welcome='self'`) |
| `vow` | 신랑·신부 | 2 | 감정 정점 · 연기 절제 |
| `bless` | 아버님·어머님 | 2 | |
| `letter` | 신랑 or 신부 | 2 | 부모님께 / 서로에게 대표 1씩 |
| `tribute` | 신랑·신부 | 1 | 짧은 감사말 |
| `toast` | 대표 하객 | 1 | 건배사 |
| `declare`(ask/chorus) | **하객 군중** | 2 | ★AI 단일 보이스로 군중 불가 → §6 결정 7 |
| veil·ring·ringwarm·valley·song | — | 0 | 발화 없음(동작·음악) |

**합계 약 17개 · 총 ~1,000음절 ≒ 3.4분.** 나레이션 53클립(12.9분)의 26%.
v0.1이 상정했던 "코스별 완성 오디오북 3종 ≒ 24분"보다 **7분의 1**이다. 블록 분해가 제작량도 줄인다.

### 2-B. 안전장치 4개 (언캐니·오해 방지)

1. **화면 라벨 상시 표기** — 배역 클립 재생 중 화면에 `🎙 예시 목소리 · 당일엔 신랑님이 직접 말해요`. 나레이션 클립 재생 중에는 뜨지 않는다(대비로 구분).
2. **진입 시 1회 고지** — 미리듣기 시작 화면에 한 줄: "사람이 말하는 부분은 예시 목소리로 들려드려요. 당일엔 두 분과 가족이 직접 말합니다."
3. **연기 강도 하향** — 배역 음성은 **낭독톤**으로 수록한다(오디오북). 감정 연기·울먹임·과호흡 표현 금지. 특히 `vow`·`letter`는 절제할수록 언캐니가 줄고, 실제 당일의 감정을 데모가 미리 소진하지 않는다.
4. **예시 대사는 가상 인물 것만** — 시뮬레이션 코스A의 준호·세영·이만수 계열 문장을 재사용. **고객이 쓴 실제 문장은 어떤 경우에도 TTS 하지 않는다**(§1 유지 항목 4).

### 2-C. ★스크립트 표시 = 배지 2종 (2026-07-31 사용자 지시)

> 사용자 지시 verbatim: "신랑신부 부모님이 직접 대사하는 곳 그 외에 선택 가능한 부분들은 스크립트에 따로 표시를 해서, 고객이 '아 지금은 임의로 해놓은 거구나, 전체적으로 이런 느낌의 흐름이구나' 이해를 돕기 위함"

미리듣기 화면은 **지금 흐르는 구간이 어떤 성격인지**를 항상 배지로 알린다. 축이 둘이다.

| 배지 | 붙는 곳 | 문구(안) | 데이터 원천 |
|---|---|---|---|
| **① 예시** | 배역 클립 재생 중 | `예시 목소리 · 당일엔 두 분이 직접 말해요`<br>`예시 목소리 · 당일엔 아버님이 직접 말씀하세요` | §2-A 발화 블록 표 |
| **② 선택** | 옵션 있는 블록 | `여기는 고를 수 있어요 · 넣기 / 빼기` | ★**`COURSES[].seq[].pick` 이미 존재** |
| (무배지) | 나레이션 클립 | — | 대비로 "이건 저희가 준비하는 부분"이 읽힘 |

**②의 데이터는 새로 쓸 게 없다.** `order-preview.html`의 코스 정의에 `pick` 문구가 이미 전 블록에 깔려 있다 — 실측 16종:

```
입장 멘트 느낌 6가지 중 선택 / 넣기 / 빼기 / 울컥하면 배우자가 대신 /
부모님께 / 서로에게 / 나레이션 / 하객 응답 / 가족 낭독 / 인사말 준비 /
꽃 헌정 / 큰절 / 포옹 / 한 분 대표 / 양가 각각 / 축배 / 케이크 / 둘 다 /
어머니 / 아버지 / 가까운 분 / 생략 / 가족만 / 전체 하객
```

미리듣기 스크립트가 이 값을 그대로 물려받으면 **코스 카드와 미리듣기가 같은 원천을 쓰므로 문구가 어긋날 수 없다**(`build-dubbing-script.mjs`의 동기 보증과 같은 원칙).

효과: 사용자 발단 메시지의 두 목적이 배지 하나씩을 가져간다 — **①이 "이미지 트레이닝"**(어디가 내 차례인지 몸으로 익힘)을, **②가 "코스 정하기 이해"**(어디를 바꿀 수 있는지 보임)를 담당한다.

표기 규칙: 배지는 **이모지 없이 텍스트로**(CLAUDE.md 이모지 최소 규칙) · 전각 줄표 금지 · 호칭은 "두 분"·"하객분들".

콘텐츠 3트랙:

- **트랙 1 · 텍스트 장면 레이어** — 지금 · 0원 · 내 몫. 나레이션 문안은 `ritual-data.js`에서 자동 추출(신규 `scripts/build-course-story.mjs`), 지문·장면만 저작. 코스 B·C 집필이 미작성 런북 B·C 초안을 겸한다.
- **트랙 2 · 나레이션 53클립** — 목소리 A/B 확정 후. 완성되는 대로 클립 단위로 꽂힌다.
- **트랙 3 · 배역 예시 클립 ~17개** — 나레이션 확정 후 착수. 미리듣기 전용.

## 3. 당일 신뢰성 원칙 (콘솔 요구사항 · CC 구현 시 승계)

- **오프라인 우선**: 음원·코드 사전 로드. 리허설 때 **기내모드로 1회 완주** 테스트 통과해야 실전 투입.
- **자동재생 정책**: 브라우저 오디오는 첫 터치 후 해제 — 개식 전 디렉터가 콘솔을 한 번 터치하는 절차를 운영 순서에 명시.
- **백업 2중**: 보조 기기에 콘솔 + 번호 파일 폴더(플랜 B) 상비.
- **화면 꺼짐 방지**: Wake Lock.
- **트랙 분리**: 콘솔 로드 대상에서 트랙 3(배역 예시)을 제외해 당일 오발사를 원천 차단.

### 3-A. ★콘솔 조작 사양 — 2트랙 분리 · 자동 더킹 + 수동 오버라이드 (2026-07-31 사용자 질문 대응)

**사용자 제안**: "BGM 순서대로 따로 · 나레이션 순서대로 따로 · 버튼 눌러 타이밍 맞춰 소리 줄이고 높이고".
**판정: 트랙 분리는 채택. 상시 수동 볼륨은 기각. 대신 수동 전용 큐 버튼 4개를 얹는다.**

**① 2트랙 분리 = 맞다 (큐시트 실측이 뒷받침).**
큐시트 순간별 표 11행이 순간마다 **다른** BGM(무드·BPM·편성)을 요구하므로 BGM은 한 곡이 아니라 **장면별 재생목록**이다.
결정적 근거는 두 트랙의 **전환 시점이 어긋난다**는 것 — 큐시트 14행 "반지·링워밍 … 성혼선언 직전 **음악 페이드아웃 시작**"은
나레이션이 아직 반지 구간을 진행 중인데 음악만 먼저 움직이라는 지시다. 한 타임라인으로는 표현 불가 → **독립 2트랙이 강제된다.**

**② 상시 수동 볼륨 = 기각.**
- 큐시트 23행이 이미 "**더킹은 자동(사이드체인) · 수동 볼륨 편집 불필요**"로 못박음.
- 손 부족: 시뮬레이션 코스A 실측상 디렉터 조작이 이미 **27회**(클립 발사 17 + 수동 '다음' 4 + 비언어 유도 2 + 발화 4). 클립마다 내리고 올리면 3배로 뛴다.
- 재현성: 더킹 페이드는 **다운 0.3~0.5초 / 복귀 0.8~1.5초**(큐시트 25행). 손으로 이 곡선을 53회 동일하게 그릴 수 없다. 한 번 어긋나면 말이 묻히거나 음악이 뚝 끊긴다.

**③ 그러나 자동으로 표현 불가능한 큐가 4개 있다 — 여기가 사용자 직관이 옳은 지점.**
자동 더킹은 "말이 있을 때 내린다"만 할 수 있다. 아래는 전부 **말이 없을 때 음악을 움직이라**는 지시라 트리거가 없다.

| # | 큐 | 큐시트 근거 | 전용 버튼 |
|---|---|---|---|
| 1 | 성혼선언 앞 **완전 침묵 2~3초** | 15행 | **음악 끊기** (즉시 페이드아웃) |
| 2 | 선언 직후 **음악 하드 인** | 15행 | **음악 넣기** (하드/소프트 2단) |
| 3 | 편지 낭독 중 **완전 정지 → 절정 문단에만 조용히 재진입** | 17행 | **더킹 홀드** ("지금 여기 유지" — 사람 낭독 중 자동 복귀 금지. 오열·중단 30초도 이걸로 흡수) |
| 4 | 폐식 **롱 페이드아웃 · 하드 스톱 금지** | 20행 | **롱 페이드아웃** (1회 누르면 20~30초 자동 하강) |

→ **콘솔에 필요한 건 볼륨 노브 여러 개가 아니라 큰 버튼 4개 + BGM 마스터 슬라이더 1개.**
평상시엔 손을 안 대고(자동), 위 4순간에만 사람이 개입한다. 조작 증가분은 예식당 **+4~6회**.

**④ 기계 — 소프트웨어는 자체 제작, 입력 장치만 기성품.**
QLab(공연 큐 표준 · macOS 전용 · 무료 티어 있음) 등 기성 큐 재생기는 **예식마다 큐를 손으로 다시 프로그래밍**해야 한다.
우리는 순서 축만 13,632조합이고 고객 S가 이미 저장돼 있으므로, **S를 읽어 큐를 자동 생성하는 것**이 자체 엔진의 존재 이유다. 이건 기성품으로 대체 불가.
