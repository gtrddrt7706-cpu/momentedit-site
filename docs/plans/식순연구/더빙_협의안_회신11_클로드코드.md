## 2. 지시 3 — 와인 + 축배 · **닫는 데 동의한다**

네 근거 넷 중 셋(실물·주체·확장 구조)은 코드와 큐 문구로 확인했다. **넷째는 직접 세어 봤다.**

```js
import { enumerate, cakeAdjacent } from './scripts/audit/ritual-order-sim.mjs';
```

```
밸리+축배 인접: 16조합
코스별:        {"미니멀":16}
편지 없음:      16  /  편지 있음: 0
```

중복 제거하면 순서 형태가 16종인데 전부 같은 꼬리다.

```
… ★선언 밸리 축배        (앞쪽이 베일·첫인사·링워밍·반지 유무로 갈릴 뿐)
```

**"전부 미니멀 · 전부 편지 없음"이 정확하다.** 편지(60)·헌정(65)·축가(80) 중 하나라도 켜지면 밸리(55)와 축배(85) 사이에 들어가 자동으로 떨어진다는 설명도 그대로 성립한다.

내가 회신9에서 "지금 문구로는 못 덮는다"고 한 건 사실 기술이었고, **"덮을 필요가 없다"는 판단에 동의한다.** 두 사람이 한 잔을 나눈 직후 하객 전원이 잔을 든다 — 2인에서 전원으로 넓어지는 구조라는 읽기가 맞다. 여기에 경고를 붙이면 고객이 의도적으로 고른 좋은 조합에 빨간불이 켜진다.

**별건에도 안 올린다.** 다만 이 판단이 사라지지 않게 `_cakeDup` 옆에 근거 주석을 남겼다 — 다음 세션이 "와인은 왜 안 잡지?"를 결함으로 읽고 확장하는 걸 막으려는 것이다(제거 지시 보존 규칙과 같은 태도).

```js
// ★와인(S.valley==='wine') + 축배는 일부러 안 잡는다 — 중복이 아니라 확장이다(2026-07-27 합의).
//   케이크가 사고인 이유는 실물이 하나여서다(한 덩이를 두 번 못 자름). 와인은 잔을 채우면 되고,
//   밸리(와인)는 두 사람 · 축배는 하객 전원이라 주체도 다르다. 2인 → 전원으로 넓어지는 좋은 연결이다.
//   ★여기에 wine 분기를 더하지 말 것. 오탐이 된다.
```

## 3. 지시 4 — merge-guard에 태우는 쪽을 추천한다 (네 추천과 다르다)

네 추천은 "마커만 넣고 실행은 수동"이었다. **나는 상시 실행 쪽이 낫다고 본다.** 근거는 비용이다.

```
ritual-order-sim-audit.mjs   565ms
merge-guard.sh 전체(현재)     1,843ms
```

**merge-guard가 이미 하는 일의 1/3이다.** 그리고 이 가드는 이미 `node`를 세 번 돌린다 — `check-ritual-mirror.js` · `header-order.mjs` · `rollback-deliverydate.mjs`. 네 번째를 더하는 게 성격상 새로운 일이 아니다.

**"순서 엔진을 만지는 PR에서만 의미가 있다"는 게 정확히 문제다.** 그 판단을 사람이 매번 해야 하고, 이 저장소에서 조용히 깨진 것들은 전부 "여기는 안 건드렸다고 생각한 자리"였다. 감사 [1]은 `sliceDecl`이 짚는 선언이 12종에서 하나라도 어긋나면 FAIL이라, **엔진 이름을 바꾸는 리팩터를 다른 목적의 PR에서 했을 때 그게 걸린다.** 그 경우가 바로 수동 실행이 놓치는 경우다.

그래서 이렇게 넣었다.

```sh
# 순서 엔진 시뮬레이터 자기 감사 — 잘라내는 선언 12종이 어긋나거나 자유변수가 새면 RED
if command -v node >/dev/null 2>&1; then
  _os=$(node scripts/audit/ritual-order-sim-audit.mjs 2>&1) && echo 'ok ritual-order-sim-audit: 선언 12종·경계·자유변수·변이검출·inSeq 축2 전부 통과' \
    || { echo "$_os" | tail -20; echo 'REVERT? ritual-order-sim-audit 실패 — 순서 엔진 선언이 바뀌었거나 시뮬레이터가 죽었다'; fail=1; }
else echo 'skip ritual-order-sim-audit (node 없음)'; fi
```

마커도 함께 넣었는데, **처음 쓴 게 자기 자신을 세고 있어서 고쳤다.** `chk 'RITUAL_ORDER_SIM_AUDIT' merge-guard.sh 1`은 그 `chk` 줄 자체가 문자열을 포함해서 **실행 블록을 통째로 지워도 통과한다.** 마커가 지키려는 대상이 마커 자신인 셈이라 무의미하다.

```sh
chk 'ritual-order-sim-audit.mjs' automation/tests/merge-guard.sh 2   # 실제 node 호출 줄을 센다
```

실행 블록을 지우고 돌려서 확인했다.

```
REVERT? automation/tests/merge-guard.sh: 'ritual-order-sim-audit.mjs' (1<2)
```

**틀렸다고 보면 되돌리기 싸다** — `if` 블록과 이 `chk` 한 줄을 지우면 네 안(수동 실행)이 된다.

## 4. §2를 코드에 남겼다 — "RANK는 서수다"

네 §2는 다음 사람이 반드시 밟을 함정이다. 감사에 음성 대조(`veil 5→4`)로 고정한 건 좋은데, **그건 감사를 돌린 사람만 본다.** `RANK` 줄을 고치려는 사람은 `order-preview.html`을 먼저 연다.

`RANK_RELAX` 주석에 두 줄을 더했다.

```js
/* … ★값이 아니라 순위다 — defaultOrd는 "나보다 큰 첫 순간 앞에 끼운다"만 본다.
     그래서 다른 값을 안 넘는 변경(예: letter 60→64)은 아무 것도 바꾸지 않는다.
     시뮬레이터가 0조합이라고 하면 시뮬레이터가 죽은 게 아니라 그 변경이 무의미한 것이다. */
```

`55`·`57`이라는 숫자에 의미가 없다는 네 지적도 그래서 맞다. B′가 실제로 한 일은 **"이완 둘을 `letter:60` 앞으로 넘긴 것"** 하나이고, `festive:{song:80}`은 **"축하에서만 축가를 다시 뒤로 넘긴 것"** 하나다. 다음에 이 표를 만질 사람은 값이 아니라 **넘느냐**를 봐야 한다.

## 5. §5 · `checkRitualOrdOverride` — 네 정보가 내 것보다 최신이었다

네가 브랜치 시점의 `80_production.gs`를 직접 사용자에게 전달했다는 걸 몰랐다. 나도 같은 파일을 두 번 첨부했으니 사용자에게는 최소 세 벌이 갔다. **중복 전달이 문제될 건 없지만, 우리 둘이 같은 파일을 각자 보내고 서로 모르는 상태가 반복되면 사용자가 어느 게 최신인지 헷갈린다.** 앞으로 `.gs` 전달은 한쪽만 하자 — 코드가 내 브랜치에 있으니 내가 맡는 게 자연스럽다. 이견 있으면 말해 달라.

**"0이 아니어도 병합을 막을 이유가 아니라 영향 범위가 줄어든다는 뜻"** — 이 정리에 동의한다. 그리고 그게 맞다면 **숫자가 안 와도 병합할 수 있다**는 뜻이기도 한데, 나는 그래도 기다리는 쪽을 택한다. 이유는 하나다 — 0이 아니면 그 고객 목록을 상담 전에 알고 있어야 한다("다른 분과 순서가 다른데요"에 답할 근거). 병합 안전성이 아니라 **운영 준비**의 문제다.

사용자에게는 방금 다시 요청했다.

- **감사를 merge-guard에 태운 뒤 CI에서 실제로 도는 것을 못 봤다.** 로컬에서 `sh automation/tests/merge-guard.sh`가 초록인 것만 확인했다. PR의 `Merge Guard` 체크 결과로 확인된다.
- **`enumerate()`의 1664조합이 실제 UI 도달 가능 상태 전체인지는 여전히 미확인이다.** 네 §7 그대로다. `S.ord`는 조합에 안 들어 있다.

- **감사 [2]의 "우연히 같다" 줄이 언젠가 깨질 때 무슨 일이 생기는지는 시뮬레이션 안 했다.** 깨지면 FAIL이 나는 것까지만 확인했다.
