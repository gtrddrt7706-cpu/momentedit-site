# 식순 전체 구조 검토 · 코워크

작성 2026-07-26 (코워크) · 기준 `origin/main` = `1840932`
대상: `assets/ritual-data.js`(COURSES·MIN·사전 12종) + `order-preview.html`(빌더 엔진 596~675 · BLOCK 1370~1425 · estMin 1437) + 근거 문서 6종

지금까지 검토는 **더빙 대본(53클립) 문안**에만 붙어 있었다. 이 문서는 그 한 층 위, **식순 자체의 짜임**을 본다. 코스 5종이 각각 어떤 감정 곡선을 그리는지, 순간을 넣고 뺄 때 그 곡선이 유지되는지, 코드가 확정 문서대로 도는지를 실측으로 확인했다.

## 0. 먼저 정정한다 — 내가 이전에 "의심"으로 올린 것 중 절반이 틀렸다

이전 구간에서 구조 이슈 후보를 몇 개 적어 두고 사용자에게 아직 보고하지 않았다. 코드를 끝까지 읽고 나니 **그중 상당수가 내 오독이었다.** 보고 전에 잡아서 다행이고, 무엇이 왜 틀렸는지를 남긴다.

| 내가 의심했던 것 | 실측 결과 |
|---|---|
| 담백 코스만 카드(7개)와 엔진(9개)이 어긋난다 | **틀렸다.** `bless`·`valley`는 `seq`에 있지만 `OFFTGL`+`momOn()` 경로로 기본 OFF다(`S.bless='off'` · `S.valley='none'`). `BLOCK.bless`/`BLOCK.valley`가 OFF일 때 `null`을 반환해 `fullBlocks()`에서 빠진다. 기본값 실제 진행 = 입장·첫인사·서약·반지·선언·편지 + 폐식 = **정확히 7개.** 다섯 코스 전부 `flow` 개수와 기본 진행 개수가 일치한다 |
| 성혼선언 위치가 3:2로 갈리는 건 사고다 | **틀렸다. 의도다.** 런북_코스A "★성혼선언은 중반 유지·덕담으로 마무리(담백 확정)" · 코스설계_v1 코스B·C "편지낭독 → 부모님 헌정(정점) → 성혼선언(하객 합송)". 두 문법이 문서로 확정돼 있다 |
| `MIN.XM`의 `bless:0`·`valley:0`이 `delta`와 모순 | **틀렸다.** `estMin()` 주석이 직접 설명한다 — "valley/bless는 위 델타가 처리해 0". 이중 계산 방지다 |
| `seq`에 있는데 `flow`에 없는 항목(폐식·guest)이 비대칭 | **틀렸다.** `momMove` 주석이 명시 — "하객 맞이(식전 안내)는 맨 위 고정 · 폐식은 목록 밖 고정". `seq`는 엔진, `flow`+`detail`은 코스 선택 카드 소개용이라는 이원 구조다 |

원인은 하나다. **`seq`만 보고 화면을 추정했다.** 이 빌더는 순서 목록(`seq`)과 켜짐 상태(`S.*` + `OFFTGL`)가 별개 축이고, 실제 진행은 두 축의 곱이다. 이 구조를 놓치면 "기본값에 9개가 강제된다"는 정반대 결론이 나온다.

아래 §2부터는 이 구조를 반영해 다시 판정한 것만 적는다.

## 1. 코스 5종 짜임 · 실측 기준 전체 지도

기본값(`applyCourse()` 직후, 아무것도 안 건드린 상태)으로 실제 진행되는 순서다. 괄호는 코스에 들어 있지만 기본 OFF라 화면에 회색으로 보이는 순간.

```
담백 25분 · 7순간
  입장 ─ 첫인사 ─ 서약 ─ 반지 ─ 성혼선언 ─ 편지◆ ─ (밸리) ─ (덕담) ─ 폐식
  ▁▂▃▄▆█▁                              ↑정점이 마지막 순서
  여운 담당: 폐식 나레이션(CLOSE_NAR) 단독

미니멀 18분 · 5순간
  입장 ─ 서약 ─ 반지 ─ 성혼선언 ─ 폐식        [첫인사·편지·덕담은 선택]
  ▁▃▄▅▁                                  ↑정점 표식 없음(letter가 없어 peak:true 블록 부재)

감동 29분 · 9순간
  베일 ─ 입장 ─ 첫인사 ─ 서약 ─ 반지 ─ 편지◆ ─ 헌정 ─ 성혼선언(하객 응답) ─ 폐식
  ▂▃▄▅▄█▇▆▁                                  ↑정점    ↑통합    ↑착지

가족 30분 · 9순간
  입장 ─ 덕담 ─ 서약 ─ 링워밍 ─ 반지 ─ 편지◆ ─ 헌정 ─ 성혼선언(가족 낭독) ─ 폐식
  ▂▄▅▄▄█▇▆▁                                 ↑정점    ↑통합    ↑착지

축하 30분 · 8순간
  입장 ─ 첫인사 ─ 서약 ─ 반지 ─ 성혼선언 ─ 편지◆ ─ 축배·케이크 ─ 폐식
  ▃▄▄▄▆█▆▁                              ↑정점    ↑밝은 착지
```

**두 개의 문법이 있다.** 담백·미니멀·축하는 **선언 중반형**(성혼선언을 공식 절차로 중간에 두고 감정 정점을 뒤에), 감동·가족은 **선언 종반 통합형**(감정 정점을 먼저 쓰고 성혼선언으로 착지). 이 구분이 코드 전반의 판단 기준이 되므로 이 문서에서는 계속 이 이름으로 부른다.

두 문법 다 연구2 아크(정점 65~85% 지점, 끝은 정점보다 한 톤 낮은 정돈된 벅참)를 만족한다. 문제는 문법이 두 개인데 **코드에 그 사실을 아는 곳이 한 군데도 없다는 것**이다. 아래 §2-1이 그 결과다.

### 코스 간 변별력

| | 시작 | 정점 | 착지 | 고유 시그니처 |
|---|---|---|---|---|
| 담백 | 첫인사 | 편지 | 폐식 나레이션 | (없음 · 뺀 것이 성격) |
| 미니멀 | 입장 직행 | 서약 | 성혼선언 | 최단 |
| 감동 | 베일 다운 | 편지 | 하객 응답형 선언 | 베일 + **하객이 함께 답하는 선언** |
| 가족 | 부모님 덕담 | 편지 | 가족 낭독 선언 | 덕담 개식 + 링워밍 |
| 축하 | 첫인사 | 편지 | 축배·케이크 | 축배 |

**감동과 가족이 구조적으로 가장 가깝다.** 둘 다 9순간, 둘 다 편지 정점, 둘 다 헌정, 둘 다 선언 종반 통합형. 실제 차이는 시작 한 순간(베일 vs 덕담)과 링워밍뿐이다. 그런데 감동의 `addable` 문구는 "베일 다운·부모님 헌정이 이 코스의 시그니처예요"라고 적혀 있어 **헌정을 시그니처로 내세운다. 헌정은 가족 코스에도 그대로 있어서 변별이 안 된다.**

감동의 진짜 고유값은 `COURSE_DEF.gamdong.declareWho='ask'` — 하객 응답형 성혼선언이다. 다섯 코스 중 감동에만 기본으로 붙는다. 카피를 이쪽으로 옮기는 편이 정확하다.

> 제안 문구 · `COURSES.gamdong.addable`
> 현재: `베일 다운·부모님 헌정이 이 코스의 시그니처예요.`
> 제안: `베일 다운으로 열고, 하객분들이 함께 답하는 성혼 선언으로 닫는 코스예요.`

## 2. 확정 이슈와 제안

### 2-1. ★근본 원인 · `RANK`가 문법 하나만 안다 (5개 이슈의 공통 뿌리)

`RANK={guest:0, veil:5, entry:10, welcome:20, bless:25, vow:30, ringwarm:35, ring:40, declare:50, letter:60, tribute:65, valley:70, song:80, toast:85}`

이 표는 팔레트("이 코스에 없는 순서 더하기")로 더한 순간이 어디에 끼어 들어갈지를 정한다. 삽입 규칙은 `defaultOrd()` 안:

```js
for(var i=0;i<s.length;i++){ if((RANK[s[i]]||0) > gr){ pos=i; break; } }
```

**`declare:50`이 `letter:60`보다 앞이다.** 즉 이 표는 선언 중반형 문법 하나만 인코딩하고 있다. 그런데 감동·가족은 `declare`가 마지막 순서다. 결과:

| 코스 | 팔레트로 더할 수 있는 순간 | 실제로 끼는 자리 |
|---|---|---|
| 감동 | 밸리(70)·축가(80)·축배(85) | **전부 성혼선언 뒤 = 맨 끝** |
| 가족 | 밸리(70)·축가(80)·축배(85) | **전부 성혼선언 뒤 = 맨 끝** |

감동 코스에서 부부가 "분위기 전환이 필요해서" 케이크를 더하면, 케이크가 끼는 자리는 **하객 전원이 함께 답한 성혼선언 바로 다음, 폐식 직전**이다. 착지를 만들어 놓고 그 뒤에 케이크를 자른다. 연구2 안티패턴 3(유쾌로 끝맺음 → 여운 없이 단체촬영 진입)에 정확히 해당한다.

축가는 더 나쁘다. 축가는 이완 소재인데 이완이 필요 없는 맨 끝에 놓인다.

**제안 · 코스별 랭크 오버라이드 한 줄**

```js
// ★RANK_OV — 선언 종반 통합형 코스(감동·가족)는 성혼선언이 마지막 본식 순서다.
//   팔레트로 더한 순간이 그 뒤로 밀리면 착지를 넘어가 버린다.
//   84로 두면 축배(85)만 선언 뒤에 남고(연구1 클로징 배치), 밸리·축가는 선언 앞으로 들어온다.
var RANK_OV={gamdong:{declare:84}, family:{declare:84}};
function rankOf(k){ var o=(RANK_OV[S.course]||{}); return o[k]!==undefined?o[k]:(RANK[k]!==undefined?RANK[k]:99); }
```

`defaultOrd()`의 `RANK[g]` · `RANK[s[i]]` 두 곳을 `rankOf(...)`로 바꾸면 끝난다. 담백·미니멀·축하는 오버라이드가 없어 동작 무변화.

검산(감동에 팔레트로 더했을 때):

```
밸리(70)  → declare(84) 앞    …편지 ─ 헌정 ─ 밸리 ─ 성혼선언 ─ 폐식
축가(80)  → declare(84) 앞    …편지 ─ 헌정 ─ 축가 ─ 성혼선언 ─ 폐식
축배(85)  → declare(84) 뒤    …헌정 ─ 성혼선언 ─ 축배 ─ 폐식
```

세 경우 다 연구2 아크(정점 → 이완 → 통합 착지, 또는 착지 → 밝은 마무리)와 맞는다.

### 2-2. ★담백 · 밸리가 예식 맨 끝에 있다

```
현재  seq: guest, entry, welcome, vow, ring, declare, letter, bless, valley
확정 문서: 혼인서약 → 반지교환 → 성혼선언 → [밸리 슬롯] → 편지낭독 → 부모님 덕담
          (코스설계_v1 코스 A 본문)
큐시트  : 성혼선언 → 와인·케이크("편지 전 톤 낮추며 정돈") → 편지 낭독(정점) → 헌정·덕담
          (더빙_연출_큐시트 2026-07-20)
```

문서 두 개가 밸리를 **편지 앞**에 두라고 한다. 코드는 **덕담 뒤, 예식 맨 끝**에 둔다.

기본값에서는 밸리가 OFF라 드러나지 않는다. 하지만 담백의 `addable`은 고객에게 이렇게 말한다 — "원하면 와인 세리머니·케이크 커팅·부모님 덕담을 더할 수 있어요." 순서 조정 화면에서 버튼 한 번이면 켜진다. 둘 다 켜면:

```
성혼선언 ─ 편지◆ ─ 덕담 ─ 와인/케이크 ─ 폐식
                          ↑ 예식이 케이크 커팅으로 끝난다
```

**제안 · `seq` 두 항목의 자리만 바꾼다**

```js
// 현재
seq:['guest','entry','welcome','vow','ring','declare','letter','bless','valley']
// 제안
seq:['guest','entry','welcome','vow','ring','declare','valley','letter','bless']
```

- 기본값 결과 무변화(밸리·덕담 둘 다 OFF → 7순간 그대로)
- 밸리만 켜면 `성혼선언 → 밸리 → 편지` = 큐시트와 정확히 일치
- 둘 다 켜면 `성혼선언 → 밸리 → 편지◆ → 덕담 → 폐식` = 코스설계_v1 코스 A 본문과 정확히 일치
- 부수 효과로 순서 조정 화면에서 회색 "사이 순서"가 선언과 편지 사이에 보이게 된다. 부부가 스크롤하다 "여기에 숨 고르는 자리가 있구나"를 자연스럽게 배운다

`BLOCK.bless`의 큐가 이미 `'편지 뒤라 한 톤 낮춰 따뜻하게(정점 반복 아님)'`라고 적혀 있다. 즉 **코드 자신이 덕담을 편지 뒤 여운으로 전제한다.** 지금 구조도 그 점은 맞다. 어긋난 건 밸리 하나다.

### 2-3. ★감동 · 밸리 `at:9`도 같은 문제

```js
opt:[{k:'valley', at:9}]   // seq 길이가 9라 splice(9) = 맨 끝
```

코스설계_v1 코스 B는 `반지교환 → [밸리: 케이크] → 편지낭독`이다. `seq` 인덱스로 `ring`은 5, `letter`는 6이므로 **`at:6`**이 그 자리다.

```js
opt:[{k:'valley', at:6}]
```

결과: `베일 → 입장 → 첫인사 → 서약 → 반지 → 밸리 → 편지◆ → 헌정 → 성혼선언 → 폐식`

`OPTWHY.gamdong.valley`가 "감정 흐름이 끊기지 않도록 기본에서 빼 뒀어요 · **분위기 전환이 필요하면 더해요**"라고 안내한다. 전환이 필요한 지점은 서약·반지의 절차 구간에서 편지의 감정 구간으로 넘어가는 경계지, 이미 다 끝난 맨 끝이 아니다.

§2-1의 `RANK_OV`를 적용하면 팔레트 경로는 자동으로 고쳐지지만, `opt`의 `at`은 별도 경로라 이 한 글자를 따로 바꿔야 한다.

### 2-4. ★축하 · `opt at:6,6`이 감동 2연타를 만들고 큐 문구까지 틀리게 한다

```js
festive.opt = [{k:'song', at:6}, {k:'bless', at:6}]
```

`defaultOrd()`의 삽입은 `s.splice(Math.min(o.at+i, s.length), 0, o.k)` — 이미 넣은 개수 `i`로 인덱스를 보정한다. 그래서 둘 다 켜면 song이 6, bless가 7에 들어가고 실제 전개는 이렇게 된다.

```
성혼선언 ─ 축가 ─ 덕담 ─ 편지◆ ─ 축배 ─ 폐식
           이완    감동    감동
```

문제 두 가지.

**하나. 덕담(감동) 바로 뒤에 편지(감동).** 연구2 안티패턴 4 "눈물 이벤트 연속 → 감정 소진·피로". 그리고 이완 소재인 축가가 두 감동 앞에 낭비된다.

**둘. 큐 문구가 화면에서 사실과 어긋난다.** `BLOCK.bless`는 가족 코스가 아닐 때 이 큐를 출력한다.

```
나레이션 소개 → 부모님께 마이크 전달 · 말씀 끝나면 다음 · 편지 뒤라 한 톤 낮춰 따뜻하게(정점 반복 아님)
```

축하 코스에서는 덕담이 **편지 앞**인데 큐는 "편지 뒤라"고 말한다. 이 큐는 화면뿐 아니라 부부가 뽑는 인쇄 식순지에도 들어간다. 미니멀은 `bless at:6`이 편지(`letter at:5`) 뒤에 오도록 계산돼 있어 정상이다. **다섯 코스 중 축하 하나만 어긋난다.**

**제안 · `at` 두 글자**

```js
opt:[{k:'song', at:7}, {k:'bless', at:7}]
```

결과: `성혼선언 → 편지◆ → 축가 → 덕담 → 축배 → 폐식`
정점(편지) → 이완(축가) → 여운(덕담) → 밝은 착지(축배). 연구2 아크와 일치하고, 덕담 큐의 "편지 뒤라"도 사실이 된다.

**추가 제안 · 큐를 위치 기반으로 바꾼다.** `at` 수정만으로는 팔레트 경로가 안 덮인다. 감동 코스에 팔레트로 덕담을 더하면 `RANK[bless]=25`라 서약 앞으로 들어가고, 큐는 여전히 "편지 뒤라"를 출력한다. 코스가 아니라 **실제 위치**를 보게 하면 모든 경우가 한 번에 닫힌다.

```js
// 현재: famOpen(=코스가 가족인가)로 분기
// 제안: 실제 순서상 편지보다 뒤인가로 분기
var _o=ordNow(), _afterLetter = inSeq('letter') && _o.indexOf('bless') > _o.indexOf('letter');
```

`_afterLetter`가 참일 때만 "편지 뒤라 한 톤 낮춰", 거짓이면 "예식의 문을 여는 말씀" 계열 큐. 부부가 ↑↓로 순서를 직접 바꿀 수 있는 빌더라 위치 기반이 원래 맞다.

### 2-5. 가족 · 첫인사 `at:3` — 이건 판단이 필요하다 (내 단정 보류)

```js
family.opt = [{k:'welcome', at:3}]
// 켜면: 입장 → 덕담 → 첫인사 → 서약
```

코스설계_v1의 공통 자물쇠는 `입장 → 환영·첫인사 → [본문] → 폐식`이고, 런북_코스A도 `2. 환영·첫인사 (자물쇠·고정)`이라고 못박았다. 그 기준이면 `at:2`여야 한다.

**그런데 반대 근거도 코드 안에 명시돼 있다.**

```js
OPTWHY.family.welcome = '이 코스는 부모님 덕담이 예식의 문을 열어서, 첫인사는 겹치지 않게 선택으로 뒀어요'
BLOCK.bless(famOpen) = '오늘 예식의 문은, 두 사람을 가장 오래 지켜봐 오신 부모님의 말씀으로 엽니다.'
```

가족 코스는 **의도적으로 덕담을 개식으로 쓴다.** `at:2`로 옮기면 "덕담이 문을 연다"는 서사가 깨진다. 이건 버그가 아니라 두 확정 문서가 서로 다른 말을 하는 지점이다.

**내 추천은 `at:2`다.** 이유는 하객 체험 쪽이다. 신랑신부가 걸어 들어와 자리에 서고, 하객이 처음 듣는 사람 목소리가 부모님이고, 정작 주인공 두 사람은 2분쯤 지나서야 첫마디를 한다. 25명 규모의 가까운 자리에서는 이 공백이 어색하게 읽힐 수 있다. `at:2`로 옮겨도 덕담은 여전히 예식 본문의 첫 순서(서약 앞)라 "가족이 문을 연다"는 성격은 유지된다.

다만 **되돌리기가 싼 변경이 아니다** — 확정 문서 한쪽을 무효화하는 판단이므로, 병합 검증 규칙 6번대로 사용자 결정을 받고 가는 게 맞다. 결정 대기함 항목으로 올리기를 제안한다.

### 2-6. 감동 · 베일 다운 선택지가 카드에서 하나 빠져 있다

```
VEIL 사전:            mother / father / close / skip           (4종)
실제 선택 UI(1229~1232): 어머니 / 아버지 / 가까운 분이 / 생략   (4종 ✓)
```

`VEIL.close.nar`은 이미 완성돼 있고("가장 가까운 사랑이 신부의 베일을 내립니다"), 더빙 대본 53클립에 `G6-close`(37번 · 47음절)로 **녹음 대상에 살아 있다.** 녹음은 하는데 카드에서 안 보인다.

> 제안 · `COURSES.gamdong.detail[0]`
> `how`: `문이 열리기 직전, 어머니나 아버지가(또는 가장 가까운 분이) 신부의 베일을 내려 주고 두 분의 손을 이어 줘요.`
> `pick`: `어머니 / 아버지 / 가까운 분 / 생략`

`assets/ritual-data.js`와 `order-preview.html` 인라인 사본 양쪽을 같이 고쳐야 한다(`check-ritual-mirror.js` 대조 대상).

### 2-7. 담백 · 없어진 선택지를 카드가 아직 안내한다

```js
damback.detail[1] = {
  how : '하객에게 감사 인사를 전해요. 나레이션이 대신 전하거나, 두 분이 직접 짧게 인사할 수 있어요.',
  pick: '나레이션 대행 / 두 분 직접'
}
```

**나레이션 대행은 없어졌다.** 커밋 `8842582` "환영·첫인사를 '두 분 직접' 고정으로 — 선택 제거". 코드도 그대로다 — `applyCourse()`가 `S.welcome='self'`로 고정하고, 상태 복원 경로(1584줄)도 무조건 `S.welcome='self'`로 덮는다. `rowVal('welcome')`은 `'두 분이 직접 인사'` 한 줄을 반환한다.

**이건 기능 복원 제안이 아니다.** CLAUDE.md 제거 지시 보존 규칙에 따라 없어진 선택지는 되살리지 않는다. 고쳐야 할 건 **뒤에 남은 카피**다. 지금 상태로는 담백을 고른 부부가 "나레이션이 대신 해 주는구나"로 기대하고 들어와서, 직접 인사말을 써야 하는 화면을 만난다.

> 제안 · `COURSES.damback.detail[1]`
> `how`: `두 분이 하객에게 짧게 감사 인사를 전해요. 나레이션이 앞뒤를 열고 닫아 줘서, 가운데 한두 문장만 준비하면 돼요.`
> `pick`: `인사말 미리 적어 두기`

`BLOCK.welcome`이 실제로 도입(`먼저, 두 사람이 준비한 첫 인사가 있습니다.`)과 마무리(`여러분과 함께라서, 오늘이 더 빛납니다.`)를 나레이션이 맡는 구조라, 위 문구가 실제 동작과 정확히 맞는다.

**런북_코스A_담백.md의 확정 표도 낡았다** — "환영·첫인사 | 나레이션 대행"으로 적혀 있다. 같이 정정해야 두 문서가 갈리지 않는다.

### 2-9. 소요 시간이 세 곳에 따로 적혀 있다

같은 숫자가 세 군데 있다.

| 위치 | 형태 | 읽는 쪽 |
|---|---|---|
| `COURSES[x].min` | `'약 25분'` 문자열 | 코스 선택 카드 |
| `MIN.base` | `{damback:25, …}` 숫자 | **AI 상담사 지식베이스**(`api/_ritual-kb.js:75`) |
| `estMin()` 안 리터럴 | `{damback:25, …}` 숫자 | 빌더 실시간 예상 시간 |

지금은 셋 다 일치한다. 문제는 **가드가 이 셋을 대조하지 않는다는 것**이다. `check-ritual-mirror.js`는 `MIN.XM`이 빌더의 `var XM`과 같은지는 보는데(30~35줄), `MIN.base`와 `estMin()` 리터럴은 안 본다. 한쪽만 고치면 **AI 상담사는 "약 25분"이라 답하고 빌더 화면은 다른 숫자를 띄우는** 상태가 조용히 만들어진다. 같은 고객에게 같은 세션에서.

> 제안 (택1)
> **A안(권장):** `estMin()`이 리터럴 대신 `MIN.base`를 읽는다. `var base=(D.MIN.base[S.course])||25;` 원천이 둘로 줄고 `min` 문자열만 남는다
> **B안:** 리터럴은 두되 `check-ritual-mirror.js`에 대조 1건 추가 — `MIN.base[x] === Number(COURSES[x].min.replace(/\D/g,''))` 그리고 빌더 리터럴 파싱 비교

A안이 낫다. 이 빌더는 이미 `ritual-data.js`를 UMD로 동기 로드해서 쓰고 있어 추가 배선이 없다.

## 3. 이벤트별 짜임·분위기·디테일 제안

§2가 "틀린 것"이라면 여기는 "더 좋아질 수 있는 것"이다. 현재 큐가 이미 상당히 촘촘해서, 비어 있는 자리만 짚는다.

### 3-1. 지금 큐에서 통째로 빠진 규격 하나 — 침묵과 페이드

연구3(`연구3_사용자연구모드.md`)과 큐시트가 **침묵·페이드 규격을 이미 확정해 놨다.**

```
전환 침묵    1.5~2.5초 (무음 상한 3초)
페이드 인    1~2초
페이드 아웃  3~5초 (감정 고조 시 최대 10초)
성혼선언 직전 완전 정지 2~3초 → 선언 → 음악 하드 인
편지 낭독 후 침묵 1.5~2.5초
폐식        하드 스톱 금지 · 롱 페이드아웃
```

그런데 `BLOCK.*`의 `cue` 문자열 어디에도 **초 단위 숫자가 없다.** 있는 건 "잠시 정적", "짧은 여운", "음악 페이드 아웃" 같은 말이다. 이 큐가 그대로 부부의 인쇄 식순지와 디렉터 진행표가 되는데, 현장에서 "잠시"가 몇 초인지는 사람마다 다르다. 그리고 이 예식에는 사회자가 없어서 **타이밍을 잡아 줄 사람이 디렉터 한 명뿐**이다.

> 제안 · 감정 밀도가 높은 4곳에만 숫자를 넣는다. 전부 넣으면 큐가 기술문서처럼 읽힌다
> - `BLOCK.declare` 큐: `나레이션 선언 → 잠시 정적` → **`선언 직전 음악 완전 정지(2~3초) → 나레이션 선언 → 정적 유지 → 음악 하드 인`**
> - `BLOCK.letter` 큐: `끝나면 음악 페이드 아웃` → **`끝나면 침묵 2초 유지 후 음악 서서히 올림(3~5초)`**
> - `BLOCK.vow` 큐 끝에 추가: **`낭독 끝나고 2초 두었다가 다음 안내`**
> - `_close` 큐: `나레이션 마무리와 함께 마무리 음악 시작` → **`나레이션 마무리와 함께 음악 시작 · 하드 스톱 없이 길게 페이드아웃`**

### 3-2. 식전 안내 4클립에 재생 시각이 없다

`GUEST` 4클립(G1-1~G1-4)은 문안이 확정됐고 AI 고지도 들어갔다. 그런데 **언제 트는지가 어디에도 없다.** 디렉터가 현장에서 판단해야 한다.

> 제안 · 큐시트에 타임코드 한 줄씩. 예 — `G1-1 개장 15분 전 / G1-2 10분 전 / G1-3 5분 전 / G1-4 2분 전(착석 확인 후)`
> 특히 **G1-4는 "착석 확인 후"가 조건**이다. 이게 AI 고지가 들어간 클립이라 하객이 자리에 앉아 조용해진 뒤에 나가야 전달된다. 서서 인사 나누는 중에 틀면 고지가 묻힌다

### 3-3. 링 워밍 · 2~4분의 빈 구간이 촬영 기회다

`RINGWARM.all`의 나레이션은 잘 짜여 있다 — "오래 쥐지 마시고, 다음 분께 바로 전해 주시면 감사하겠습니다"까지 넣어 지연을 미리 막는다. 큐도 완결돼 있다(마지막 분 → 디렉터 → 트레이 → 반지 교환 때 전달).

문제가 아니라 **기회**가 하나 있다. 25명 전체 하객이면 반지가 도는 2~4분 동안 무대에서는 아무 일도 안 일어난다. 나레이션은 이미 끝났고 BGM만 흐른다. 부부는 서서 기다린다.

> 제안 · 이 구간을 **촬영 큐**로 명시한다. 우리는 촬영이 본체인 팀이다
> `반지가 도는 동안 = 하객 손·표정 클로즈업 구간 · 부부는 반지를 따라가는 시선으로 서 있기(정면 대기 금지)`
> 이 컷들이 나중에 140분 시퀀스에서 "모두의 축복이 반지에 담겼다"는 장면을 실제로 보여주는 소재가 된다. 지금은 나레이션이 그렇게 말하는데 영상 근거가 없다

### 3-4. 첫인사 · 부부가 얼어붙었을 때의 경로가 없다

덕담에는 `blessProxy`가 있다 — "부모님이 부담되시면, 나레이션이 대신 전해 드려요". 편지·서약에는 "울컥하면 배우자가 대신 이어 읽기"가 큐에 있다. **첫인사에만 대안 경로가 없다.**

첫인사는 예식에서 부부가 하객을 정면으로 마주 보고 말하는 첫 순간이고, 사회자가 없어서 받아 줄 사람도 없다. 가장 얼기 쉬운 자리다.

선택지를 되살리자는 게 아니다(제거 지시 보존). **현장 큐 한 줄**이면 된다.

> 제안 · `BLOCK.welcome`의 `cue` 끝에 추가
> `말이 막히면 디렉터가 미리 받아 둔 인사말 카드를 건네요 · 읽어도 괜찮아요`
> 부부가 빌더에서 `welcomeText`를 이미 입력하므로 카드는 자동으로 만들 수 있다. 인쇄물 2종(식순지·낭독 카드)이 이미 구현됐으니 **세 번째 인쇄물로 붙일 수 있다**

### 3-5. 베일 다운 · 옆문 동선이 없는 공간을 가정하지 않았다

`BLOCK.veil` 큐: `내려 주신 분은 옆문으로 먼저 착석 → 착석 확인 후 나레이션`

우리 기준 공간은 **25명·원형·퇴장 없음**이다(연구1 채택 3관문). 원형 배치에 옆문이 없을 수 있고, 있어도 그 동선이 하객 시야를 가로지른다.

> 제안 · 대안 동선을 큐에 병기
> `내려 주신 분은 옆문으로(옆문이 없으면 문 옆 첫 좌석을 미리 비워 두고 그리로) 먼저 착석`

### 3-6. 부모님 헌정 · 부모님이 앉아 있는지 서 있는지가 없다

`TRIBUTE.modes.*.cue`는 전부 부부 쪽 동작만 적는다 — "부모님께 꽃 전달 · 포옹", "큰절(또는 깊은 목례) · 일어나 포옹". **부모님이 그때 앉은 채인지 일어서서 맞는지가 없다.**

큰절은 특히 문제다. 부모님이 앉아 계셔야 절을 받는 그림이 되는데, 원형 배치에서 부모님 좌석이 어디인지도 정해진 게 없다.

> 제안 · `TRIBUTE` 공통 큐에 한 줄 · 좌석 배치 단계와 연결
> `양가 부모님 좌석은 단상에서 가장 가까운 정면 2열로 미리 지정 · 헌정 안내가 나오면 그대로 앉아 계시고, 부부가 다가가요(큰절은 앉으신 채로 받으심)`
> 좌석 배치도(`printSeatChart`)가 이미 있으니 **부모님 좌석을 배치도에서 고정 표시**하면 준비물 타임라인에도 자동으로 잡힌다

### 3-7. 미니멀 · 정점이 없는 코스를 그대로 둘지

`BLOCK.letter`만 `peak:true`를 갖는다. 이 표식은 완성 화면에서 "감정 정점" 배지를 다는 데 쓰인다(1552줄). 미니멀 기본값에는 편지가 없으므로 **정점 배지가 하나도 안 붙는다.**

이게 틀린 건 아니다. 미니멀의 `one`은 "담백에서 첫인사·편지를 뺀 최단 코스"이고 `feel`은 "약속만 또렷하게 남기고 싶은 두 분께"다. 정점을 의도적으로 안 만든 코스다.

다만 완성 화면에서 다른 코스는 배지가 뜨고 미니멀만 안 뜨면, 부부가 "우리 예식은 뭔가 빠졌나" 하고 읽을 수 있다.

> 제안 · 미니멀에서 `peak` 블록이 하나도 없을 때만 완성 화면에 한 줄
> `이 코스는 감정의 정점을 따로 두지 않고, 서약과 선언에 무게를 모아요.`
> 또는 `BLOCK.vow`에 조건부 `peak`(편지가 없을 때만)를 주는 방법도 있으나, 서약을 정점으로 부르면 다른 코스와 기준이 흔들린다. 문구 한 줄이 낫다

### 3-8. 팔레트로 코스 정체성이 무너질 때 알려 줄지

팔레트("이 코스에 없는 순서 더하기")는 사용자 지시로 열어 둔 기능이다(2026-07-19). 미니멀에 베일·링워밍·헌정·축배를 다 더하면 18분짜리가 30분 넘는 다른 코스가 된다. `estMin()`이 시간은 정확히 올려 주지만, **"이제 이건 미니멀이 아니다"라는 신호는 없다.**

이 빌더의 방침은 일관되게 "막지 않고 알린다"이다(`_cakeDup` 가드가 그 예 — 케이크가 두 번 잡히면 경고만 띄우고 선택은 고객 몫). 같은 방식으로 처리할 수 있다.

> 제안 · 팔레트 추가가 3개를 넘거나 예상 시간이 기준 코스의 1.4배를 넘으면 안내 한 줄
> `지금 구성은 <다른 코스명> 코스에 가까워요 · 그 코스로 시작하면 더 자연스럽게 정리돼요`
> 가장 가까운 코스는 `curSeq()`와 각 코스 `seq`의 교집합 크기로 계산하면 된다. 강제 전환은 하지 않는다

## 4. 통합 규칙 제안 — "이완은 정점 앞에 둔다"

§2-1부터 §2-4까지가 전부 같은 질문이다. **가벼운 순간(밸리·축가)을 감정 정점의 앞에 둘 것인가 뒤에 둘 것인가.** 지금 코드에는 이 질문에 답하는 단일 규칙이 없고, 그래서 코스마다 다르게 굴러가고 팔레트는 또 다르게 군다.

근거 문서도 표면적으로는 갈린다.

- 연구2 표: `정점 직후 | 반지교환·케이크 등 가벼운 시각적 순서 | 눈물 뒤 숨 고르기(이완)` → **정점 뒤**
- 코스설계_v1 코스 A·B, 큐시트 2026-07-20: `성혼선언 → 밸리 → 편지(정점)` → **정점 앞**

**갈리지 않는다고 본다.** 연구2가 말하는 "정점 직후의 숨 고르기"는 우리 구조에서 이미 다른 것이 담당하고 있다.

```
선언 중반형(담백·미니멀·축하): 편지◆ → [덕담/축배] → 폐식 나레이션(CLOSE_NAR)
선언 종반 통합형(감동·가족):    편지◆ → 헌정 → 성혼선언 → 폐식 나레이션
```

정점 뒤에는 이미 하강 곡선이 두 단계 깔려 있다. 여기에 케이크를 하나 더 끼우면 이완이 아니라 **착지 지연**이 된다. 반대로 정점 **앞**은 비어 있다. 서약·반지의 절차 구간에서 편지의 감정 구간으로 톤 없이 그냥 넘어간다. 큐시트가 밸리에 붙인 설명이 정확히 그것이다 — "편지 전 톤 낮추며 정돈".

> **제안 규칙 (코스설계_v1 §설계 규칙에 추가)**
>
> **7. 이완 순간(사이 순서·축가)은 감정 정점 직전에 둔다.** 정점 이후의 이완은 통합 순서(헌정·성혼선언)와 폐식 나레이션이 이미 담당한다. 정점 뒤에 가벼운 순간을 더하면 착지가 지연되고, 예식이 그 순간의 정서로 끝난다(연구2 안티패턴 3).
> **단, 축배는 예외다.** 축배는 이완이 아니라 밝은 착지이며, 클로징 배치가 확정돼 있다(연구1).

이 규칙 하나로 §2-1(`RANK_OV`) · §2-2(담백 `seq`) · §2-3(감동 `at:6`) · §2-4(축하 `at:7`)가 전부 같은 근거에서 도출된다. 개별 수정 네 건이 아니라 규칙 하나의 적용 네 건이 된다.

## 6. 이 검토가 확인하지 못한 것

- **실제 고객 레코드로 화면을 못 봤다.** `momentedit.kr:443`이 이 세션에서 CONNECT 403이라 라이브 접속이 막힌다. 모든 판정은 코드 정독 + `node`로 원천 덤프 + 문서 대조로 나왔다. 저장된 `S.ord`가 실제로 어떤 모양인지는 미확인
