## 0. 목표 (성공의 정의)

**고객**: 계약하면 내 결혼식 진행이 "이미 완성"돼 있고, 순간을 하나 더할 때마다
**내 예식의 나레이션을 귀로 미리 듣는다.** 저장하면 예식 대본이 소리로 완성된다.
→ 어느 웨딩 업체에도 없는 경험. 계약 전환과 만족의 핵심 무기.

**운영자**: 녹음 세션 1회로 전 파일 제작 → 이후 모든 고객에게 무한 재사용(한계비용 0).
**재녹음이 나오지 않게 설계하는 것이 이 프로젝트의 운영 핵심.**

**시스템**: 지금 만드는 오디오 파일·매니페스트가 그대로 **Phase 3 당일 GO 콘솔의 재생 자산**이 된다.
한 번 녹음해서 두 곳(마이페이지 미리듣기 + 예식 당일 실제 진행)에 쓴다.

## 1. 대원칙 (사용자 확정 · 2026-07-10)

1. 뼈대(고정 순서)는 운영자가 정한다.
2. 얹기 이벤트 카탈로그도 운영자가 정한다.
3. 나레이션은 운영자가 미리 녹음한 오디오 파일 (자동 생성 아님).
4. 고객은 마이페이지에서 완성된 자기 식순의 나레이션을 직접 들어본다.
5. 기존 구조(뼈대+얹기+나레이션 3층 · mypage.html 단독 · GAS는 저장만) 유지.

## 2. 이 설계의 승부처 (깊은 고민의 결과)

### 승부처 ① 오디오 자산은 두 번 쓰인다
마이페이지 미리듣기용으로 만드는 파일이 곧 **예식 당일 실제로 홀에 흐를 나레이션**이다.
따라서 파일 체계를 처음부터 "당일 재생 가능" 기준으로 설계한다:
`assets/narration/manifest.json` (id · 파일명 · 길이 · 대본 텍스트)을 단일 연결점으로 두면,
마이페이지도 GO 콘솔(Phase 3)도 같은 매니페스트를 읽는다. 재녹음 시 파일만 교체하면 전부 반영.

### 승부처 ② 이름 문제의 답은 "하이브리드"가 유력
녹음 파일엔 신랑·신부 이름을 못 넣는다. 그런데 입장 호명("신랑 OO, 신부 OO")은 예식의 하이라이트다.
- 후보 A: 전 문장 무이름 재작성 (파일 관리 최소 · 호명의 감동은 포기)
- 후보 B (유력): **평소 문장은 무이름 공용 + 이름이 꼭 필요한 문장(입장 호명 등 1~2개)만 고객별로 추가 녹음.**
  건당 30초 녹음 작업. 마이페이지엔 공용 버전 재생 + "당일엔 두 분 성함이 들어간 버전으로 준비돼요" 안내.
- 후보 C: 화면 텍스트만 이름 표시, 오디오는 전부 무이름
→ 3-1에서 결정. B는 감동과 운영비용의 균형점.

### 승부처 ③ 재녹음 최소화 = 문장 변형 최소화 + 순서 강제
파일 수 = 문장 수 × 변형 수. 편지(방향 3종)·서약(2종)·환영(2종)·와인(캡슐 2종)처럼 변형이 곱해지면
녹음 목록이 불어난다. 예상 파일 수: 고정 블록 ~10개 + 이벤트 ~20개 = **약 25~35개** (충분히 관리 가능).
단, **순서를 강제한다: 카탈로그·문장이 100% 확정된 뒤에만 녹음** (2장·3장 완료 → 녹음 → 4장).
확정 전에 녹음하면 재녹음 세션이 반드시 발생한다.

## 4. 진행 방식 (2026-07-11 라운드 방식으로 전환)

**코스에서 파인으로 반복 심화**: 라운드 1 = 큰 방향 6개(흐름·행사 구성·고객 선택권·마이페이지 UX·BGM나레이션 노출·옵션 처리) → 라운드 2 = 각 방향 안의 중간 결정 → 라운드 3+ = 디테일·문구·시간. 아래 챕터 스텝 목록은 "빠뜨리면 안 되는 항목 체크리스트"로 유지하되, 진행 순서는 라운드가 우선한다. 시간·멘트는 마지막 라운드.

- 질문은 **한 번에 1개**, 객관식(추천안 첫 번째·이유 포함). 아래 스텝 순서대로 → 누락 방지.
- 매 질문에 ①현재 상태 ②추천+이유 ③대안 ④이 결정이 영향 주는 곳을 함께 표시.
- 답 확정 즉시 이 문서에 기록. 애매하면 ⏸보류로 두고 진행 (막히지 않기).
- **챕터 끝마다 확정표 검수** 후 다음 장. 언제든 이전 결정 번복 가능 (문서에 수정 기록).
- 전 챕터 후: 녹음 대본 전달 → 운영자 녹음 → 파일 수령 → 구현 → 배포 → 라이브 확인.

## 13. ★큰틀 확정 (2026-07-12) — 자물쇠 3 + 코스 프리셋 + 슬롯 스왑

```
🔒 고정(3, 전 예식 공통):  입장  →  환영인사  →  [코스 본문]  →  폐식·촬영안내
📋 코스 본문 = 미리 설계한 이벤트 배열(서약·반지·성혼·편지·축가 등은 코스 안에 존재)
```

- **자물쇠 = 딱 3개**: 입장 · 환영인사 · 폐식/촬영안내. (개식은 입장에 흡수 가능 — 대본 단계 결정)
- **서약·반지·성혼도 자물쇠가 아님** → 코스 안에 담김. 담백한 코스는 생략 가능, 격식 코스는 포함. §10 카탈로그 12종은 '코스 구성 부품'으로 위치 변경.
- **추천 코스 다수** = 연구·분석으로 앞으로 정성껏 제작(다음 대작업). 지금은 큰틀만.
- **스왑**: 코스마다 [바꾸기] 가능한 슬롯을 **1~3개로 제한**(코스 성격 따라 다름). 슬롯 외 이벤트·순서는 고정 → 우리가 짠 흐름이 안 무너짐.
- **스왑 후보 = 슬롯별 큐레이션(①안)**: 그 자리에 어울리는 2~3개만 제시. 파일 최소·배치 완성도 통제.
- 모듈형 오디오(§12)와 정합: 스왑해도 그 이벤트 파일만 교체 재생 → 재녹음 0.

### 이 결정이 바꾼 것
- 큰3(고객 선택권) = **코스 택1 + 슬롯 1~3개 스왑**으로 구체화(자유 조립 아님).

## 12. ★아키텍처 확정 (2026-07-12) — 모듈형 오디오 + 반자동 GO 콘솔

이 프로젝트의 뼈대 결정. 이후 모든 설계는 여기서 파생된다.

### 12-1. 오디오 구조 = 묶음 세그먼트(코스 고정형 · 2026-07-12 사용자 확정)
- **단위 = 이음새까지 붙인 세그먼트**: `[BGM + 앞 이벤트 마무리멘트 + 브릿지 + 다음 이벤트 시작멘트]`. 낱개 파일이 아니라 연결이 완성된 묶음.
- 코스가 정해져 있으니 **코스별로 세그먼트를 통으로 미리 제작**(프리미어 프로) → 연결 완성도 최고.
- **슬롯 스왑 = 교체 지점 세그먼트 1개만 미리 수정**해 대기. 나머지 코스 세그먼트는 그대로 재사용.
- 시작 멘트는 여전히 자기완결형(앞 순서 미지칭)으로 써서 스왑 변형 제작을 최소화.
- **탈락 대안**: A(양쪽 참조 전환 = 조합 폭발) · B(코스 통짜 단일파일 = 스왑 시 통짜 재편집).

**제작 물량(코스 확정 후 산정)**: 코스 N종 × 세그먼트 + 슬롯별 스왑 변형 세그먼트. 코스가 고정이라 상한이 분명. 세그먼트 파일명에 버전 포함(R7 캐시 무효화).

### 12-1b. 큐사인 익히기 = 기능적 리허설 (V5 격상 · 2026-07-12)
- 고객이 마이페이지에서 **확정된 자기 코스 오디오를 미리 들어봄**. 단순 미리보기가 아니라 **"언제 걷고·언제 말하고·멘트가 어디서 끝나는지" 큐를 몸에 익히는 연습 도구**.
- 신랑신부와 스튜디오가 **같은 큐를 공유** → 당일 합이 맞음. 사회자 없이도 매끄러운 핵심 근거.
- 큐시트에 "이 멘트가 끝나면 → 입장 시작" 식의 **큐 안내 텍스트**를 오디오와 함께 노출.

### 12-2. 당일 재생 = ②반자동 GO 콘솔 (✅ 확정)
- 마이페이지에서 확정된 식순대로 **파일이 자동으로 줄 세워진 재생 화면**. 디렉터는 "다음 ▶"만 누른다(순서 실수 0).
- 당일 흐름: `[BGM] → 시작멘트 → (사람이 하는 실제 진행) → 마무리멘트 → [BGM 브릿지] → 다음 칸 시작멘트 …`
- 이 콘솔이 기획서의 "Phase 3 GO 콘솔". manifest.json(파일·길이·대본·큐)을 마이페이지 미리듣기와 **공유**한다(한 번 만들어 두 곳에서 사용).
- 안정장치(기획 계승): 전체 프리로드·리허설 모드·나레이션 더킹·비상 페이드·이전 다시·GO 연타 가드·화면 꺼짐 방지.

### 12-3. 파생 확정
- V2(매끄러운 구조) = 12-1로 해결. R3 연구는 "자기완결 도입·브릿지"의 문장 완성도를 높이는 재료로 재정의.
- 고객 화면엔 **추천 코스 5종을 프리셋**으로 제공(고르기 쉬움) → 타임라인에서 빼고 더하기(자유 조립). 코스 5종 구성은 다음 단계.
- manifest.json 스키마에 이벤트별 {시작멘트 id, 마무리멘트 id, BGM 큐, 길이}를 포함 → 준비물·예상시간·큐시트·GO 콘솔이 전부 이 하나에서 자동 생성.
