## 0. 목표 (성공의 정의)

**고객**: 계약하면 내 결혼식 진행이 "이미 완성"돼 있고, 순간을 하나 더할 때마다
**내 예식의 나레이션을 귀로 미리 듣는다.** 저장하면 예식 대본이 소리로 완성된다.
→ 어느 웨딩 업체에도 없는 경험. 계약 전환과 만족의 핵심 무기.

**운영자**: 녹음 세션 1회로 전 파일 제작 → 이후 모든 고객에게 무한 재사용(한계비용 0).
**재녹음이 나오지 않게 설계하는 것이 이 프로젝트의 운영 핵심.**

**시스템**: 지금 만드는 오디오 파일·매니페스트가 그대로 **Phase 3 당일 GO 콘솔의 재생 자산**이 된다.
한 번 녹음해서 두 곳(마이페이지 미리듣기 + 예식 당일 실제 진행)에 쓴다.

## 1. 대원칙 (사용자 확정 · 2026-07-10)

1. 뼈대(고정 순서)는 운영자가 정한다.
2. 얹기 이벤트 카탈로그도 운영자가 정한다.
3. 나레이션은 운영자가 미리 녹음한 오디오 파일 (자동 생성 아님).
4. 고객은 마이페이지에서 완성된 자기 식순의 나레이션을 직접 들어본다.
5. 기존 구조(뼈대+얹기+나레이션 3층 · mypage.html 단독 · GAS는 저장만) 유지.

## 2. 이 설계의 승부처 (깊은 고민의 결과)

### 승부처 ① 오디오 자산은 두 번 쓰인다
마이페이지 미리듣기용으로 만드는 파일이 곧 **예식 당일 실제로 홀에 흐를 나레이션**이다.
따라서 파일 체계를 처음부터 "당일 재생 가능" 기준으로 설계한다:
`assets/narration/manifest.json` (id · 파일명 · 길이 · 대본 텍스트)을 단일 연결점으로 두면,
마이페이지도 GO 콘솔(Phase 3)도 같은 매니페스트를 읽는다. 재녹음 시 파일만 교체하면 전부 반영.

### 승부처 ② 이름 문제의 답은 "하이브리드"가 유력
녹음 파일엔 신랑·신부 이름을 못 넣는다. 그런데 입장 호명("신랑 OO, 신부 OO")은 예식의 하이라이트다.
- 후보 A: 전 문장 무이름 재작성 (파일 관리 최소 · 호명의 감동은 포기)
- 후보 B (유력): **평소 문장은 무이름 공용 + 이름이 꼭 필요한 문장(입장 호명 등 1~2개)만 고객별로 추가 녹음.**
  건당 30초 녹음 작업. 마이페이지엔 공용 버전 재생 + "당일엔 두 분 성함이 들어간 버전으로 준비돼요" 안내.
- 후보 C: 화면 텍스트만 이름 표시, 오디오는 전부 무이름
→ 3-1에서 결정. B는 감동과 운영비용의 균형점.

### 승부처 ③ 재녹음 최소화 = 문장 변형 최소화 + 순서 강제
파일 수 = 문장 수 × 변형 수. 편지(방향 3종)·서약(2종)·환영(2종)·와인(캡슐 2종)처럼 변형이 곱해지면
녹음 목록이 불어난다. 예상 파일 수: 고정 블록 ~10개 + 이벤트 ~20개 = **약 25~35개** (충분히 관리 가능).
단, **순서를 강제한다: 카탈로그·문장이 100% 확정된 뒤에만 녹음** (2장·3장 완료 → 녹음 → 4장).
확정 전에 녹음하면 재녹음 세션이 반드시 발생한다.

## 4. 진행 방식

- 질문은 **한 번에 1개**, 객관식(추천안 첫 번째·이유 포함). 아래 스텝 순서대로 → 누락 방지.
- 매 질문에 ①현재 상태 ②추천+이유 ③대안 ④이 결정이 영향 주는 곳을 함께 표시.
- 답 확정 즉시 이 문서에 기록. 애매하면 ⏸보류로 두고 진행 (막히지 않기).
- **챕터 끝마다 확정표 검수** 후 다음 장. 언제든 이전 결정 번복 가능 (문서에 수정 기록).
- 전 챕터 후: 녹음 대본 전달 → 운영자 녹음 → 파일 수령 → 구현 → 배포 → 라이브 확인.

```
1장 뼈대(14스텝) → 2장 이벤트(22스텝) → 3장 대본(7스텝)
      → ★운영자 녹음 세션★ → 4장 파일(6스텝) → 5장 듣기UX(3스텝)
      → 6장 화면(5스텝) → 7장 반영(5스텝) → 배포·라이브 확인
```

구현(코드 작업)은 3장 확정 시점부터 병행 가능 (오디오 없이 화면·데이터 먼저, 파일은 나중에 끼움).
